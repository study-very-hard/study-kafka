## Sec 4 카프카 클러스터 운영
### 22. 카프카 클러스터를 운영하는 여러가지 방법

- 클러스터 운영상의 노하우, 보안설정, 모니터링 도구는 너무 많기에 SaaS 를 사용하는 것을 추천한다고 함
- SaaS의 장점
  - 웹 대시보드 혹은 CLI등을 제공해줌 -> 세부 설정 간편, 모니터링 등 운영 지표를 카프카가 관리해줌
- 서비스 형태의 종류:
  - on-premise
    - 자체적으로 서버를 구축하고 운영
    - 상황에 맞춘 커스터마이징 구성 가능
    - 도입 비용 + 운영 및 관리를 위한 유지보수 비용이 발생함
  - IaaS (Infrastructure-as-a-Service)
    - 물리/가상 컴퓨팅 리소스를 발급받아 사용
    - 사용자가 운영체제 및 애플리케이션 등을 설정, 배포, 운영
  - PaaS (Platform-as-a-Service)
    - 어플리케이션 개발 및 실행 환경 제공
    - 사용자가 컴퓨팅 리소스를 신경 쓰지 않아도 됨
  - SaaS (Software-as-a-Service)
    - 소프트웨어의 전체 생명주기를 업체에서 관리하고 기능을 제공
    - 소프트웨어 관리를 업체에 위임하고 기능만 사용할 때 유용
  - 각 형태별 카프카 운영 방법:
    - on-premise: 자체적으로 서버를 구축하고 운영
      - 가장 낮은 레이어부터 진행해야하기에 많은 관리와 유지보수가 필요함
      - 오픈소스 혹은 기업용(유료) 카프카를 설치해 운영
      - 운영상의 높은 난이도가 존재할 가능성이 있음. 노하우 필요
    - IaaS: AWS, GCP 등의 컴퓨팅 리소스를 발급받아 사용
      - 구축형에 비해 스케일러블한 환경 구성 가능
      - 운영상의 높은 난이도가 존재할 가능성이 있음. 노하우 필요 -> 그래도 구축형보다는 좋다
    - SaaS: 소프트웨어의 전체 생명주기를 업체에서 관리하고 기능을 제공
      - 컨플루언트 클라우드 또는 AWS MSK 등
      - 사용자가 운영 및 관리를 신경 쓰지 않아도 됨
      - 다양한 주변 생태계 (ksqlDB, 모니터링 도구 등)을 옵션으로 제공
- 기업용 카프카의 특징:
  - 기능상의 튜닝이 되어있음
  - 여러 종류의 DB에 연결가능한 커넥터 등의 추가기능이 제공됨
  - 모니터링 툴 제공됨
- 직접 설치해 운영할 경우:
  - IaaS와 구축형이 가장 흔한 운영 방식
  - 파일 시스템에 전송된 데이터가 저장되고, 대규모 통신이 일어나기 때문에 고성능의 하드웨어를 사용하는 것을 권장
  - 하드웨어 스펙:
    - 메모리: 32GB. 
      - 힙에 6GB, 나머지는 OS의 페이지 캐시 영역으로 활용
    - CPU: 24 core
      - SSL등 보안 설정 필요할 경우 더 높은 코어 필요
    - 디스크: RAID10 으로 설정된 디스크
      - NAS 사용 불가 -> 데이터 처리량에서 이슈가 발생하기 때문
    - 네트워크: 통신량에 맞춰 설정
    - 파일 시스템: XFS / ext4 
- 운영상의 팁:
  - 개발 환경:
    - 브로커: 5개
      - 복제가 제대로 진행되고 있는지, 여러 옵션들이 정상적으로 처리됨을 확인하기 위해서는 많은 브로커가 있는게 더 좋은 테스트 환경이 될 것 같다.
    - 메모리: 16GB (6GB 힙, 나머지는 OS의 페이지 캐시 영역으로 활용)
    - CPU: 16 core
    - 디스크: 환경의 사용량에 따라 조정
  - 상용(운영) 환경:
    - 브로커: 10개
    - 메모리: 32GB (6GB 힙, 나머지는 OS의 페이지 캐시 영역으로 활용)
    - CPU: 24 core
    - 디스크: 사용량에 따라 조정
  - 디스크 사용량 조정 팁:
    - 복제가 들어가기에 복제 수 만큼 데이터의 양이 많아짐

### 23. SaaS형 아파치 카프카 소개
- Confluent
  - 카프카에 대한 개념을 최초 고안한 제이 크랩스와 동료들이 설립한 회사
  - 오픈소스 카프카에 어떤 기능이 더 필요한가를 고민해 나온 제품
  - Connector, ksqlDB, rest proxy 등의 툴들을 오픈소스화 하는 등 선구적 역할
  - ksqlDB:
    - 스트리밍 데이터를 실시간으로 처리하고 분석할 수 있는 SQL 기반의 스트리밍 쿼리 엔진
    - 토픽에 있는 데이터를 filtering, join 등을 할 수 있게 해주는 기능
  - 두가지 형태로 서비스를 제공:
    - 클라우드:
      - 클라우드 기반 카프카 클러스터 (SaaS)
      - 120개가 넘는 커넥터, ksqlDB, 스키마 레지스트리 서비스 제공
      - 99.95% SLA
      - 엔터프라이즈 수중의 보안 수준 제공
      - 데이터 적재 제한 없음
        - 디스크에 대한 고민을 하지 않아도 되는 장점이 있음
      - 운영상의 고민 사항이 적어지기 때문에 저자도 토이 프로젝트에서 활용해 봤다고 함
    - 플랫폼:
      - 구축형 기반 설치형 카프카 클러스터
      - 필요에 따라 컨플루언트 팀에서 지원, 학습 제공
      - 서버를 내부에서 발급하여 직접 설치
      - 단계별 스토리지 기능 (Tiered Storage) 제공
      - GUI 기반 모니터링 시스템 제공
- AWS MSK(Managed Streaming for Apache Kafka)
  - 오픈소스 아파치 카프카를 AWS에서 설치와 모니터링을 제공해주는 서비스
    - 주키퍼, 클러스터 설정 등을 자체적으로 진행해줌
    - 카프카 버전을 선택해서 생성 가능 -> 구축형에서 전환시 유용함
  - 서버에 대한 설정 변경 등도 웹 콘솔을 통해서 다수의 브로커들을 쉽게 변경 가능
  - 보안 설정도 클러스터 생성시에 TLS 인증 설정 가능
  - 이미 AWS를 운영 중인 경우 적용이 더 쉬워짐

### 24. SaaS형 아파치 카프카 장점과 단점
- 장점:
  - 인프라 관리의 효율화
    - 카프카 브로커/주키퍼 들을 계속해서 모니터링하며 위험을 감지할 필요가 없어짐
  - 모니터링 대시보드 제공
    - 브로커 상태, 토픽 상태, 소비자 그룹 상태 등을 시각적으로 확인 가능
    - 지표로 수집하는 데이터의 종류가 굉장히 많은데, 이를 개발자가 학습하지 않아도 됨
      - 정말로 중요한 지표를 알아서 확인하게 해주는 기능을 제공
  - 보안 설정
    - TLS 인증, ACL 설정 등 다양한 보안 기능은 오픈 소스 레벨에서도 제공되나, 어떤 상황에 어떤 보안을 적용하고 운영하는 것을 결정하고 진행하는 것은 쉬운일이 아니다
      - 이를 간단한 웹 설정으로 제공한다
- 단점:
  - 서비스 사용 비용
    - 구축형, IaaS는 서버 사용 비용만 든다
    - MSK의 경우 아무것도 안해도 시간당 1.632$ (현재 8코어 32기가 기준) -> 한달에 약 177만원..
      - 영상 촬영 시점 기준 인스턴스를 직접 할당받아 쓰는 경우 약 절반 가까이 절감되었음
      - 그러나 인력적 비용에 대한 절감을 고려했을 때도 유의미한지는 고민이 필요함
  - 커스터마이징 제한
    - 직접 운영을 하다보면 우리 서비스에 맞춘 최적화가 가능한데, 이러한 디테일한 설정이 어려워짐
    - 멀티 클라우드 (2개 이상의 퍼블릭 클라우드를 동시 운영) 혹은 하이브리드 클라우드 (사내 서버와 퍼블릭 클라우드를 함께 사용) 가 불가능함
  - 클라우드의 종속성
    - 특정 클라우드 제공자에 종속될 수 있음
    - 비용적으로 더 나은 서비스 제공자가 생겼다거나, 최적화를 위한 IaaS 전환을 고려해야할 때 어려움이 있을 수 있음
- 여러 단점이 있더라도 SaaS가 더 나은 경우:
  - 인프라 관리의 효율화, 모니터링 대시보드 제공, 보안 설정 등의 장점이 단점을 상쇄할 수 있음
    - 노하우가 없는 팀이라면, SaaS가 더 나은 선택지가 될 수 있음

## Sec 5 아파치 카프카 CLI 활용

### 27. 카프카 CLI 툴 소개
- 카프카 운영을 하다보면, 토픽이 진짜 생성되었는지, 데이터가 정상적으로 가는지, 파티션의 갯수를 확인한다던지 하는 등의 경우에 활용하게 되는 CLI
  - 그렇기 때문에 운영을 잘 하려면 CLI를 사용하는 방법을 잘 알고 있어야 함
- 명령어가 길어서 처음에는 입력하기 좀 부담스러움
  - 그러나 자주 사용해야하기 때문에 익숙해지는 것이 좋다
- CLI를 통해 토픽 관련 명령을 실행할 때 필수 옵션과 선택 옵션:
  - 선택 옵션:
    - 설정하지 않을 경우, 브로커의 기본 설정이나 CLI 기본 값으로 대체됨
      - Ex: 토픽이 생성될 때 파티션의 개수 -> CLI 로 명령할 때 지정하지 않았다면 브로커에 지정된 디폴트 값으로 생성됨


### 28. 로컬에서 카프카 브로커 실행
- 강의 촬영 시점 기준으로는 3버전은 아직 사용에서 흔히 활용되지는 않았다
- 사용할 브로커 버전: 2.11-2.1.0 -> 기존 AWS test 시 활용한 버전이라 유지
- 설정 (server.properties) 값에 대한 설명:
  - log.dir: 로그 세그먼트가 쌓이는 경로
  - num.partitions: 신규로 토픽이 생성될 때 기본으로 생성되는 파티션의 개수
- 실행 순서: 주키퍼를 우선 실행 시킨 후, 주키퍼가 정상적으로 떴을 때 카프카 브로커를 실행
- 카프카가 제공하는 스크립트들의 활용
  - 카프카 브로커가 정상적으로 떴는지 확인할 수 있는 방법: `bin/kafka-broker-api-version.sh`
    - bin/kafka-broker-api-version.sh --bootstrap-server <broker_host>:<broker_port>
    - 카프카의 실행 상태, 브로커에 적용된 옵션등을 확인 할 수 있음
  - 카프카에 등록된 토픽 목록 확인: `bin/kafka-topics.sh`
    - bin/kafka-topics.sh --list --bootstrap-server <broker_host>:<broker_port>

### 29. kafka-topics.sh
- 클러스터 정보와 토픽 이름을 토대로 토픽을 생성하는 스크립트
- `bin/kafka-topics.sh`
  - `--create`: 생성 옵션 (이 옵션을 달면 생성됨)
  - --topic <topic_name>
  - `--bootstrap-server <broker_host>:<broker_port>`: 클러스터 서버 IP 정보와 포트
  - `--describe`: 토픽의 상세 정보를 확인하는 옵션
    - 토픽명, 파티 개수, ReplicationFactor, 다른 컨피그 (segment 관련 등)
    - 어느 브로커에 리더가 있는지, ISR 구성이 어케 되어있는지 등도 확인 가능
  - `--alter`: 설정을 변경할 때 사용가능한 옵션
    - ex:파티션 개수를 늘리기 위해 사용할 수 있음
      - 늘리는건 가능하나, 줄이는 건 불가함
        - 줄이려하면 InvalidPartitionsException 이 발생함
  - 내 버전에서의 명령어 예시: `bin/kafka-topics.sh --zookeeper test-broker02:2181 --list`

### 30. kafka-config.sh
- 토픽에 옵션을 설정하기 위한 스크립트
- `bin/kafka-configs.sh`
  - `--alter`: 설정을 변경할 때 사용가능한 옵션
  - `--add-config <key>=<value>`: 설정을 추가하거나 변경
    - `min.insync.replicas`: 최소 동기화 복제본 수
- server.properties 를 직접 조회하지 않고 브로커 서버 인스턴스 외부에서 조회가 가능

### 31. kafka-console-producer.sh
- 카프카에 있는 토픽에 메시지를 전송하기 위한 스크립트
  - 주로 테스트 용도로 데이터를 넣어보고 싶을 때 사용하는 스크립트
- `bin/kafka-console-producer.sh`
  - 필수 옵션:
    - `--bootstrap-server <broker_host>:<broker_port>`: 클러스터 서버 IP 정보와 포트
    - `--topic <topic_name>`: 전송할 토픽 이름
  - bootstrap server 와 topic 옵션만 적용하면 실행 후 입력 모드로 전환됨
  - `--property <설정>=<설정 값>` 설정을 추가하는 옵션 
    - `"parse.key=true"`: 메세지 키를 포함시킨다는 옵션
    - `"key.separator=:"`: 키와 값의 구분자를 지정하는 옵션
    - ex: bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic test --property "parse.key=true" --property "key.separator=:"
      - 명령어 실행후 입력 콘솔 모드에서 key1:no1 를 입력시 토픽에 key1이라는 메세지 키의 no1 이라는 메세지 값을 가진 데이터가 적재됨을 확인할 수 있음
      - 내 버전(2.11-2.1.0)에서는 `bin/kafka-console-producer.sh --broker-list localhost:9092 --topic test01-only --property "parse.key=true" --property "key.separator=:"`
- **메세지 키가 필요한 경우:**
  - 특정 키를 가진 데이터의 처리에 순서 보장이 필요한 경우
  - 메세지키가 있으면 하나의 파티션으로만 그 데이터가 적재되기에 순서 보장이 가능해짐
    - 없으면 round-robin이라 보장이 어려울 수 있음

### 32. kafka-console-consumer.sh
- 카프카에 있는 토픽에서 메세지를 수신하기 위한 스크립트 
  - 주로 테스트 용도로 데이터를 임시적으로 조회할 때 사용하는 스크립트
- `bin/kafka-console-consumer.sh`
  - 필수옵션:
    - `--bootstrap-server <broker_host>:<broker_port>`: 클러스터 서버 IP 정보와 포트
    - `--topic <topic_name>`: 조회할 토픽 이름
  - 선택 옵션:
    - `--from-beginning`: 토픽의 처음부터 메세지를 조회
    - `--property <설정>=<설정 값>`: 설정을 추가하는 옵션
    - `--max-messages <숫자>`: 최대 메시지 수를 지정하는 옵션
    - `--partition <파티션 번호>`: 특정 파티션에서 메시지를 조회하는 옵션
    - `--group <group_name>`: 컨슈머 그룹 지정
      - 이 값이 설정되었을 경우에만 컨수머가 컨숨을 하게되면 커밋이 됨
        - 컨숨하여 커밋하게 되면 어디에 존재하게 되나? -> __consumer_offsets에 저장됨
        - 컨수머 그룹이 설정되어야 __consumer_offset이 생성되며 저장됨
  - 내 버전에서의 명령어: `bin/kafka-console-consumer.sh --bootstrap-server test-broker02:9092 --topic test01-only --property print.key=true --property key.separator="-"`
- 메세지 키와 밸류만 확인 할 수 있다
### 33. kafka-consumer-groups.sh
- 컨수머 그룹을 관리하기 위한 스크립트
- `bin/kafka-consumer-groups.sh`
  - 필수 옵션:
    - `--bootstrap-server <broker_host>:<broker_port>`: 클러스터 서버 IP 정보와 포트
  - `--describe`: 컨수머 그룹의 상태를 조회
    - 몇번 오프셋의 레코드까지 현재 그룹에서 가져갔는지, 현재 가져간 파티션 번호, 컨수머 랙 (생성된 최신 레코드의 오프셋 - 현재까지 가져온 레코드의 오프셋), 생성된 최신 레코드의 오프셋, 현재까지 가져온 레코드의 오프셋 등의 정보를 볼 수 있음 
  - `--list`: 컨수머 그룹 목록 조회
  - `--reset-offset <읽기 설정 옵션> <실행 옵션>`: 오프셋을 재설정하는 옵션
    - 읽기 설정 옵션:
      - `--to-earliest`: 가장 초기 오프셋으로 재설정
      - `--to-latest`: 가장 최신 오프셋으로 재설정
      - `--to-offset <offset>`: 특정 오프셋으로 재설정
      - `--to-datetime <datetime:yyyy-MM-ddTHH:mm:ss>`: 특정 시간으로 오프셋을 이동
  - 활용처:
    - 컨수머 그룹에 할당된 10억건의 메세지가 있을 때, 
      - 우리는 최신의 10억건 째부터 바로 필요한 경우: `--reset-offset --to-latest` 를 활용해 신규 데이터를 처리하도록
      - 우리는 옛날 데이터들을 다시 처리해야해: `--reset-offset --to-earliest` 를 활용해 초기 오프셋부터 데이터를 처리하도록
  - 내 버전에서의 명령어 예시: `bin/kafka-consumer-groups.sh --bootstrap-server test-broker02:9092 --group test-gr --describe`

### 34. 그 외 커맨드 라인 툴
- `kafka-producer-perf-test.sh`: 프로듀서 성능 테스트를 위한 스크립트
- `kafka-consumer-perf-test.sh`: 컨슈머 성능 테스트를 위한 스크립트
  - 위 두 명령어 모두 실행하는 기기로부터 카프카 브로커까지 얼마나 빠르게 전송/수신되는지를 알 수 있음
- `kafka-reassign-partitions.sh`: 파티션 재할당을 위한 스크립트
  - 핫스팟이 된 파티션이 있을 경우, 이 스크립트를 통해 파티션을 재할당하여 부하를 분산시킬 수 있음
  - 리더를 변경해야하는 경우에도 활용 가능
    - 설정을 통해 리밸런싱을 자동화 할 수도 있음 (`auto.leader.rebalance.enable=true`)
  - 주키퍼 정보를 전달해야함
- `kafka-delete-records.sh`: 특정 오프셋 이후의 레코드를 삭제하는 스크립트
- `kafka-dump-log.sh`: 로그 파일의 내용을 덤프떠서 확인하는 스크립트
  - 애플리케이션 개발자는 자주 쓸일은 없을 것 같다

### 35. 카프카 토픽을 만드는 두가지 방법
1. kafka-topics.sh --create 옵션을 활용
   - 토픽에 대한 상세한 옵션 설정이 가능하기에, 일반적으로 더 적합한 방법
2. 컨수머 / 프로듀서가 생성되지 않은 토픽에 대해 데이터를 요청하면 브로커에 생성됨
   - 브로커의 설정에 자동 설정이 켜져있을 경우에만 가능
   - 이 경우 브로커에 설정된 옵션들을 따라 생성됨
     - 파티션 수 등
