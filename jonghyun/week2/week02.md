# 아파치 카프카 애플리케이션 프로그래밍 Sec 1~3

## Sec 2 아파치 카프카의 역사와 미래
### 3. 아파치 카프카의 탄생과 기본 구조
- 링크드인에서 내부 데이터 흐름을 개선하기 위해 개발함.
- 애플리케이션끼리 통신하여 데이터를 처리하는 것이 아니라 중앙집결 시켜 처리할 수 있도록 만든 구조
- 이것이 카프카!
- 메시지 큐 구조를 사용함
  - 프로듀서를 통해 메세지를 받으면 토픽의 파티션중 하나에 할당되고 컨수머가 소비하는 구조
  - 하지만 일반적인 큐와 달리 소비되도 사라지지 않음

### 4. 아파키 카프카가 데이터 파이프라인으로 적합한 4가지 이유
1. 높은 처리량
   - 카프카는 프로듀싱 하거나 컨숨할 때 모두 묶어서 전송함
   - 네트워크 비용은 데이터 양이 많으면 무시할 수 없는 양이 되기에 배치로 전송
   - 파티션 분배를 통해 동일데이터를 병렬처리할 수 있게 해줌
2. 확장성
   - 데이터가 적을 때 -> 클러스터의 브로커 수를 최소로 줄여 스케일 인
   - 데이터가 폭증 -> 브로커 개수를 늘려 스케일 아웃
   - 프로듀서에서 데이터가 어떻게 생성되는지 패턴의 예측이 어렵기에 이러한 확장성은 크게 도움이 됨
3. 영속성
   - 데이터를 메모리에 저장하지 않고 파일 시스템에 저장함
     - 운영체제 레벨에서 파일 시스템을 최대한 활용하는 방법을 적용해 속도 문제 해결
       - 파일 I/O 성능 향상을 위해 페이지 캐시 영역을 메모리에 따로 생성하여 읽은 파일 내용을 메모리에 올려서 다시 사용하는 방식.
       - 이 방식이 카프카에서 특별한 이유는 뭘까? DB는 이걸 안하는건가?
         - 디비의 경우에도 당연히 사용함 
           - 버퍼풀에 저장해 둠
         - 카프카에서 더 특별한건, 카프카는 OS 페이지 캐시에 전부 맡겨도 괜찮은 선입선출 구조이기 때문
           - 결국 순차적으로 쌓이는 구조이고, SQL 처럼 Join 이나 가져오는 데이터 형식의 변환등이 없이 저장된 바이트를 그대로 전송할 수 있기 때문
   - 디스크 기반의 파일 시스템을 활용하기 때문에 장애가 발생해도 재시작시 수신했던 메세지가 유실되지 않고 재처리 가능함
4. 고가용성
   - 클러스터로 운영되는 특징상 일부 서버(브로커)에 장애가 발생하더라도 무중단으로 안전하고 지속적으로 데이터를 처리할 수가 있음.
     - 클러스터로 구성된 카프카가 메세지를 수신 받으면 모든 브로커에 복제함

### 5. 빅데이터 아키텍쳐의 종류와 카프카의 미래
- 초기 빅데이터 플랫폼:
  - 원천, 파생, 서빙 데이터로 분류하고, 수집된 원천 데이터를 통해 파생 데이터를 만들고 마지막에 서빙 데이터로서 유저들에게 다시 제공되었음
  - 이러한 구조의 한계:
    - 실시간으로 생성되는 데이터들에 대한 인사이트를 서비스 애플리케이션에 빠르게 전달되지 못함
    - 파생되는 데이터들의 히스토리 파악이 어려움
    - 데이터의 가공이 생기면서 파편화되어 데이터 거버넌스를 지키기 어려움
- 람다 아키텍처:
  - 3가지 레이어:
    - 배치 레이어
      - 원천 데이터를 모아서 특정 시간, 타이밍마다 일괄 처리
    - 스피드 레이어
      - 원천데이터를 실시간으로 분석하는 용도
      - 카프카가 여기에 위치함
    - 서빙 레이어
      - 배치 / 스피드 레이어에서 만든 데이터를 저장해 서비스 애플리케이션이 활용할 수 있도록 해줌
  - 한계: 
    - 배치와 스피드 레이어로 분리됨
      - 분석처리를 위한 레이어가 두개가 되며 중복 처리되거나, 로직을 두벌 짜야하는 이슈가 발생함
      - 이로인해 하나의 로직을 추상화해 2번의 배포를 진행해야했고, 디버깅도 각각해야하는 등 관리포인트가 늘게됨
    - 이를 해결하기 위해 나온게 아래의 카파 아키텍쳐
- 카파 아키텍처:
  - 배치 레이어가 사라진 람다 아키텍처
    - 디버깅, 배포, 운영 분리 파편화를 제거함
  - 카프카를 활용함으로서 달성됨!
    - 배치 데이터와 스트림 데이터를 모두 모을 수 있어야 함
- 배치 데이터:
  - bounded(한정된) 데이터 처리
  - 대규모 분산 처리 수행
  - 분/시간/일 단위 처리를 위한 지연 발생
  - 복잡한 키 조인 수행 
  - 하둡등을 통해 MapReduce 방식으로 처리
- 스트림 데이터:
  - unbounded(무한) 데이터 처리
  - 지속적으로 데이터가 들어옴
  - 분 단위 이하 지연
  - 단순한 키 조인만 수행
- 카프카에서 스트림 데이터를 배치로 사용하는 방법:
  - 마테리얼라이즈드 뷰로 활용하는 방식
    - 로그에 시간을 남김으로서, 시간을 기준으로 데이터를 처리하면 스트림으로 적재되었더라도 배치로 활용이 가능함
- 스트리밍 데이터 레이크:
  - 2020 카프카 서밋에서 제이 크랩스가 제안한 아키텍처
  - 서빙 레이어마저 제거하고 스피드 레이어만 남김.
    - 카프카에 분석과 프로세싱을 완료한 거대한 용량의 데이터를 저장해 사용한다면 서빙 레이어가 불필요해진다는 아이디어.
  - 현실적으로 달성하긴 어렵다:
    - 자주 사용하는 데이터와 자주 사용하지 않는 데이터를 구분해서 유지할 필요가 없는 데이터는 남길 이유가 없어짐
      - 현재는 티어드 스토리지 방식으로 해결함
        - 자주 접근하는 데이터만 카프카에 남기고, 자주 사용되지 않는 데이터는 오브젝트 스토리지에서 관리하는 방식
  - 그러나 미래에는 모든 데이터 레이크 아키텍처를 카프카로 통합할 수 있는 미래가 올 것 같다.

## Sec 3 카프카 기본 개념 설명

### 8. 오픈소스 아파치 카프카 생태계
- 카프카 클러스터
- 프로듀서
- 컨수머
- 스트림즈
- 커넥트
  - 프로듀서 컨수머로 개발하면 되지 않나? 
    - 클러스터로 운영이 가능하다는 차이가 있음
    - 반복적으로 여러번 생성할 수 있고, 하나의 덩이로 운영할 수 있다는 차이점이 있음
      - 한번 데이터를 설정해두고, 상황에 맞춰 여러번 반복할 때 사용이 가능할 듯 함
  - 소스 (프로듀서 역할)
  - 싱크 (컨수머 역할)
- 미러메이커
  - 이번 강의에서는 다루지 않음
- 이러한 소스들은 전부 자바로 제공이 되고, 그 외의 언어들의 경우는 3rd 파티이기에 모든 기능이 제공되는지가 보장되지는 않는다.

### 9. 카프카 브로커와 클러스터
- 주키퍼
  - 카프카 클러스터 운영을 위해 반드시 필요한 애플리케이션
    - 2점대 버전 까지만 필수
      - 3점대부터는 필수는 아님 
      - 현재는 KRaft 로 대체되고 있다는 듯 함.
- 클러스터
  - 하나의 브로커로만 운영하는 것은 일반적이지 않다고 함
  - 3개의 브로커로 클러스터로 운영하는 것이 더 일반적

### 10. 카프카 클러스터와 주키퍼
- 하나의 주키퍼 앙상블에 여러대의 카프카 클러스터를 운용하는 것도 가능
  - 각각의 클러스터는 다른 수의 카프카 브로커를 가질 수 있음
- 3.0 부터의 카프카는 주키퍼 없이 클러스터로 운영이 가능함
### 11. 카프카 브로커의 역할들
- 컨트롤러
  - 클러스터로 운영을 하게되면, 다수의 브로커 중 하나가 컨트롤러 역할을 함
    - 리더 == 컨트롤러
  - 다른 브로커들의 상태를 체크하고, 문제가 발생할 경우 문제가 있는 브로커의 리더 파티션을 재분배
  - 컨트롤러 역할의 브로커가 죽으면 -> 다시 컨트롤러를 선출하여 역할을 수행함
- 데이터 삭제
  - 브로커만이 토픽의 데이터를 삭제할 수 있다. 
    - 다른 어플리케이션 (프로듀서/컨수머 등)으로 삭제는 불가능
  - 데이터 삭제는 파일 단위로 이뤄지고, 그 단위를 `로그 세그먼트`라고 칭함
    - 로그 세그먼트에는 다수의 데이터가 포함되어 있어 DB처럼 특정 데이터를 선별해 삭제는 불가능
    - 딜리트 옵션을 통해 일정 시간이나, 정해진 용량 한계치에 따라 데이터를 삭제하도록 설정할 수 있음
    - 컴팩션이라는 옵션을 통해 가장 최신의 레코드를 제외한 나머지를 모두 삭제할 수도 있음
      - 특수한 상황에서만 사용
- 컨수머 오프셋 저장
  - 컨수머가 메세지를 받고 커밋(commit)을 브로커에 보내면, 브로커 내부에서 컨수머가 소비한 어느 파티션에 어느 오프셋까지 소비되었는지를 기록하는 기능
    - `__consumer_offset`에 저장됨
- 그룹 코디네이터
  - 컨수머 그룹의 상태를 체크해서 파티션을 컨수머와 매칭되도록 분배하는 역할을 함
    - 파티션과 컨수머는 1:1로 매핑됨 -> 해당 컨수머가 그룹에서 빠지게 되면 해당 컨수머를 삭제하고 그룹내에 다른 컨수머를 신규 할당하여 데이터가 처리되도록 해줌
      - 이를 `리밸런싱`이라 부른다

### 12. 브로커 로그와 세그먼트
- 브로커의 핵심 역할: 데이터의 저장
  - server.properties.log.dir 옵션으로 저장되는 파일 디렉터리를 지정할 수 있음
- 세그먼트가 나뉘는 기준:
  - 설정값을 통해 용량과 시간을 기반으로 
    - log.segment.bytes: 바이트 단위 최대 세그먼트 (디폴트 1기가)
    - log.roll.ms(hours):세그먼트 생성 이후 다음 파일로 넘어가는 주기 (디폴트 7일)
  - 로그 파일의 이름은 세그먼트 파일 내부에 첫번째 레코드의 오프셋 번호로 생성된다.
    - ex:000000000000.log -> 0번째 오프셋을 가진 레코드부터 시작하는 세그먼트
- 현재 데이터가 적재되고 있는 세그먼트 파일 == 액티브 세그먼트
  - 삭제 대상 조건에 포함되더라도 삭제 되지 않는 파일
- 카프카의 데이터가 삭제되는 주기:
  - 액티브 세그먼트가 아닌 세그먼트중 retention 옵션에 따라 세그먼트 단위로 삭제됨
    - 시간이 지나거나, 용량에 따라서 삭제됨

### 13. 세그먼트와 삭제 주기(cleanup.policy)
- cleanup.policy=delete
  - active한 세그먼트 외의 세그먼트를 삭제하는 방식
  - 설정값:
    - retention.ms(minutes, hours): 세그먼트를 보유할 최대 기간 (디폴트 7일)
    - retention.bytes: 세그먼의 로그 적재 바이트 값 (디폴트는 -1 -> 지정하지 않는다는 뜻)
    - log.retention.check.interval.ms: 세그먼트가 삭제 영역에 들어왔는지 확인하는 간격 (디폴트 5분)
  - 상황에 따른 운영 고민:
    - 특정 토픽의 데이터 양이 굉장히 많은 경우:
      - retention.ms 가 너무 길면 브로커의 파일 시스템에 저장되는 로그 파일이 너무 많아짐
      - 브로커의 디스크 크기에 따라 어느 정도 용량으로 저장할지 고민이 필요함
        - ex: 하루에 1테라씩 쌓인다면 디폴트 따라 7일이면 7테라가 됨 -> 인스턴스 뻥남
    - retention.ms 은 `일반적으로는 3일` 정도로 유지한다고 한다
      - 보통 근무를 월~금 하고, 토,일에 노니까 3일로 해두면 금요일 밤 시작해 토욜일욜에 장애가 발생해도 월요일에 처리가 가능해서 그렇다고 함
  - 데이터의 삭제는 세그먼트 파일 단위로 이뤄지기 때문에, 개별 레코드 별 삭제는 불가능 함
    - 그렇기 때문에 프로듀서에서 레코드를 브로커에 생성할 때는 검증이 매우 중요함
      - 컨수머에서의 검증도 마찬가지
- cleanup.policy=compact
  - 각각의 레코드(메세지)에는 키와 밸류가 있음
  - 세그먼트 파일 내에서 가장 최신에 있는 가장 최신의 메세지(오프셋이 가장 큰) 키의 데이터를 남기고 나머지 오래된 메세지들을 삭제 
    - 다른 세그먼트에 있는 중복 메세지 키도, 아래의 영역 별 압축으로 인해 사라진다
    - 이 때문에 세그먼트 파일의 이름에 포함되는 시작 오프셋이 세그먼트에서 삭제될 수도 있다
  - 클린 로그: 이미 압축을 거쳐서 최신화가 완료된 로그 세그먼트 파일
  - 테일 영역: 클린 로그가 모여있는 영역을 테일 영역이라고 함
    - 이 레코드들에는 중복되는 메시지 키가 없다
  - 더티 로그: 압축을 아직 거치지 않은 레코드들의 집합
  - 헤드 영역: 더티 로그가 모여있는 영역
    - 중복된 메세지키가 있을 수 있다
  - min.cleanable.dirty.ratio:
    - 데이터 압축의 시작 시점을 결정하는 설정값 (디폴트 0.5)
    - 0 < x < 1 의 값으로 설정하며, 더티 로그의 비율이 지정한 비율을 넘어서면 클린업을 실행함
    - 유의 사항:
      - 비율을 너무 높게 설정하면 (ex: 0.9) 9:1 비율이 될 때 까지 압축이 실행되지 않아 디스크 용량을 차지하는 시간이 길어질 수 있음
      - 너무 낮게 설정하면 (ex: 0.1) 압축이 너무 자주 일어나 최신의 데이터를 유지할 수 있다는 장점이 있으나 브로커에 부하를 주게됨

### 14. 복제(replication)
- 장애 허용 시스템으로 동작하도록하는 원동력
- 복제를 왜 하는걸까?
  - 클러스터로 묶인 브로커 중 하나가 죽더라도 데이터를 유실하지 않고 안전하게 사용하기 위해서
  - 그러한 상황을 막기 위해 각각의 브로커에 분산해서 복제해 저장
- 카프카의 데이터 복제 단위: 파티션
  - 특정 브로커에 파티션 리더가 존재하고, 팔로워 파티션에 넘겨줘서 저장됨
- 토픽의 생성시 replication factor를 설정해서 복제의 수를 정할 수 있고, 대부분의 경우 브로커수에 맞춰서 지정함
  - replication factor에는 리더도 포함됨
  - 디폴트는 브로커의 기본 옵션에 따라서 달라진다고 함
  - ex:3으로 지정하면 리더하나 팔로워 둘로 토픽이 생성되는 구조
- 프로듀서 컨수머가 직접 통신하는 대상은 리더 파티션 뿐이다.
  - 데이터 베이스에서는 데이터의 생성이나 수정 삭제는 몰라도 read는 복제에서도 가능한데, 카프카의 경우는 왜 컨숨도 리더에서만 가능할까?
    - 예상: 
      - 디비의 경우 replica lag을 허용할 수 있지만, 컨수밍하는 시점의 데이터의 오차를 통한 이슈가 훨씬 클 것 같다
      - __consumer_offset의 기록을 위해
- 팔로워 파티션이 신규 데이터를 가져오는 방식:
  - 팔로워에서 현재 자기가 가지고 있는 오프셋과 리더의 오프셋을 주기적으로 비교하고, 차이가 발생하면 복제해서 가져가는 방식
- 복제의 트레이드 오프:
  - 디스크 사용량을 증가하게 되는 대신, 가용성을 끌어올리는 것
- 리더 파티션이 죽으면 승급 과정을 통해 신규 리더가 선출된다
  - 근데 이러면 일시적으로 레플리카의 수가 줄어드는데 이 때는 복제가 어떻게 이뤄지는 것일까?
  - 나의 추측: 해당 설정이 맥시멈에 대한 설정이기 때문에, 너무 많은 팔로워 파티션에 복제하는 것을 방지하는거지, 적을 경우에는 문제가 안되는 것이 아닐까?
  - 소스 코드 분석을 통한 결론: 
    - replicationFactor → PartitionAssignment.replicas 생성 → PartitionRegistration.replicas 저장 → 각 브로커가 자기 brokerId가 replicas에 있는지 확인 → 없으면 follower fetcher를 시작하지 않음
    - 즉 팔로워에서 하는 것이기 때문에 수가 안맞더라도 문제가 되지 않는다
- replication factor를 1로 설정해도 되는 경우:
  - 일부 데이터가 좀 유실되도 괜찮은 경우
    - ex:GPS 데이터의 경우 중간중간에 불필요한 데이터가 껴 있기에 전체 흐름에 필요하지 않음 

### 15. ISR(In-Sync-Replicas)
- 리더 파티션과 팔로워 파티션이 싱크가 된 상태를 의미함
  - 리더 파티션의 모든 오프셋 정보가 팔로워 파티션에도 복제가 완료된 것
- ISR이 안맞은 상태 (리더의 데이터가 전부 복제되지 못한 상태)에서 신규 리더가 선출되면, 신규 리더에는 없는 이전 리더의 레코드가 있을 수 있음.
  - 이러한 상태일 때도 신규 리더를 선출해서 가용성을 살리겠다!
    - unclean.leader.election.enable=true 을 설정
    - 유실을 감수하고 복제가 안된 팔로워 파티션을 리더로 승급
  - 유실을 절대 감수하지 않고, 리더 파티션의 브로커가 복구 될 때까지 중단하겠다!
    - unclean.leader.election.enable=false 을 설정
    - 유실을 감수하지 않고 가용성을 포기
    - 전체 클러스터가 맛이 가는 것이 아니라, 해당 토픽에 대해서만 중단되는 것

### 16. 토픽과 파티션
- 토픽은 최소 하나 이상의 파티션으로 이뤄져 있다
- 파티션은 큐와 비슷한 구조로 이루어져 있다
  - 다만 카프카에서는 컨수머가 데이터를 가져가도 데이터는 유지됨!
- 토픽 생성시 파티션이 배치되는 방법:
  - 파티션은 일반적으로 0번 브로커부터 시작해 round-robin 방식으로 리더 파티션들이 각 브로커 마다 하나씩 생성됨
    - 이렇게 분산이 되기에 특정 브로커에 통신이 집중되는 핫스팟을 방지함
    - 데이터가 많아지더라도 브로커를 늘림으로서 대응이 가능해짐
- 특정 브로커에 파티션이 쏠리는 현상:
  - 특정 브로커에 리더가 집중되는 경우, 해당 브로커에 부하가 집중될 수 있음
    - 이 경우 모든 클라이언트 (프로듀서 / 컨수머)가 해당 브로커와 통신하게 됨 
      - 이리 되어 해당 브로커의 CPU/RAM 등의 리소스 사용량이 유난히 커질 수 있음
  - 이를 막는 것이 카프카 클러스터를 운용할 때 중의해야하는 점
    - 카프카에서는 `kafka-reassign-partitions.sh` 스크립트를 사용하여 파티션을 재배치할 수 있음
- 파티션 개수와 컨수머 개수의 처리량
  - 컨수머 파티션의 관계는 1:1
    - 파티션이 한개라면 컨수머를 늘려도 추가적인 처리량이 늘수는 없음
  - 그렇기에 처리량을 늘리려면 파티션과 컨수머를 같이 늘려야 병렬 처리량이 늘어남
    - 실무적으로는, 최대 늘어날 수 있는 요청 폭증량을 예측해 그 수에 맞는 파티션 컨수머를 만드는 것이 일반적이다
- 파티션 개수를 줄이는 것은 불가능함
  - 디스크에 저장되어 있는 세그먼트들에 대해 파티션이 줄어 들게 되면 해당 디렉터리들을 병합해서 타임스탬프 인덱스등을 재분배하는 과정이 있어야 하는데 이러한 작업은 어렵고, 비용이 많이드는 작업이라 이러한 기능에 대한 지원을 카프카는 하지 않는 것으로 본다
    - KIP-694에서 파티션 개수를 줄이는 것에 대한 논의가 진행된 적이 있으나 진행되고 있지는 않다고함
      - [아직도 discussion 중](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/165227379/KIP-694+Support+Reducing+Partitions+for+Topics)임을 확인할 수 있다._

### 17. 레코드
- 레코드를 이루는 것들:
  - timestamp
    - 스트림 프로세싱에 활용되기 위해서 사용됨
    - 프로듀서에서 설정하지 않으면 프로듀서에서 생성한 시간이 들어감
      - 설정을 통해 브로커에 적재 되는 시간으로 설정할 수도 있다
      - message.timestamp.type 으로 설정 가능
  - headers
    - 0.11 부터 제공된 기능
    - 키밸류 데이터를 저장할 수 있음
    - 레코드의 스키마 버전이나 포맷등 프로세싱에 참고할 만한 데이터를 담을 수 있음
      - http의 헤더와 유사한 용도
  - message key
    - 카프카의 독특한 데이터 처리 방식중 하나
    - 데이터를 처리하는게 아니라 분류를 위해서 사용하는 키
      - 파티셔너를 통해 어떤 파티션에 할당될지를 정하는 값
    - 필수값은 아님
      - 지정하지 않으면 null 로 설정됨
      - 이 경우 파티셔너는 round-robin으로 균등하게 파티션에 적재함
    - 기본 파티셔너를 사용히는 경우 키가 있으면 해시값에 의해 특정 파티션에 매핑되어 전달되게 된다
  - message value
    - JSON/CSV/오브젝트로 되어있는 데이터를 담는 공간
    - 제네릭으로 사용자에 의해서 지정됨
    - 다양한 형태(Float, Byte[], String)로 지정하여 사용이 가능
      - 지정 포맷으로 직렬화/역직렬화 클래스를 만들어서 POJO 형태를 만들면 커스텀해서 사용이 가능
    - 컨수머 입장에서는 어떤 포맷으로 역직렬화할지 알 방법이 없기 때문에, 미리 역직렬화 포맷을 알고 있어야 한다
      - 그래서 편리하게 사용하고자 String 직렬화/역직렬화를 사용한다고 함
        - 이 경우 int, float 같은 데이터도 String으로 저장하기 때문에 공간낭비가 문제가 될 수도 있음
  - offset
    - 프로듀서가 생성한 레코드에는 없고, 브로커에 실제 저장될 때 생성됨
    - 0부터 생성되고 1씩 증가함
    - 각 파티션마다 독립적으로 증가함
      - 중복 처리를 방지하기 위한 목적으로 활용됨

### 18. 유지보수하기 좋은 토픽 이름 정하기
- 토픽 이름 제약 조건:
  - 빈 문자열은 지원하지 않음
  - 마침표 하나(.) 또는 둘(..)로 시작하거나 끝날 수 없음
  - 토픽의 이름은 249자 미만
  - 영어 대/소문자 아라비안 숫자, 마침표(.), 하이픈(-), 밑줄(_) 사용 가능
    - 그 외의 문자는 불가능
  - 카프카 내부 로직 관리 목적으로 사용되는 2개의 토픽 이름(__consumer_offsets, __transaction_state)으로 생성 불가
  - 마침표(.)와 언더바(_)가 동시에 들어가면 안됨
    - 생성은 가능하나 사용시 이슈가 발생할 수 있고, 사용하면 워닝 메세지가 발생함
    - 이 때문에 되도록 영어 소문와 숫자, 하이픈을 황용하는 것을 추천함
- 의미있는 토픽 이름이 중요한 이유
  - 한번만든 토픽의 이름은 변경이 불가능함
  - 토픽의 이름은 데이터의 얼굴이 된다. -> 대충 작명시 유지보수에 어려움을 겪을 확률이 높다
    - abcd, bigdata, test-XXXXXXX 이런 이름들은 무얼 목적으로 만들어졌는지 확인이 불가함
  - 이름에 대한 규칙을 사전에 정의하고, 구성원들이 이를 따르는 것이 중요함
    - 규칙을 따르지 않으면 유지보수와 운영에 어려움이 발생할 수 있음
      - 실제로 사용하는지 아닌지 등에 대한 파악도 어렵고, 운영시 혼란을 초래할 수 있음
    - 규칙을 따르지 않는 토픽 이름을 가진 토픽들은 주기적으로 확인후 사용여부를 컴토해 삭제하는 것을 추천
      - 테스트 등 단발성의 토픽이면 삭제 처리
      - 안좋은 이름으로 운영중인 토픽이라면 명확한 네이밍을 지은 새 토픽 생성후 마이그레이션을 진행하는게 더 좋을 것 같다는 의견
- 네이밍 컨벤션으로 잡을 때 넣으면 좋은 요소들:
  - 환경
  - 팀명
  - 메시지 타입
    - 직렬화 역직렬화를 알 수 있게 지정해두면 좋음
  - 서비스명
  - 클러스터 네임
  - 지라 번호
  - ex: <환경>.<팀명>.<어플리케이션명>.<메시지타입>

### 19.클라이언트 메타데이터와 브로커 통신
- 클라이언트 메타데이타
  - 클라이언트(프로듀서/컨수머)는 `리더 파티션의 위치(어느 브로커에 있는지)`를 알기 위해서 메타데이터를 필요로함
  - 클라이언트는 메터데이터를 요청하고 카프카 클러스터가 응답하는 구조
    - 클러스터 구조가 아니고 리더가 존재하지 않는다면 불필요햔 구조
  - 옵션값:
    - metadata.max.age.ms: 메타데이터를 강제로 리프레시하는 간격 (디폴트 5분)
    - metadata.max.idle.ms: 프로듀서가 idle 할떄 메타데이터를 캐시에 유지하는 기간 (디폴트 5분)
      - ex: 프로듀서가 특정 토픽으로 데이터를 보낸 이후 이 값으로 지정한 시간이 지나면 강제로 메타데이터를 리프레시
  - 메타데이타 이슈가 발생한 경우:
    - 리더 파티션이 다운되거나 모종의 이유로 리더가 아닌 잘못된 파티션 정보를 리더로 인식하는 경우 (아직 메타데이타가 리프레시 되기 이전에 클라이언트에서 잘못된 파티션으로 요청을 보내는 경우):
