# Sec 10 카프카 커넥트

---
### 카프카 커넥트 소개
- 카프카 커넥트란? 
  - 오픈소스로 제공하는 툴중 하나로 주로 토픽에 데이터를 넣거나 뺄 때 템플릿 형태로 파이프라인을 반복해서 생성할 때 사용함
- 어플리케이션 전체 영역을 카프카 커넥트라고 칭함
  - 실직적으로 구현하는 구현부는 각각 소스(프로듀서 역할)/싱크(컨수머 역할) 커넥터로 칭함
- 모니터링 상의 이점:
  - 기존 프로듀서/컨수머 구조는 각각 어플리케이션에 모니터링을 달아야 하지만, 커넥트를 쓰게되면 커넥트 애플리케이션만 모니터링하면 데이터의 생성/소비에 대한 모니터링이 가능함
- 커넥트 내부 구조:   
![img.png](img.png)
  - 태스크: 로직을 실행하는 가장 낮은/작은 단위
    - 실질적으로 데이터를 처리하는 스레드 = 태스크 스레드
    - 소스(프로듀스)/싱크(컨숨)하는 로직이 구현되는 구현부
  - 커넥터: 커넥터 스레드도 띄워져서 태스크들을 관리하는 오케이스트레이션 담당
    - 한개의 스레드에서 태스크들을 관장
    - 설정 값을 받고, 검증을 주로한다

### 커넥터
- 소스 커넥터: 프로듀서 역할
  - 특정 소스 (파일 시스템 / 데이터베이스 등) 에서 데이터를 가져와서 토픽으로 넣는 역할
- 싱크 커넥터: 컨수머 역할
  - 토픽의 데이터를 가져와서 활용해 다른 저장소 (파일 시스템 / 디비 등)에 적재하는 역할
- 저자가 생각하는 커넥터를 제일 많이 활용하는 영역: 파일 시스템의 데이터를 저장한다든가 DB와 연동하는 부분
  - ex: MySQL 같은 RDBMS에 데이터가 저장되면, 지속적으로 토픽에도 데이터를 저장하고 싶은 경우
    - 커넥터가 유의미한 경우: 비슷하게 SELECT해오는 테이블이 존재하고 그에 맞춰 특정 토픽에 프로듀스하는 로직이라면, 반복적인 작업이 될 수 있기 때문에 커넥터를 하나 만들어두면 여러 케이스에 대응해서 사용이 가능함
- 커넥터 플러그인
  - 커넥터는 기본적으로 플러그인 형태로 동작
    - ex: MySQL, MongoDB 플러그인 등으로 연결을 시도함
  - 오픈소스 커넥터: 오픈소스로 열려있는 커넥터 플러그인
    - 직접 커넥터를 만들 필요가 없고, 그 안에 들어갈 태스크만 정의해서 사용가능함
    - 다만 모든 오픈소스의 라이선스가 풀려있는 것은 아니기에 사용시 라이선스를 확인해서 참고해야함
  - 직접 개발 커넥터: 개발자가 직접 필요한 파이프라인을 정의해서 jar 파일을 빌드해서 커넥트에 추가시켜서 플러그인으로 실행하는 방식 

- 컨버터, 프랜스폼:
  - 커넥터를 운영할 때 반드시 필요한 옵션은 아니지만, 풍부하게 도와주는 역할을 함 
  - 커넥트 내부의 데이터 (스키마 + value로 구성되어 있음)을 카프카에 저장되는 byte[]로 변환해주는 역할을 담당함
  - 컨버터: 데이터를 처리하기 전에 스키마를 변경하도록 도와줌
  - 트랜스폼: 데이터 처리시 각 메시지 단위로 데이터를 간단하게 변환하기 위한 용도로 사용됨
    - ex: JSON 데이터를 커넥터에서 사용할 때 트랜스폼을 사용하면 특정 키를 삭제하거나 추가할 수 있음

### 커넥트 배포 및 운영
- 카프카 커넥트의 실행방식은 두가지로 나뉨: 1. 단일 모드 2 분산 모드
- 단일 모드(Standalone 모드): 단일 애플리케이션으로 실행됨
  - 하나의 커넥트 프로세스에서 하나의 커넥트 역할만 담당하게 만드는 구조.
    - 소스/싱크가 하나가 아닌 각각의 커넥트 애플리케이션
  - 단일 프로세스로 실행되기에 고가용성 구성이 불가 -> 단일 장애점 (Single Point Of Failure) 가 될 수 있음
    - 주로 개발 환경이나 중요도가 낮은 파이프라인에 사용
- 분산 모드(Distributed mode): 여러 프로세스가 하나의 그룹으로 이루어져서 분산해서 운영됨
  - 보통 2개 ~ 100개 이상으로 운영하는 것이 일반적
    - 저자는 500개 이상까지도 운영해본 경험이 있다.
  - 프로세스를 여러 개 운영하는데 장점이 있음 -> 소스 커넥터 / 싱크 커넥터가 스레드로 실행되기 때문에 부족한 컴퓨팅 리소스를 스케일 아웃을 통해 극복이 가능함 
  - 운영환경에서는 일반적으로 분산모드로 운영하게 됨
- 커넥트에 요청을 보내 실행시키는 방식: REST API
  - 정의된 REST API를 통해 어떤 커넥터를 실행해달라는 명령을 내리면 파이프라인을 신규 스레드를 생성해서 운영되고, 필요없어지면 삭제도 가능함

### 단일모드 커넥트
- 디버깅이나 테스트 용도, 혹은 중요도가 떨어지는 데이터 파이프라인을 운용할 떄 사용
- 실행하기 위해서는`connect-standalone.properties` 설정을 수정하여야 한다. (다른 파일을 만들고 설정값으로 줘도 됨)
- 예시 실행 명령어: `bin/connect-standalone.sh config/connect-standalone.properties config/connect-file-source.properties`
  - 각 명령어 해석: 
    - `bin/connect-standalone.sh`: 카프카 커넥트 실행 스크립트
  - `connect-standalone.properties`: 커넥트 설정
  - `connect-file-source.properties`: 커넥터 설정

### 분산모드 커넥트
- 사용환경에서 가장 많이 쓰이는 커넥트
  - 페일오버가 가능하고, 지속적인 스케일 아웃이 가능
- 동일한 group.id를 지정한 커넥트들은 마치 클러스터가 된 것 처럼 하나의 커넥트 인스턴스에 REST API로 요청을 보내더라도 설정을 통해 분산되어 모든 커넥트 인스턴스에 전파가됨 
- 설정 (`connect-distributed.properties`):
  - `offset.storage.topic`: 어느 오프셋까지 읽었는지에 대한 데이터가 보관된 토픽  
  - `config.storage.topic`: 커넥트 설정에 대한 데이터가 보관된 토픽
  - `status.storage.topic`: 각 커넥트의 상태에 대한 데이터가 보관된 토픽
  - `offset/config/status.storage.replication.facotr`: 각 오프셋/설정/커넥트에 대한 복제 개수
  - 위 설정들은 분산 모드로 실행할 때 카프카 내부에서 사용하는 토픽이라 생각하면 됨
    - 그 말인 즉슨 위 토픽들에 데이터를 임의로 넣거나 하게되면 문제가 될 수 있기에 자체적인 접근을 막아야함
  - 카프카 클러스터에 설정 정보를 남겨 신규 인스턴스가 뜰 때 활용할 수 있음

### 커스텀 소스 커넥터
- 필요한 디펜던시: `implementation 'org.apache.kafka:connect-api'`
  - 커넥터 개발에 필요한 클래스들이 포함된 라이브러리
  - JVM 언어에서 사용이 가능함
- 소스 커넥터와 소스 태스크를 생성해야함
- 소스 커넥터:
  - 커넥터 설정 파일을 초기화하고 어떤 태스크를 사용할 것인지 정의하는데 사용됨
  - `SourceConnector` 클래스를 상속받아 필요 설정을 오버라이드해 구현하면 된다
    - `taskConfigs`: 여러개의 태스크가 뜰 때 각 태스크 별로 다른 설정을 주기위해 활용
- 소스 태스크:
  - 데이터를 다루는 부분의 코드 영역
  - 카프카 토픽의 오프셋이 아닌 자체적인 오프셋을 관리하는데, 이 오프셋은 소스 커넥터에서 읽는 소스에서 어디까지 읽었는지에 대한 데이터를 다루는 오프셋으로, 이전 강의에서 다룬 설정 파일 중 `offset.storage.topic` 에서 저장되는 오프셋은 태스크에서 다루는 오프셋을 의미함 (소스 커넥터가 밀어넣는 토픽의 오프셋이 아님)
  - `SourceTask` 클래스를 상속받아서 태스크를 구현하면 됨
    - `version`: 태스크에 대한 버저닝을 위해 활용
    - `start`: 커넥트에서 제공된 설정을 통해 초기화시키는 메서드
    - `poll`: 태스크의 데이터를 토픽으로 보내는 메서드
      - 프로듀서의 send 역할을 하는 메서드
      - 일정 간격마다 호출되어서 실질적으로 데이터를 처리하는 용도
      - 이 메서드에서 리턴하는 값이 토픽으로 올라가게 된다

### 커넥터 옵션값 설정시 중요도(Importance) 지정 기준
- 커넥터 설정에 중요도를 넣는 설정 값으로, 중요도에 대한 설정
- 이 옵션은 그냥 명시성을 위해 주석같은 인지성으로 넣는 값으로 HIGH를 넣는다고 따로 내부적으로 더 빠르게 진행되거나 하는 것은 아님

### 커스텀 싱크 커넥터
- 소스 커넥터랑 동일한 라이브러리 활용
- 싱크 커넥터:
  - `SinkConnector`를 상속받아서 구현
    - 소스쪽과 대부분 유사
- 싱크 태스크:
  - `SinkTask` 를 상속받아서 구현
    - 마찬가지로 소스와 유사함
    - `flush`: `put`에서 레코드들을 처리하고나서 플러시/커밋 등의 처리 구문을 담당하는 메서드
      - put이 호출될 때 마다 하는 것은 아니고, 커넥트의 오프셋을 커밋 시점마다 호출되어 저장함
    - `put`: 토픽에 올라간 데이터들을 매계변수로 받아서 데이터베이스나 파일시스템 등에 저장하는 역할을 수행하는 메서드
      - 저자의 경험상 가장 중요한 구현부 -> 실질적인 데이터 전송을 다루는 영역이기 떄문으로 보인다.
- 커넥터를 실행시킬 때 지정하는 값으로 패키지 명을 넘기기 때문에, 패키지 구조를 잡을 때 고려해야한다

### 분산모드 카프타 커넥트 실습
- 분산모드로 실행시키는 명령어: `bin/connect-distributed.sh {connect-distributed.properties path}`
- 커넥트를 실행시키는 어플리케이션 쪽에서 커넥트 API를 호출해 실행시킬 수 있음
- `tasks.max`: 태스크에 할당되는 최대 스레드
  - 싱용환경에서는 일반적으로 싱크 커넥터는 컨수머 역할을 하기 때문에 `tasks.max`는 파티션 개수와 동일하게 운용한다.
- 카프카 커넥트에서 제공하는 API들을 활용해 실행, 상태 확인 (모니터링), 종료 등을 시킬 수 있다.
  - 커넥터 실행: POST `/connectors`
  - 커넥터 실행 상태 확인 GET `connectors/{connect-name}/status`
  - 커넥터의 태스크 확인 GET `/connectors/{connect-name}/tasks`
  - 커넥터 특정 태스크 상태 확인 GET `/connectors/{connect-name}/tasks/{task-idx}/status`
  - 커넥터 특정 태스크 재시작 POST `/connectors/{connect-name}/tasks/{task-idx}/restart`
  - 커넥터 수정 PUT `/connectors/{connect-name}/config`
  - 커넥터 중지 PUT `/connectors/{connect-name}/pause`
  - 커넥터 시작 PUT `/connectors/{connect-name}/resume`
  - 커넥터 재시작 `/connectors/{connect-name}/restart`
  - 커넥터 삭제 DELETE `/connectors/{connect-name}`
