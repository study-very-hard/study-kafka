# Sec 8 멱등성 프로듀서, 트랜잭션 프로듀서와 컨슈머

---

### 멱등성 프로듀서
- 멱등성이란?
  - 여러 번 연산이 수행되더라도 동일한 결과를 나타내는 것
- 카프카 프로듀서의 기본 동작 방식: at least once
  - 클러스터로 최소 한번의 전달을 보장하는 방식
  - 중복이 발생할 수 있음 -> 멱등성 보장을 컨수머에서 해결해야할 필요가 있어짐
- 멱등성 프로듀서란?
  - 동일한 데이터를 여러 번 전송해도 브로커에는 한 번만 적재되도록 보장하는 프로듀서
  - 0.11.0 이후 버전부터 설정을 통해 적용가능
  - 네트워크 오류(주로 이쪽 이슈)나 재시도 상황 등 이슈가 발생한 상황에서 같은 레코드가 중복 저장되는 문제를 줄이기 위해 사용
  - `enable.idempotence=true` 옵션으로 설정 가능
    - 기본값은 false
      - 3.0.0 버전 부터는 이 기본값이 true로 변경된다고 함
    - 옵션이 적용되면 exactly once delivery 를 지원함
      - 그러나 진정 한번만 전송하는 방식으로 지원하는게 아니라, 여러번 전송하더라도 전송된 데이터를 확인해 중복 데이터를 적재하지 않는 방식으로 exactly-once를 보장한다.
- 멱등성 프로듀서의 동작:
  - 멱등성 보장을 위해 내부적으로 프로듀서ID(PID, 프로듀서의 고유 아이디)와 시퀀스 번호 ID(SID, 레코드의 전달 번호 아이디)를 함께 전달
    - 브로커는 프로듀서가 보낸 레코드의 시퀀스 번호를 확인해 이미 처리한 시퀀스 번호가 다시 오면 중복으로 판단해 저장하지 않음
    - 멱등성의 추가 비용: 배치에 Producer ID와 Sequence Number를 붙이고 브로커가 최근 순서를 확인하는 로직이 추가됨
- 멱등성 프로듀서의 한계:
  - 동일한 프로듀서 세션 안에서의 중복 전송만 방지
    - 프로듀서가 재시작되면 PID가 달라져서 브로커 입장에서는 새 프로듀서로 인식됨
- 멱등성 프로듀서로 설정했을 시의 옵션:
  - 멱등성 프로듀서로 설정하면 자동으로 설정되는 옵션들이 있음
  - retries 값이 Integer.MAX_VALUE로 설정됨 
  - acks 도 all 로 설정됨  
    - acks=all 이면 모든 팔로워 파티션에 저장한 후에 완료되기에 성능적 이슈가 있음. 
    - 그렇기에 멱등성 프로듀서가 진짜 필요한지 고려해서 적용해야함 
- 멱등성 프로듀서 사용시 오류 확인:
  - 일반적인 상황은 아님
  - 순서가 맞지 않는 시퀀스 번호가 오면 예외가 발생할 수 있음
    - sid 가 0번이 적재되어 있는데 1번이 아니라 2번으로 프로듀스 했다면 발생하는 예외 
      - OutOfOrderSequenceException이 발생함
  - 메시지 중복을 줄이려면 재시도 옵션과 함께 사용하는 것이 중요
- 저자가 생각하는 더 좋은 아키텍처
  - 일반적으로는 컨수머에서 멱등성을 보장하는 방식을 사용해 부하를 덜 수 있다고 함.
    - 그걸 고려해서 성능적 문제가 될 수 있는 멱등성 프로듀서의 사용은 신중해야한다 함
    - 그러나 또 항상 이렇지는 않을 수 있으니 멱등성 프로듀서의 존재도 알아두면 좋고, 상황에 맞춰 선택하라 함


### 트랜잭션 프로듀서, 컨수머
- 카프카에서의 트랜잭션: 다수의 파티션에 데이터를 저장할 경우 모든 데이터에 대해 동일한 원자성(atomic)을 만족시키기 위해 사용됨.
  - 다수의 데이터를 동일 트랜잭션으로 묶음으로서 전체 데이터를 처리하거나 전체 데이터를 처리하지 않도록 하는 것을 의미한다.
#### 트랜잭션 프로듀서
- 여러 레코드 전송을 하나의 트랜잭션 단위로 묶어 원자적으로 처리하는 프로듀서
- 일부 레코드만 성공하고 일부는 실패하는 상황을 방지할 때 사용
- 동작 방식:
  - 보내려는 파티션에 레코드를 적재한 후, 커밋을 수행하면 전체가 성공하거나 전체 실패가 결정됨
    - 트랜잭션의 시작과 끝을 표현하기 위한 트랜잭션 레코드를 하나 더 보낸다고 함
- 설정:
  - 고유한 값을 `transactional.id`로 지정해야함
  - 프로듀서 시작 시 `initTransactions()` 호출
  - 메세지 send() 전에 beginTransaction() 끝난 후에 commitTransaction() 혹은 abortTransaction() 을 호출
```java
producer.initTransactions();

producer.beginTransaction();
producer.send(new ProducerRecord<>(TOPIC, "전달하는 메시지 값"));
producer.send(new ProducerRecord<>(TOPIC2, "전달하는 메시지 값2"));
producer.send(new ProducerRecord<>(TOPIC3, "전달하는 메시지 값3"));
producer.commitTransaction();
```
- 실패 시에는 `abortTransaction()`으로 트랜잭션을 취소할 수 있음

#### 트랜잭션 컨수머
- 트랜잭션 프로듀서가 보낸 데이터를 읽을 때 커밋된 데이터만 읽도록 설정 가능
  - 트랜잭션 컨수머는 파티션에 있는 데이터를 바로 읽는게 아니라, 트랜잭션 프로듀서의 커밋이 완료되면 그 때 컨숨하는 방식
- 설정:
```java
configs.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
```
- `read_uncommitted`: 커밋 여부와 상관없이 읽음
  - 트랜잭션 컨수머가 아닌 기본 컨수머의 기본값
- `read_committed`: 트랜잭션이 커밋된 데이터만 읽음
  - 이걸로 변경하면 트랜잭션 컨수머로 설정됨
