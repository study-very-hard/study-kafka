## 아파치 카프카 개요 및 설명 
- 소스 애플리케이션과 타겟 애플리케이션이 많아지며 데이터를 전송하는 라인이 많아지며 배포와 장애 대응에 문제가 생기기 시작함.
  - 이러한 복잡성을 해결하기 위해 링크드인에서 개발한 오픈소스
- 소스 어플리케이션과 타겟 어플리케이션 간의 결합도를 낮추는 역할을 한다
  - 소스 어플리케이션은 카프카에만 데이터를 전송
  - 타겟 어플리케이션은 카프카에서 수신
- 운영상의 특징:
  - 유연한 고가용성 큐로 동작해 서버의 이상(전원이 내려가거나 하는 등)이 발생했을 때도 데이터의 손실 없이 복구 가능
  - 낮은 지연과 높은 처리량을 바탕으로 효과적으로 많은 데이터를 처리할 수 있음
    - 빅데이터 처리에 유용

## 토픽이란?
- 데이터가 들어갈 수 있는 공간
- 파티션:
  - 토픽을 구성하는 요소로 큐와 같이 데이터를 적재하는 공간
  - 컨수머가 소비할 떄, 선입선출로 소비함
  - 파티션에 있는 데이터는 소비되었다고 삭제 되지 않음
    - 컨수머 그룹이 다르고, 오프셋 설정이 earliest 인 경우에 신규 컨수머가 추가되면 기존 파티션에 있는 예전 데이터를 읽고 재처리가 가능함
      - 같은 내용을 다른 저장 메서드 (RDB, NoSQL, Hadoop, etc) 등에 저장하는 경우 유용하게 사용 가능
  - 파티션이 1개 이상일 경우, 신규 메세지:
    - 키가 있고 기본 파티셔너 사용:
      - 키의 해시값을 연산해 특정 파티션에 할당
    - 키가 없고(null) 기본 파티셔너 사용:
      - Round Robin으로 파티션에 할당됨
  - 토픽 내부에 파티션은 늘릴 수는 있으나, 줄일 수는 없음
    - 이 때문에 파티션의 생성에는 주의해야함 
  - 파티션의 데이터가 삭제:
    - 설정을 통해 시간 / 용량을 기준으로 삭제가 가능함

## 브로커, 복제, ISR(In-Sync-Replication)
- 브로커:
  - 하나의 카프카 서버 단위
  - 보통 3개 이상의 브로커를 활용하는 것을 권장
- 복제 (replication)
  - 파티션의 복제
  - 복제의 수는 브로커의 수보다 클 수 없음
  - 디비의 리더-팔로워와 같이 리더와 팔로워로 구분됨
    - 복제본을 통한 리더의 장애 복구
    - 리더가 프로듀서로 부터 실제로 메세지를 받고, 팔로워에 전달됨

## 파티셔너란?
- 프로듀서의 파티셔너:
  - 프로듀서에서 데이터를 보낼때 반드시 통과하는 게이트웨이.
  - 파티셔너를 통해서 특정 토픽에 있는 특정 파티션에 적재가 됨.
- 디폴트 파티셔너: UniformStickyPartitioner
  - 메세지 키가 있는 경우: 
    - 메세지 키를 기준으로 특정한 해시 값을 만든 후 해당 해시에 속하는 파티션으로 전송
      - 같은 메세지가 같은 파티션에 들어가는 것이 보장됨 -> 컨숨되는 순서또한 보장이 됨
  - 메세지키가 없는 경우:
    - 특수한 라운드 로빈으로 파티션에 들어감
- 프로듀서에서 배치로 모을 수 있는 최대한을 모아서 파티션에 넣음
- 커스텀 파티셔너를 만들기 위해 Partitioner 인터페이스를 제공함
  - 특수하게 VIP 고객을 위한 데이터만 빠르게 처리하고 싶을 떄 커스텀을 진행할 수 있음
  - AMQP에서의 priority queue와 비슷한 느낌

## 컨수머 랙(Consumer Lag)이란?
- 컨수머 랙: 프로듀서가 넣는 속도가 너무 빨라, 프로듀서의 마지막 offset과 컨슈머의 마지막 offset이 차이
  - 운영상의 중요한 지표로 사용이 가능함
- 여러 파티션에 존재하는 경우 랙은 여러개가 될 수 있다
  - records-lag-max: 하나의 컨수머 그룹에서 2개 이상의 파티션에서 데이터를 가져갈 때 발생한 가장 큰 오프셋 격차

## 컨수머 랙 모니터링 애플리케이션 카프카 버로우(Burrow)
- 컨수머 단위에서의 랙 모니터링은 위험하고 운영요소가 많이 들어감
  - 왜? 
    - 컨수머 상태에 디펜던시를 걸리게 됨
    - 컨수머가 다운되면 랙을 모니터링 할 수 없게됨
    - 컨수머가 개발될 때 마다 랙 정보를 저장할 수 있도록 로직의 개발이 필요해짐
  - 이를 해결하기 위해 링크드인에서 고안된게 버로우
- 버로우의 특징:
  - 멀티 카프카 클러스터 지원
    - 하나의 버로우 인스턴스로 모든 클러스터의 랙을 확인 가능
  - 슬라이딩 윈도우를 통한 컨수머의 상태(Status) 확인
    - 데이터 양이 일시적으로 많아 졌을 떄:
      - 컨수머의 오프셋이 증가한다 => WARNING
      - 컨수머가 데이터를 못 가져간다 => ERROR
      - 그 외 => OK
  - HTTP API 지원
    - 확장성 + 범용성 생태계 구축

## Kafka. RabbitMQ, Redis Queue 의 차이점
- 메시징 플랫폼은 2가지로 나눠짐:
  - 메세지 브로커:
    - 이벤트 브로커의 역할을 할 수 없음
    - 메세지를 받아서 처리되면 즉시/짧은 시간안에 삭제됨
    - ex: RabbitMQ, Redis Queue 등
  - 이벤트 브로커:
    - 메세지 브로커의 역할을 할 수 있음
    - 레코드를 하나만 저장하고 인덱스로 개별 엑세스 관리함
    - 필요한 시간 동안 이벤트를 보존할 수 있음
    - ex: Kafka, AWS Kinesis
- 이벤트 브로커가 이벤트를 바로 삭제하지 않는 이유는 뭘까?
  - 딱 한번 발생하는 이벤트를 저장함으로서 단일 진실 공급원 (Single Source of Truth)로 활용 가능
  - 장애가 발생했을떄, 해당 지점부터 재처리 가능
  - 많은 양의 데이터를 효과적으로 처리 가능

## 컨수머 애플리케이션
- 컨수머가 하나 죽더라도 __consumer_offset 에 저장된 컨수머의 오프셋 정보로 마지막 오프셋을 찾아가 데이터 처리 시작 가능
  - topic 별 하위에 그룹별로 저장됨
  - 고가용성 특징
- 컨수머의 개수?
  - 같은 컨수머 그룹:
    - 파티션의 개수보다 이하여야함
    - 파티셔너에서 배운 내용대로, 키를 지정할 경우 해싱 처리를 통해 같은 키의 값이 하나의 파티션에만 쌓이게 됨
      - 토픽에 파티션이 늘어나게 되면 해시가 어떻게 처리되는가?
        - 키와 파티션의 매핑이 깨지게됨. => 키의 순서 보장이 엉망이 될 가능성이 매우 높음
          - 추후에 생성하는 것은 지양해야함 -> 파티션 갯수 선정에는 주의가 필요.
            - 어떻게 알맞은 파티션 수를 선정하는가?
  - 다른 컨수머 그룹:
    - 각 컨수머 그룹은 다른 그룹에 영향을 주지 않음
    - 컨수머 그룹의 수 만큼 늘어날 수 있음

## 스트림즈 애플리케이션
- 카프카 스트림즈란?
  - 컨수머를 사용하는 것 보다 더 안전하고 빠르고 다양한 기능을 사용할 수 있는 기능
- 장점:
  - 카프카와 완벽 호환됨
    - 카프카 버전에 영향받는 일이 없음.
  - 스케쥴링 도구가 필요없다
    - 기존의 스파크 같은 툴은 yarn 등의 리소스 관리자등을 구축해야한는데 이러한 과정이 없음
  - 스트림즈DSL 과 프로세서API 제공
    - 스트림즈DSL: 이벤트 기반 데이터를 처리할 때 사용하는 메서드(map, join 등)들을 재공해서
  - 로컬 상태저장소 사용
    - 상태기반 처리의 구현에 유리함
      - 이전 데이터를 프로세스가 메모리에 저장하면서 다음 데이터를 처리해야하는 문제가 있음
    - 스트림즈는 로컬에 rocksdb를 사용해 상태를 저장후, 수정이 필요하면 변경로그에 기록해 필요시 수정

## 카프카 커넥트
- 반복적인 데이터 파이프라인을 운영해야하는 경우에 활용하는 툴
- 커넥트:
  - 커넥트가 동작하게 하기 위한 패키지
  - 단일 실행 모드 커넥트:
    - 주로 개발 환경에서 사용
  - 분산 실행 모드 커넥트:
    - 실제 환경은 특수한 목적이 있지 않다면 분산 실행 모드로 실행됨
    - 여러 프로세스를 하나의 클러스터로 묶어서 운영하는 방식
- 커넥터: 
  - 파이프라인에 필요한 동작들과 메서드를 포함한 애플리케이션
  - 싱크 커넥터: 데이터의 동기화를 위해 특정 토픽의 데이터를 특정 저장소에 저장을 하는 역할을 함
    - 컨수머와 비슷한 역할을 함
    - 일반적 네이밍 컨벤션: {dbType}SyncConnector
