# 섹션 6. 카프카 프로듀서 애플리케이션 개발

> 📅 학습일: 2026-08-02

## 1. 프로듀서 소개

- 카프카에서 데이터의 시작점은 프로듀서. 프로듀서 애플리케이션은 카프카에 필요한 데이터를 선언하고 브로커의 특정 토픽 파티션에 전송
- 프로듀서는 데이터를 전송할 때 **리더 파티션을 가지고 있는 카프카 브로커와 직접 통신**
- 브로커로 데이터를 전송할 때 내부적으로 **파티셔너 → 배치 생성** 단계를 거침

---

## 2. 프로듀서 내부 구조

- **ProducerRecord**: 프로듀서에서 생성하는 레코드(토픽, 파티션, 타임스탬프, 메시지 키, 메시지 값으로 구성). 오프셋은 미포함
- **send()**: 레코드를 전송 요청하는 메서드
- **Partitioner**: 어느 파티션으로 전송할지 지정하는 파티셔너. 기본값은 `DefaultPartitioner`
- **Accumulator**: 배치로 묶어 전송할 데이터를 모으는 버퍼
- **Sender**: 어큐뮬레이터에 쌓인 배치 데이터를 가져가 카프카 브로커로 전송하는 스레드

전체 흐름: `ProducerRecord → send() → Partitioner → Accumulator(배치) → Sender → 카프카 클러스터`

---

## 3. 프로듀서 파티셔너

### 기본 파티셔너

- 프로듀서 API는 `UniformStickyPartitioner`, `RoundRobinPartitioner` 2개의 파티셔너를 기본 제공
- 카프카 클라이언트 라이브러리 2.5.0부터 파티셔너를 지정하지 않으면 `UniformStickyPartitioner`가 기본값
- **메시지 키가 있을 때**: 두 파티셔너 모두 키의 해시값과 파티션을 매칭하여 전송 → 동일한 메시지 키는 항상 동일한 파티션으로 전달됨. 단, 파티션 개수가 변경되면 매칭이 깨짐
- **메시지 키가 없을 때**
  - `RoundRobinPartitioner`: ProducerRecord가 들어오는 대로 파티션을 순회하며 전송 → 어큐뮬레이터에서 묶이는 정도가 적어 전송 성능이 낮음
  - `UniformStickyPartitioner`: 어큐뮬레이터에서 레코드가 배치로 묶일 때까지 기다렸다가 전송. 결국은 파티션을 순회하므로 모든 파티션에 분배되며, RoundRobinPartitioner보다 향상된 성능을 가짐

### 커스텀 파티셔너

- `Partitioner` 인터페이스를 상속받아 사용자 정의 클래스에서 메시지 키/값에 따른 파티션 지정 로직을 직접 구현 가능
- 파티셔너를 통해 파티션이 지정된 데이터는 어큐뮬레이터에 버퍼로 쌓이고, 센더 스레드가 이를 가져가 브로커로 전송

---

## 4. 프로듀서 주요 옵션

### 필수 옵션

- `bootstrap.servers`: 전송 대상 카프카 클러스터에 속한 브로커의 host:port를 1개 이상 작성. 2개 이상 입력하면 일부 브로커에 이슈가 발생해도 접속 문제 없이 설정 가능
- `key.serializer` / `value.serializer`: 레코드의 메시지 키 / 메시지 값을 직렬화하는 클래스를 지정

### 선택 옵션

- `acks`: 브로커에 정상적으로 저장되었는지 전송 성공 여부를 확인하는 옵션. `0`, `1`, `-1(all)` 중 설정. 기본값 `1`
- `linger.ms`: 배치를 전송하기 전까지 기다리는 최소 시간. 기본값 `0`
- `retries`: 브로커로부터 에러를 받은 뒤 재전송을 시도하는 횟수. 기본값 `2147483647`
- `max.in.flight.requests.per.connection`: 한 번에 요청하는 최대 커넥션 개수. 설정된 값만큼 동시에 전달 요청을 수행. 기본값 `5`
- `partitioner.class`: 레코드를 파티션에 전송할 때 적용하는 파티셔너 클래스. 기본값 `DefaultPartitioner`
- `enable.idempotence`: 멱등성 프로듀서로 동작할지 여부. 기본값 `false`
- `transactional.id`: 레코드를 전송할 때 트랜잭션 단위로 묶을지 여부. 기본값 `null`

## 5. ISR(In-Sync-Replicas)와 acks 옵션

### ISR(In-Sync-Replicas)

- 리더 파티션과 팔로워 파티션이 모두 싱크된 상태를 뜻함. 복제 개수가 2인 토픽 기준으로 리더 파티션에 0~3 오프셋이 있다면, 팔로워 파티션도 0~3까지 오프셋이 존재해야 동기화 완료로 간주
- 프로듀서는 특정 파티션에 데이터를 저장할 때 **리더 파티션을 통해서만 처리**하며, 리더 파티션에 새 레코드가 추가되면 팔로워가 위치한 브로커가 그 데이터를 복제함 → 복제에 걸리는 시간차 때문에 리더와 팔로워 간 오프셋 차이(=ISR 개념)가 발생

### acks

프로듀서가 전송한 데이터가 카프카 클러스터에 얼마나 신뢰성 높게 저장되었는지를 확인하는 옵션. 값에 따라 안정성과 속도가 달라짐 (복제 개수가 1인 경우에는 acks 값에 따른 성능 차이가 크지 않음)

| 값 | 동작 | 특징 |
| --- | --- | --- |
| `acks=0` | 리더 파티션에 저장되었는지 확인하지 않음 | 전송 속도가 가장 빠름. 데이터 유실 가능 |
| `acks=1` | 리더 파티션에만 정상 적재되었는지 확인 | 리더 적재 후 팔로워 복제 전에 리더 브로커 장애가 발생하면 유실 가능 |
| `acks=-1(all)` | 리더 + 팔로워(ISR)까지 모두 정상 적재되었는지 확인 | 가장 느리지만 일부 브로커 장애에도 안전. 안정성은 `min.insync.replicas` 값에 따라 달라짐 |

### min.insync.replicas

- `acks=all`로 설정할 때 유효한 옵션. 프로듀서가 데이터 적재를 확인하기 위한 **최소 ISR 그룹의 파티션 개수**
- `min.insync.replicas=1`이면 ISR 중 최소 1개(=가장 먼저 적재가 완료되는 리더 파티션)만 확인 → `acks=1`과 동일하게 동작
- `min.insync.replicas=2`(복제 개수 2 이상 권장)이면 리더 + 팔로워 1개 이상의 적재를 확인 → 브로커 1대에 장애가 발생해도 데이터가 유실되지 않는다고 볼 수 있음

## 6. 프로듀서 애플리케이션 개발하기

프로듀서 API를 사용하려면 카프카 공식 자바 클라이언트 라이브러리(`kafka-clients`)를 프로젝트 의존성으로 추가해야 함.

### 기본 프로듀서

```java
Properties configs = new Properties();
configs.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);
configs.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
configs.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());

KafkaProducer<String, String> producer = new KafkaProducer<>(configs);
ProducerRecord<String, String> record = new ProducerRecord<>(TOPIC_NAME, messageValue);
producer.send(record);
producer.flush();
producer.close();
```

### 메시지 키를 가진 프로듀서

- `ProducerRecord` 생성 시 (토픽 이름, 메시지 키, 메시지 값) 순서로 파라미터를 넣으면 메시지 키가 지정됨

```java
new ProducerRecord<>(TOPIC_NAME, "Pangyo", "Pangyo");
```

### 파티션 번호를 지정한 프로듀서

- (토픽 이름, 파티션 번호, 메시지 키, 메시지 값) 순서로 파라미터를 넣으면 파티션을 직접 지정 가능. 파티션 번호는 토픽에 존재하는 번호로 설정해야 함

```java
new ProducerRecord<>(TOPIC_NAME, partitionNo, "Pankyo", "Pankyo");
```

### 커스텀 파티셔너를 가지는 프로듀서

- `ProducerConfig.PARTITIONER_CLASS_CONFIG`에 커스텀 파티셔너 클래스를 지정하면 해당 로직으로 파티션이 결정됨

```java
configs.put(ProducerConfig.PARTITIONER_CLASS_CONFIG, CustomPartitioner.class);
```

### 레코드의 전송 결과를 확인하는 프로듀서

- `send()`는 `Future<RecordMetadata>`를 반환함. `get()`을 호출하면 프로듀서로 보낸 데이터의 전송 결과(적재된 파티션·오프셋 등)를 **동기적으로** 확인 가능

```java
RecordMetadata metadata = producer.send(record).get();
```

### 프로듀서의 안전한 종료

- `close()`를 호출하면 어큐뮬레이터에 저장되어 있는 모든 데이터를 카프카 클러스터로 전송한 뒤 종료됨

```java
producer.close();
```

## 정리

- 프로듀서는 데이터를 카프카 클러스터로 보낸다
- 프로듀서는 파티셔너, 어큐뮬레이터, 센더를 지나 카프카 클러스터로 데이터가 보내진다
- 프로듀서의 기본 파티셔너는 UniformStickyPartitioner와 RoundRobinPartitioner가 있다
- 메시지 키가 있을 경우에는 UniformStickyPartitioner와 RoundRobinPartitioner의 동작은 동일하다
- UniformStickyPartitioner은 RoundRobinPartitioner을 개선한 파티셔너이다
- ISR은 리더 파티션과 팔로워 파티션의 레코드가 모두 동일한 개수로 동기화가 완료된 묶음을 뜻한다
- acks는 0, 1, all(-1)로 설정할 수 있으며, 데이터 저장 신뢰도를 정할때 사용된다
- min.insync.replicas는 acks가 all(-1)일 때 유효한 설정이다
