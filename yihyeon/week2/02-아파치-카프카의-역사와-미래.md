# 섹션 2. 아파치 카프카의 역사와 미래

## 카프카의 탄생

### 배경: 링크드인의 파편화된 데이터 파이프라인

- 2011년 링크드인(LinkedIn)은 파편화된 데이터 수집·분배 아키텍처 운영에 큰 어려움을 겪음
- 초기에는 소스 애플리케이션 → 타깃 애플리케이션을 **단방향 1:1로 직접 연결**했고, 아키텍처가 단순해 운영 부담이 적었음
- 서비스가 커지면서 소스/타깃 애플리케이션 개수가 늘어나자 **전송 라인이 기하급수적으로 복잡해짐**

### 기존 해결 시도의 실패

- 상용 데이터 프레임워크, 오픈소스, 각종 메시징 플랫폼, ETL(Extract Transform Load) 툴을 도입해 개선을 시도
- 그러나 파편화된 파이프라인의 **복잡도 자체를 낮추지는 못함**

### 카프카의 등장

- 결국 링크드인 데이터팀이 신규 시스템을 직접 개발 → **아파치 카프카(Apache Kafka)**
- 핵심 아이디어: 애플리케이션끼리 직접 연결하지 않고, **한 곳(Unified Log)에 모아 중앙집중화하여 처리**

---

## 메시지 큐 구조를 그대로 살린 카프카 내부 구조

### 커플링 해소

- 기존 1:1 매칭 파이프라인은 커플링 때문에 한쪽 이슈가 다른 쪽 애플리케이션에 영향을 줌
- 카프카는 이 의존도를 끊음 → 소스 애플리케이션은 **어느 타깃으로 보낼지 고민하지 않고 일단 카프카로 전송**

### 큐 자료구조와의 유사성

- 카프카 내부에서 데이터가 저장되는 **파티션의 동작은 FIFO(First In First Out) 큐와 유사**
- 큐에 데이터를 넣는 쪽 = **프로듀서(Producer)**
- 큐에서 데이터를 가져가는 쪽 = **컨슈머(Consumer)**
- 구조: 토픽(Topic) 안에 여러 파티션(Partition 0, 1, 2…)이 존재하고, 각 파티션은 순서대로 레코드를 적재

## 빅데이터 플랫폼으로서 카프카의 4가지 특징

### 1) 높은 처리량

- 프로듀서가 브로커로 데이터를 보낼 때, 컨슈머가 데이터를 받을 때 **묶음 단위(배치)로 전송**
- 많은 양의 데이터를 보낼 때 네트워크 통신 횟수를 최소화 → 처리량 극대화
- **파티션 단위 병렬 처리**로 동일 시간당 처리량을 더 늘릴 수 있음
- 파티션 개수만큼 컨슈머를 늘려 병렬 처리 가능

### 2) 확장성

- 데이터가 얼마나 들어올지 예측하기 어려운 환경에 대응
- **가변적인 환경에서 안정적으로 확장(scale-out) / 축소(scale-in) 가능**
- 브로커 개수를 늘려 클러스터 규모를 확장, 트래픽이 줄면 다시 축소
- 클러스터의 브로커 추가/제거는 **무중단으로 운영 가능**

### 3) 영속성

- 다른 메시징 플랫폼과 달리 전송받은 데이터를 **메모리가 아닌 파일 시스템(디스크)에 저장**
- 디스크 I/O의 느린 속도 문제는 **페이지 캐시(page cache)** 를 활용해 보완
  - 운영체제가 메모리 일부 영역을 페이지 캐시로 사용해 디스크 접근을 줄임
- 프로세스가 비정상 종료되더라도 **파일 시스템에 남아 있는 데이터로 복구 가능**

### 4) 고가용성

- 3대 이상의 브로커로 구성된 클러스터를 통해 **일부 브로커에 장애가 발생해도 무중단 운영**
- **복제(replication)** 를 통해 데이터를 안전하게 보관
- 클러스터 브로커 개수에 따라 복제 개수를 지정 가능
- 서로 다른 브로커에 복제본이 분산 저장되어 있어, 특정 브로커 장애 시에도 데이터 유실 없이 처리 지속
- 클라우드 환경에서는 서로 다른 **가용 영역(availability zone)** 에 브로커를 배치해 안정성을 높이기도 함

## 데이터 레이크 아키텍처와 카프카의 미래

### 초기 빅데이터 플랫폼

- 각 서비스 애플리케이션으로부터 **엔드 투 엔드로 데이터를 배치(batch) 수집**
- 원천 데이터 → 파생 데이터 → 서빙 데이터로 이어지는 파이프라인
- 단점
  - 구조가 유연하지 못함
  - 실시간 데이터에 대한 인사이트를 서비스 애플리케이션에 빠르게 전달하지 못함
  - 원천 데이터로부터 파생된 데이터의 **히스토리 추적이 어려움**
  - 계속되는 가공으로 데이터가 파편화 → **데이터 거버넌스(data governance: 데이터 표준 및 정책)** 유지가 어려움

### 람다 아키텍처

3개의 레이어로 구성

| 레이어 | 역할 |
| --- | --- |
| 배치 레이어 | 배치 데이터를 모아 특정 시간/타이밍마다 일괄 처리 |
| 서빙 레이어 | 가공된 데이터를 데이터 사용자·서비스 애플리케이션이 사용할 수 있도록 저장한 공간 |
| 스피드 레이어 | 서비스에서 생성되는 원천 데이터를 실시간으로 분석하는 용도. 낮은 지연이 필요할 때 사용 |

### 람다 아키텍처의 한계

- 배치 처리와 실시간 처리를 분리해 **처리 방식은 명확히 나눌 수 있었지만**, 레이어가 2개로 나뉘어 생기는 단점 존재
  - 데이터 분석·처리 **로직이 2벌**로 각 레이어에 따로 존재해야 함
  - 배치 데이터와 실시간 데이터를 융합해 처리할 때 **유연하지 못한 파이프라인**이 만들어짐
- 1개의 로직을 추상화해 두 레이어에 적용하는 **서밍버드(Summingbird)** 같은 시도가 있었지만 완벽한 해결은 아니었음

### 카파 아키텍처

- **제이 크렙스(Jay Kreps)** 가 제안 (카프카 최초 고안자)
- 람다의 단점(로직 파편화, 디버깅, 배포, 운영 분리 이슈)을 없애기 위해 **배치 레이어를 제거**
- 스피드 레이어에서 데이터를 모두 처리 → 엔지니어가 더 효율적으로 개발·운영 가능

### 카파 아키텍처의 활용: 로그로 배치 표현하기

- 로그는 배치 데이터를 스트림으로 표현하기에 적합
- 기존 방식: 배치 데이터 = 각 시점(시간별·일자별 등)의 **전체 데이터를 백업한 스냅샷**
- 카파 방식: 각 시점의 **변환 기록(change log)** 을 시간 순서대로 기록
  - → 모든 시점의 스냅샷을 저장하지 않고도 배치 데이터를 표현 가능

### 스트리밍 데이터 레이크

- 2020년 카프카 서밋에서 제이 크렙스가 제안: 카파 아키텍처에서 **서빙 레이어까지 제거**한 아키텍처
- 근거: 스피드 레이어(카프카)에 분석·프로세싱이 완료된 대용량 데이터를 **장기간 저장·사용할 수 있다면** 서빙 레이어는 불필요
- 효과: 서빙 레이어와 스피드 레이어가 **이중으로 관리되는 운영 리소스를 절감**

### 스트리밍 데이터 레이크의 과제

- 자주 접근하지 않는 데이터를 굳이 비싼 자원(브로커의 메모리·디스크)에 유지할 필요가 없음
- 개선 방향: **자주 접근하지 않는 데이터는 오브젝트 스토리지처럼 저렴하고 안전한 저장소로 이관**, 자주 쓰는 데이터만 브로커에서 사용하는 구분 작업 필요

## 배치와 스트림의 상호 변환

### 배치 데이터를 처리하는 방법 (in 하둡)

- HDFS에 저장된 파일들을 데이터 노드로 모아 처리하고, 결과를 다시 HDFS에 파일로 저장

### 스트림 데이터를 배치로 사용하는 방법 (in 카프카)

- 핵심: **로그에 시간(timestamp)을 남기는 것**
- 로그에 남겨진 시간을 기준으로 처리하면, 스트림으로 적재된 데이터도 배치로 처리 가능
- 예) 2021년 신입생 목록을 배치로 뽑고 싶다면 → 스트림으로 적재된 1월 1일 ~ 12월 31일 데이터를 **구체화된 뷰(Materialized View)** 로 가져오면 배치 처리와 동일한 결과
- 카프카는 레코드에 timestamp를 남기므로 이런 방식이 가능 (Kafka Streams Application)

### 배치 데이터 vs 스트림 데이터

| 구분 | 배치(bounded) 데이터 | 스트림(unbounded) 데이터 |
| --- | --- | --- |
| 처리 범위 | 한정된(bounded) 데이터 처리 | 한정되지 않은(unbounded) 데이터 처리 |
| 처리 시점 | 정해진 시점에 일괄 처리 | 지속적으로 발생하는 데이터를 계속 처리 |
| 리소스 | 처리하는 시점에만 리소스 점유 | 항상 리소스 점유 |

## 섹션 요약

- 최초의 카프카는 **링크드인에서 기존 아키텍처를 개선하기 위해** 만든 시스템
- 카프카는 소스/타깃 애플리케이션 간의 **커플링을 완화**하기 위해 중앙집중화 구조를 취함
- 카프카의 파티션 내부 구조는 **큐와 유사한 FIFO 구조**
- 카프카의 특징: **높은 처리량, 확장성, 영속성, 고가용성**
- 람다 아키텍처에서 카프카는 **스피드 레이어**에 해당
- 람다 아키텍처는 레이어가 2개로 나뉘어 **로직이 2벌**이 된다는 단점이 있음
- **카파 아키텍처**는 람다 아키텍처의 단점을 개선한 아키텍처
- **스트리밍 데이터 레이크**는 서빙 레이어를 제거하고 카프카를 영구 저장소로 사용하는 것
