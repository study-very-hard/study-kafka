# Apache Kafka 의 탄생 배경과 철학

## 1. 등장 배경: 스파게티 아키텍처의 한계

![before kafka](/yihyeon/images/before-kafka.png)

카프카가 없던 시절, 링크드인의 데이터 시스템은 그야말로 '스파게티'처럼 꼬여 있었다.

- **엔드포인트의 폭발적 증가**
    - 서비스가 커지면서 소스 시스템(웹 앱, 로그 데이터, 모바일 앱 등)과 타깃 시스템(데이터베이스, 검색 엔진, 분석 툴 등)이 수없이 많아졌다.
- N x M 문제
    - 각 시스템을 1:1로 직접 연결(Point-to-Point)하다 보니 데이터 파이프라인이 수십, 수백 개로 늘어났다.
- 유지보수 지옥
    - 소스 시스템의 데이터 포맷이 하나만 바뀌어도, 연결된 모든 타깃 시스템의 연동 코드를 수정해야 했다. 연결이 복잡해질수록 장애 추적도 불가능에 가까웠다.

**“이 모든 시스템의 한가운데를 관통하는 단 하나의 거대한 데이터 통로를 만들 순 없을까?”**

이 고민이 카프카의 시작이었다.

## 2. 카프카의 핵심 디자인 철학

![kafka features](/yihyeon/images/kafka-features.png)

제이 크렙스는 카프카를 설계할 때 아주 단순하고 강력한 개념인 "추가만 가능한 로그(Append-only Log)"에 주목했다. 카프카를 지탱하는 3가지 철학은 다음과 같다.

### 1. 발행/구독(Pub/Sub) 모델의 분리: "보내는 사람과 받는 사람은 서로를 몰라야 한다"

카프카는 소스(Producer)와 타깃(Consumer)의 의존성을 완전히 끊어버렸다.

- **Producer**는 그저 카프카라는 데이터 중앙선(Topic)에 데이터를 던지기만 한다. (누가 가져갈지 신경 쓰지 않음)
- **Consumer**는 카프카에서 원하는 데이터만 골라서 빨아들인다. (누가 보냈는지 신경 쓰지 않음)
- 덕분에 새로운 타깃 시스템(예: 새로운 분석 툴)이 추가되어도 기존 시스템에는 아무런 영향이 없다.

### 2. 실시간 전송과 대용량 저장의 결합: "메시징 시스템 + 파일 시스템"

기존의 메시지 큐(RabbitMQ 등)는 소비자가 데이터를 읽어가면 메모리에서 데이터를 바로 지워버렸다.반면 카프카는 데이터를 **디스크에 영구적으로 저장한다.**

- **영속성(Durability):** 디스크에 순차적으로(Sequential) 저장하기 때문에 메모리 못지않게 속도가 빠르며, 서버가 터져도 데이터가 날아가지 않는다.
- **리플레이(Replay) 가능:** 이미 읽어간 데이터도 지워지지 않고 남아있기 때문에, 과거 데이터를 처음부터 다시 돌려보며 분석하거나 장애를 복구할 수 있다.

### 3.  압도적인 확장성(Scalability)과 고가용성

카프카는 처음부터 '초당 수천억 개의 이벤트'를 처리할 목적으로 설계되었다.

- **파티션(Partition) 분할:** 하나의 데이터를 여러 파티션으로 쪼개서 여러 서버에 분산 처리한다. 병렬 처리가 극대화된다.
- **클러스터링:** 서버 몇 대가 죽어도 다른 서버가 역할을 이어받아(Replication) 데이터 유실 없이 24시간 멈추지 않고 돌아간다.

# 토픽이란?

![kafka topic](/yihyeon/images/kafka-topic.png)

카프카의 철학이 "데이터를 던지는 놈과 받는 놈의 의존성을 끊는 것"이라고 앞에서 설명하였다. 그 끊어진 연결고리 한가운데서 **데이터가 쌓이는 '방' 혹은 '채널' 역할을 하는 게 바로 토픽**이다.

## 1. 토픽의 핵심 구조와 특징

토픽은 겉보기엔 단순한 데이터 보관소 같지만, 대용량 처리를 위해 내부는 아주 독특하게 설계되어 있다.

### 1. 이름 기반의 논리적 분리

- 카프카 클러스터 안에는 수많은 토픽을 만들 수 있다.
- 용도에 맞게 명확한 이름을 붙여서 관리한다. (예: `order-events`, `click-logs`, `payment-status`)
- Producer 는 이름만 보고 데이터를 던지고, Consumer 는 이름만 보고 데이터를 가져간다.

### 2. 파티션(Partition)으로 쪼개진 세계

- **이 부분이 카프카 토픽의 가장 거대한 특징이다.** 하나의 토픽은 내부적으로 여러 개의 파티션(Partition)으로 쪼개져 있다.
- 예를 들어 `order-events`라는 토픽을 만들 때 "파티션 3개로 만들어줘"라고 지정하면, 내부적으로 0번, 1번, 2번 파티션이 생성된다.
- 데이터는 토픽이라는 거대한 바구니에 통째로 담기는 게 아니라, **각 파티션에 분산되어 순서대로 차곡차곡 쌓인다.**

### 3. 추가만 가능한 로그 (Append-only Log)

- 데이터가 파티션에 들어오면, 무조건 맨 뒤에 붙는다. (큐나 스택처럼 중간에 끼어들거나 수정할 수 없다.)
- 이때 데이터가 쌓일 때마다 **0, 1, 2, 3... 고유한 번호**가 붙는데, 이게 바로 **오프셋(Offset)**이다.
- 데이터는 절대 수정(Update)하거나 임의로 삭제(Delete)할 수 없다. 보관 주기가 지나서 카프카가 오래된 것부터 지우기 전까지는 굳건히 유지된다.

## 2. 토픽을 이해할 때 가장 중요한 주의점: "순서(Ordering)”

**토픽의 대원칙:** 카프카는 **'파티션 내부'에서만 순서를 보장**한다. 토픽 전체의 순서는 보장하지 않는다.

### 만약 꼭 순서대로 처리해야 하는 데이터라면?

소스를 보낼 때 "메시지 키(**Message Key**)"를 지정해야 한다. 예를 들어 UserId 나 OrderId 를 키로 지정하면, 카프카는 그 키를 해싱하여 **항상 동일한 파티션(예: 무조건 0번 파티션)으로만 데이터를 보낸다.** 동일한 사용자의 이벤트는 늘 같은 파티션에 순서대로 쌓이므로, 순서 뒤바뀜 문제를 해결할 수 있다.

# 브로커, 복제, ISR(In-Sync-Replica)

![kafka broker](/yihyeon/images/kafka-broker.png)

## 1. 브로커란?

카프카 소프트웨어가 실행되고 있는 **하나의 독립된 인스턴스(서버 프로세스)** 를 말한다. 이 브로커들이 여러 대 모여서 힘을 합친 것을 **카프카 클러스터**라고 부른다.

프로듀서가 데이터를 보낼 때(Write)는 **무조건 대장 파티션인 'Leader'가 있는 브로커 1대**로만 신호를 쏜다. 나머지 브로커 2대는 'Follower'로서 대장 브로커의 데이터를 부지런히 복제(Sync)해 간다.

![kafka replication](/yihyeon/images/kafka-replication.png)

### 리더(Leader)와 팔로워(Follower)의 역할 분담

만약 `order-events`라는 토픽의 **0번 파티션**이 있고, `Replication Factor = 3` (복제본 3개)으로 설정했다면, 브로커 3대에 다음과 같이 찢어져서 배치된다.

- **브로커 1:** 0번 파티션의 **Leader**
- **브로커 2:** 0번 파티션의 **Follower 1**
- **브로커 3:** 0번 파티션의 **Follower 2**

## 2. ISR (In-Sync Replicas)

여기서 카프카의 아주 독특하고 영리한 개념인 ISR(In-Sync Replicas)이 등장한다.

대장(Leader) 입장에서는 팔로워들이 데이터를 잘 복사해 가고 있는지 감시해야 한다. 그런데 만약 **브로커 3**이 네트워크 상태가 나쁘거나 장비에 문제가 있어서 데이터 복제를 못 하고 한참 뒤처져(Lag) 있다고 해보자.

- **Leader의 조치:** *"너 왜 이렇게 느려? 너 나중에 나 죽으면 대장 자리 물려받을 자격 없어! 탈락!"*
- 리더는 복제를 잘 따라오고 있는 정상적인 팔로워(예: 브로커 2)와 자신만을 묶어서 **ISR**이라는 특별한 그룹(합격자 명단)을 유지한다.
    - **ISR 상태:** `[Leader(브로커1), Follower(브로커2)]`
    - **탈락자:** `Follower(브로커3)`

### ISR이 왜 중요할까? (장애 복구의 기준)

만약 데이터를 들고 있던 **브로커 1(Leader)이 갑자기 불타서 터졌다.** 이제 누군가 대장 자리를 이어받아야 시스템이 멈추지 않는다.

이때 대장 브로커를 관리하는 컨트롤러는 **무조건 ISR 명단에 들어있는 팔로워(브로커 2)만 대장으로 승격**시킨다. 데이터 복제가 너무 뒤처져서 탈락했던 브로커 3은 절대 대장이 될 수 없다. 만약 브로커 3이 대장이 되면 데이터가 유실되거나 정합성이 깨질 것이기 때문이다.

## 3. acks 설정과의 관계

이 ISR 개념은 데이터를 보내는 프로듀서의 안전장치인 **`acks` 설정**과 직결된다. 프로듀서가 데이터를 보낼 때 브로커에게 어떤 확답을 받을지 선택할 수 있다.

- `acks = 0`: 리더가 받았는지 안 받았는지 확인도 안 하고 다음 데이터를 쏜다. (가장 빠름, 유실 위험 높음)
- `acks = 1`: **리더 브로커 1대**가 디스크에 잘 저장했다고 응답하면 성공으로 친다. (적당히 빠르고 안전함)
- `acks = all` (또는 `-1`): ISR 명단에 있는 모든 브로커(Leader + 정상 Follower들)가 전부 복제를 완료했다고 확인 도장을 찍어줘야 프로듀서에게 "성공!"이라고 응답한다. (가장 안전함, 속도는 살짝 느림)

# 파티셔너(Partitioner)란?

"데이터를 보낼 때 메시지 키를 지정하면 같은 파티션으로 들어가고, 키가 없으면 라운드로빈으로 찢어진다"라고 이야기 할 때, 그 '찢어주는 작업'을 실시간으로 계산해서 실행하는 **프로듀서 내부의 컴포넌트**가 바로 파티셔너이다.

즉, 메시지를 **어느 파티션(0번, 1번, 2번...)으로 보낼지 목적지를 지정해 주는 내비게이션 역할**을 한다.

## 파티셔너의 전략

### 메시지 키(Key)가 있을 때: 해시(Hash) 전략

- **작동 방식:** 파티셔너가 메시지 키를 받으면, 이를 고유한 숫자로 바꾸는 **해싱(Hashing) 함수**를 돌린다. 그리고 그 결과값을 `현재 파티션 총 개수`로 나머지 연산(`%`)을 한다.
- **결과:** 키가 동일하면 해시 결과값도 항상 똑같기 때문에, **동일한 키를 가진 메시지는 똑같은 파티션 번호**로 들어가게 된다. (순서보장)

### 메시지 키(Key)가 없을 때(과거): 라운드로빈(Round-Robin) 전략

- **작동 방식:** 카프카 초창기 버전에서는 키가 없으면 파티셔너가 순서대로 메시지를 쪼갰다. (1번 메시지는 0번 파티션, 2번 메시지는 1번 파티션, 3번 메시지는 2번 파티션...)
- **문제점:** 데이터를 너무 잘게 찢어서 보내다 보니, 브로커로 출발하는 트럭(배치, Batch)에 데이터가 1개씩만 차서 출발하는 비효율이 생겼다.

### 메시지 키(Key)가 없을 때 (현재 표준): 스티키(Sticky) 전략

- **작동 방식:** 카프카 2.4 버전부터 도입된 최신 기본 전략이다. 파티셔너가 라운드로빈처럼 매번 파티션을 바꾸지 않고, **"하나의 파티션 트럭(Batch)이 꽉 찰 때까지 한 파티션에만 데이터를 몰아주는"** 방식이다.
- **결과:** 0번 파티션 트럭이 다 차서 브로커로 출발하면, 그다음엔 1번 파티션 트럭을 채우기 시작한다. 키가 없을 때 **네트워크 처리량(Throughput)을 극대화**하기 위한 전략이다.

# 컨슈머 랙(Consumer Lag) 이란?

카프카 브로커는 데이터를 로그 파일로 쌓아두고 인덱스(오프셋)로 관리한다. 컨슈머 랙은 한 마디로 "프로듀서가 보낸 속도에 비해, 컨슈머가 얼마나 뒤처져 있는가?"를 나타내는 지표이다.

카프카 파티션에는 두 가지 중요한 오프셋(Offset, 데이터 번호) 숫자가 실시간으로 올라간다.

1. **로그 엔드 오프셋 (Log End Offset, LEO):** 프로듀서가 데이터를 넣어서 현재 파티션에 쌓인 **가장 최신 데이터의 번호**
2. **현재 오프셋 (Current Offset):** 컨슈머가 어디까지 읽고 처리를 완료(Commit)했는지 나타내는 **현재 읽은 데이터의 번호**

이 두 숫자의 차이(Gap)가 바로 **Lag**이다. Lag이 쌓인다는 것은 **현재 시스템의 처리 속도가 트래픽을 못 따라가고 있다**는 뜻이다.

# 컨슈머 랙 모니터링 애플리케이션, 카프카 버로우(Burrow)

버로우(Burrow)는 링크드인(LinkedIn)에서 개발해서 오픈소스로 공개한 "카프카 컨슈머 랙(Lag) 전용 모니터링 시스템"이다.

## 버로우(Burrow)의 방식: "슬라이딩 윈도우”

버로우는 단순히 "지금 랙이 몇 개야?"라는 단편적인 숫자만 보지 않는다.
컨슈머의 오프셋이 움직이는 '추세(Trend)'를 일정 시간 동안 모니터링(Sliding Window)하여, 컨슈머 그룹의 상태를 문장(Status)으로 진단해 준다.

- **정상 (OK):** 프로듀서가 데이터를 많이 넣어서 랙이 잠시 10,000개로 튀었지만, 컨슈머의 현재 오프셋도 그만큼 빠른 속도로 쫓아가며 숫자를 줄이고 있다면 → **알림 안 보냄 (정상 처리 중)**
- **경고 (WARNING):** 컨슈머가 열심히 일하고는 있는데, 프로듀서가 데이터를 밀어 넣는 속도가 훨씬 더 빨라져서 랙이 계속 벌어지고 있다면 → **"얘 가속도 밀린다! 컨슈머 더 투입해라!" 알림 보냄**
- **에러 (CRITICAL):** 랙은 겨우 5개밖에 안 되는데, 5분 동안 컨슈머의 현재 오프셋 번호가 '단 1개'도 안 움직이고 멈춰있다면 → **"컨슈머 서버 뻗었거나 무한 루프 돌고 있다! 당장 확인해라!" 알림 보냄**

# 카프카, 레빗엠큐, 레디스 큐의 차이점

**"메시지 브로커(Message Broker)"냐, "이벤트 브로커(Event Broker)"냐**

## 메시지 브로커 vs 이벤트 브로커 (핵심 개념 차이)

가장 직관적인 차이는 아래와 같다.

- "소비된 데이터를 보관하는가, **지우는가**"
- "목적이 통신인가, **기록인가**"

### 메시지 브로커 (Message Broker): "전달하고 지운다"

- **철학:** 데이터를 목적지(컨슈머)에 **안전하게 배달하는 것**이 최우선이다.
- **특징:** 컨슈머가 메시지를 가져가서 처리가 완료(Ack)되면, 그 메시지는 **브로커의 큐(Queue)에서 즉시 삭제**된다.
- **장점:** 데이터가 계속 지워지므로 메모리나 디스크 관리가 가볍다. 전통적인 통신, 작업 큐(Job Queue)에 적합하다.
- **대표 주자:** **RabbitMQ, Redis Queue**

### 이벤트 브로커 (Event Broker): "일단 쌓아두고 로그로 남긴다"

- **철학:** 시스템에서 일어난 모든 사건(이벤트)을 **수정 불가능한 로그(Log) 파일로 차곡차곡 기록하는 것**이 최우선이다.
- **특징:** 컨슈머가 데이터를 읽어가도 **데이터는 절대 지워지지 않고 토픽(파티션)에 남아있다.** 컨슈머는 단지 오프셋(포인터)만 옮길 뿐이다.
- **장점:** 이미 처리한 데이터를 과거 시점으로 돌려서 다시 처음부터 읽는 것(Replay)이 가능하다. 대용량 데이터 분석, 이벤트 소싱, MSA 데이터 동기화에 압도적이다.
- **대표 주자:** **Apache Kafka**
