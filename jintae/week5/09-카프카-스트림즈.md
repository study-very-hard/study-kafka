# [Kafka] 섹션 9 - 카프카 스트림즈

지금까지는 데이터를 넣고(프로듀서) 꺼내는(컨슈머) 이야기였음.

이번 섹션은 그 사이에서 데이터를 실시간으로 가공하는 카프카 스트림즈를 다룸.

토픽의 데이터를 읽어 변환한 뒤 다시 토픽에 넣는, 카프카 안에서 완결되는 스트림 처리임.

## 카프카 스트림즈 소개

카프카 스트림즈는 토픽에 적재된 데이터를 실시간으로 변환해 다른 토픽에 적재하는 라이브러리.

카프카가 공식 지원하는 자바 라이브러리라 클러스터와 완벽하게 호환되고, 애플리케이션이나 브로커에 장애가 나도 정확히 한 번(exactly once) 처리하는 장애 허용 시스템을 갖춰 안정성이 뛰어남.

컨슈머와 프로듀서를 조합해도 비슷한 기능은 만들 수 있지만, exactly once와 장애 허용을 직접 구현하는 비용이 크기 때문에 스트림 처리가 필요하다면 스트림즈를 1순위로 두는 것이 좋음.

제약은 하나, 소스 토픽과 싱크 토픽이 서로 다른 클러스터인 경우는 지원하지 않고 단일 클러스터 안에서만 동작한다는 점임.

내부 구조의 핵심은 태스크(task)로, 데이터 처리의 최소 단위이자 파티션 개수와 동일하게 자동 생성되는 단위임.

파티션 3개짜리 토픽을 처리하면 태스크 3개가 생겨 병렬 처리하는데, 컨슈머 그룹의 컨슈머-파티션 1:1 매칭과 똑같은 그림임.

실제로 스트림즈 애플리케이션 안에는 컨슈머와 프로듀서 클라이언트가 들어 있고, 컨슈머의 group.id에 해당하는 것이 **application.id**임.

같은 application.id를 가진 프로세스를 여러 개 배포하면 하나의 그룹으로 묶여 스케일 아웃됨.

## 스트림즈DSL과 세 가지 추상화

스트림즈 구현 방식은 메서드 체인으로 조립하는 **스트림즈DSL**과 저수준으로 직접 구현하는 **프로세서 API** 두 가지임.

대부분의 기능이 DSL에 이미 있으므로 DSL을 먼저 쓰고, 빠진 기능이 필요할 때만 프로세서 API로 내려가는 것이 정석.

스트림즈DSL에는 다른 메시징 플랫폼에 없는 세 가지 추상 개념이 있음.

토픽 데이터를 어떤 형태로 선언할지의 차이인데, 같은 토픽이라도 사건의 흐름으로 볼지 키별 최신 상태로 볼지에 따라 갈림.

| 개념 | 데이터를 보는 방식 |
|---|---|
| KStream | 레코드의 흐름. 들어온 모든 레코드를 그대로 하나씩 처리 |
| KTable | 키 기준 최신값만 노출. 키-값 저장소처럼 사용 |
| GlobalKTable | 키 기준 최신값(KTable과 유사)이되 전체 파티션을 모든 태스크가 통째로 보유 |

KStream은 컨슈머로 레코드를 하나씩 받는 것과 같고, KTable은 같은 키가 다시 들어오면 최신 값으로 덮어씀.

그래서 사용자 주소처럼 최신 상태만 필요한 데이터에는 KTable이 잘 맞음.

## 조인, 코파티셔닝, 그리고 GlobalKTable

스트림즈에서 가장 독특하고 강력한 기능은 조인임.

흘러오는 주문(KStream)에 그 고객의 최신 주소(KTable)를 실시간으로 붙이는 식으로, 이벤트에 상태를 결합하는 연산임.

데이터베이스 없이 토픽 두 개만으로 낮은 지연에 대용량을 병렬 처리한다는 것이 가장 큰 장점.

레디스나 DB에 접속해 상태를 조회하고 커넥션을 관리하던 과정이 통째로 사라짐.

대신 전제가 하나 붙는데, 바로 **코파티셔닝**임.

조인하는 두 토픽은 파티션 개수가 같고 파티셔닝 전략도 같아야 함.

그래야 같은 메시지 키를 가진 데이터가 같은 파티션, 같은 태스크에 모여 로컬에서 매칭되기 때문임.

조인 키를 따로 지정하지 않아도 메시지 키가 같으면 자동으로 조인되는 것 역시 이 구조에서 나옴.

코파티셔닝이 깨져 파티션 개수가 다르면 조인은 아예 TopologyException으로 실패함.

이럴 때 쓰는 것이 GlobalKTable로, 전체 파티션 데이터를 모든 태스크가 통째로 들고 있어서 코파티셔닝이 안 된 토픽과도 조인이 됨.

대신 조인할 때 KStream 쪽의 어떤 값을 조인 키로 쓸지 직접 지정해야 하고, 전체 데이터를 복제해 들고 있으니 데이터가 크면 부하도 큼.

그래서 데이터가 작으면 GlobalKTable을, 크면 리파티셔닝 후 KTable 조인을 고름.

## 윈도우 프로세싱

시간 구간을 기준으로 취합(집계)하는 것이 윈도우 프로세싱임.

모든 취합은 메시지 키 기준으로 이뤄지므로, 취합하려는 기준에 맞춰 메시지 키를 지정해 프로듀스해야 정확하게 집계됨.

윈도우는 네 종류임.

| 윈도우 | 특징 |
|---|---|
| 텀블링 | 겹치지 않는 고정 구간. 5분마다 방문자 수처럼 구간을 딱 끊어 집계 |
| 호핑 | 겹치는 이동 구간. 사이즈와 간격 두 변수를 가짐 |
| 슬라이딩 | 레코드 타임스탬프 기준으로 구간 내 데이터를 정밀 취합 |
| 세션 | 만료 시간 기준으로 활동을 묶음. 윈도우 사이즈가 가변적 |

윈도우 연산에는 반드시 알아둘 함정이 하나 있음.

카프카 스트림즈는 커밋 단위로 결과를 출력하기 때문에, 윈도우가 끝나기 전에도 중간 정산 데이터가 먼저 나옴.

텀블링 5초에 커밋 간격이 3초라면 3초 시점의 중간값이 나온 뒤 완성된 값이 이어 나오므로, 같은 구간의 값이 여러 번 노출되는 것.

해결책은 윈도우 구간 키로 upsert(겹쳐쓰기)하는 것임.

같은 키에 같은 구간이면 나중 값으로 덮어써 최종값만 남기면, 중간 정산은 사라지고 원하는 취합 결과만 남음.

윈도우 출력이 커밋 단위로 나온다는 점과 구간 키로 덮어쓴다는 점을 이해하고 커밋 시점을 조절해 운영해야 함.

## Queryable store

KTable은 로컬 RocksDB에 구체화된 뷰(Materialized View)로 만들어져 최신 상태를 유지함.

이 뷰를 읽기 전용 키-값 스토어로 가져와 메시지 키 기준으로 토픽 데이터를 조회하는 것이 Queryable store임.

카프카로 로컬 캐시를 구현한 셈이라, 외부 캐시나 DB 없이도 분산 처리 중 최신 상태를 빠르게 조회할 수 있음.

다만 각 인스턴스는 자기가 맡은 파티션 데이터만 들고 있으므로, 분산 운영에서는 원하는 키가 어느 인스턴스에 있는지를 함께 고려해야 함.

## 프로세서 API

DSL로 표현할 수 없는 로직이 필요할 때 저수준으로 직접 구현하는 것이 프로세서 API임.

DSL이 더 추상화된 레벨이고 프로세서 API는 그 안에서 동작하는 것과 같으므로, 둘은 별개가 아니라 층위가 다를 뿐임.

구현 인터페이스는 두 가지로, 로직 후 데이터를 항상 다음으로 넘긴다면 Transformer, 넘길 수도 안 넘길 수도 있다면 Processor를 씀.

Processor도 ProcessorContext의 forward를 쓰면 다음 프로세서로 데이터를 넘길 수 있음.

토폴로지는 DSL처럼 메서드 체인으로 잇는 대신, Topology 객체에 소스와 프로세서와 싱크를 각각 등록하고 부모 프로세서 이름으로 연결선을 명시해 조립함.

## 카프카 스트림즈 vs 스파크 구조적 스트리밍

스트림 처리를 스트림즈로 할지 스파크로 할지는 데이터 엔지니어링에서 자주 하는 고민임.

결정적 차이는 두 가지로 갈림.

하나는 실행 방식으로, 스트림즈는 스탠드얼론 자바 프로세스라 스케일 아웃이 간단하지만 스파크는 Executor 클러스터 기반이라 클러스터가 준비돼 있어야 함.

다른 하나는 입력 소스로, 스트림즈는 카프카만 입력으로 받는 반면 스파크는 소켓, 파일 시스템, 카프카 등 다양한 소스를 받음.

정리하면 카프카 토픽을 입력으로 하는 경량 프로세싱이면 스트림즈, 하둡 생태계(HDFS, Hive 등)처럼 다양한 입력이 얽힌 복잡한 프로세싱이면 스파크가 맞음.

클러스터가 이미 있으면 스파크가 유리하고, 없으면 스트림즈가 개발과 운영이 훨씬 쉬움.

## 마무리

이 섹션을 관통하는 물음은 "카프카만으로 어디까지 처리할 수 있는가"였음.

토픽에서 읽어 변환하고 다시 토픽으로 쓰는 흐름(소스, 스트림, 싱크), 상태를 키-값처럼 다루는 KTable, DB 없이 하는 조인, 시간 단위 취합까지 전부 카프카 안에서 끝남.

프로듀서가 확실하게 보내기, 컨슈머가 빠짐없이 가져오기였다면, 스트림즈는 가져온 것을 실시간으로 가공하기의 트레이드오프임.

그리고 이 모든 기능은 앞 섹션들의 부품 위에 서 있음.

exactly once는 트랜잭션(섹션 8) 위에, 태스크 할당은 컨슈머 리밸런싱(섹션 7) 위에, 상태 백업은 토픽 그 자체 위에 세워졌음.

다음 섹션은 코드 없이 설정만으로 외부 시스템과 연결하는 카프카 커넥트.
