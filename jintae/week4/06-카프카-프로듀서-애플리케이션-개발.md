# [Kafka] 섹션 6 - 카프카 프로듀서 애플리케이션 개발

카프카에서 데이터의 시작점인 프로듀서.

콘솔 프로듀서는 어디까지나 테스트 도구이고, 실제 환경에서는 클릭 로그 같은 데이터를 받아 JSON 등으로 변환해 토픽에 넣는 프로듀서 애플리케이션을 직접 만들게 됨.

## 카프카 프로듀서 소개

시작 전에 알아둘 두 가지.

첫째, 프로듀서든 컨슈머든 토픽에 접근할 때는 반드시 리더 파티션이 있는 브로커와 직접 통신함.

둘째, 오픈소스 아파치 카프카가 공식 제공하는 클라이언트 라이브러리는 자바뿐임.

Go·Python·JavaScript 라이브러리는 서드파티라 성능·기능에서 차이가 날 수밖에 없으므로, 최신 기능과 안정성이 필요하면 자바로 개발하는 것이 정답.

프로듀서가 데이터를 보내는 과정은 네 단계.

ProducerRecord 생성 → send() 호출 → Partitioner가 파티션 결정 → Accumulator에 배치로 쌓임 → Sender가 브로커로 전송.

ProducerRecord에는 토픽·파티션·타임스탬프·메시지 키·메시지 값이 들어가지만 오프셋은 없음.

오프셋은 데이터가 리더 파티션에 저장될 때 브로커가 부여하는 것이라, 만드는 시점에는 지정할 수 없기 때문.

필수 값은 토픽과 메시지 값 두 가지뿐임.

send()를 호출해도 바로 전송되지 않음.

Accumulator가 레코드를 배치로 묶어두었다가 한 번에 보내는데, 레코드마다 TCP 통신을 하는 대신 최대한 묶어 보내 처리량을 높이는 구조임.

다만 반드시 배치로 묶이는 것은 아님. 레코드가 크거나 배치 사이즈가 작으면 레코드별로 나가기도 하므로, 전송 속도가 안 나오면 배치 관련 옵션부터 점검할 것.

## 파티셔너(Partitioner)

메시지 키가 있으면 키의 해시값과 파티션을 매칭해 전송함.

같은 키는 항상 같은 파티션으로 가고, 파티션 안에서는 순서가 보장되므로 키 단위 순서 처리가 가능해짐.

문제는 파티션 개수가 변경되면 해시 매칭이 전부 깨진다는 것.

그래서 키를 쓰는 토픽은 처리량을 계산한 뒤 파티션을 처음부터 여유 있게(필요량의 몇 배로) 만들어 증설할 일 자체를 없애는 것이 정석임.

키가 없을 때는 파티션에 균등 분배함.

구형인 라운드로빈 파티셔너는 레코드 단위로 파티션을 순회해 배치가 잘게 쪼개지는 단점이 있었고, 이를 개선한 것이 유니폼 스티키 파티셔너.

배치 하나가 찰 때까지 한 파티션에 붙어서 모으고, 배치 단위로 파티션을 순회함. 균등 분배는 유지하면서 배치 효율을 극대화한 것으로, 2.5.0의 기본값임.

주의할 것 하나. 어떤 파티셔너를 쓸지는 키의 유무가 아니라 partitioner.class 옵션으로 정해짐.

키 유무는 이미 정해진 파티셔너의 동작 방식을 가를 뿐임.

파티셔너는 직접 구현할 수도 있음. Partitioner 인터페이스를 구현하면 "특정 키는 무조건 0번 파티션으로" 같은 라우팅 규칙을 파티셔너 한 곳에 중앙화할 수 있음.

## 프로듀서 주요 옵션 소개

필수 옵션은 셋이고, 디폴트가 없어 지정하지 않으면 실행 자체가 안 됨.

bootstrap.servers(상용은 2개 이상), key.serializer, value.serializer.

직렬화 덕분에 카프카는 거의 모든 데이터를 적재할 수 있지만, 어떻게 직렬화했는지는 프로듀서와 컨슈머가 규약으로 공유해야 함.

int·float를 String으로 뭉뚱그리면 네트워크·디스크에서 손해지만, 콘솔 컨슈머로 디버깅할 수 있고 역직렬화 방식을 모르는 컨슈머 문제가 없어 StringSerializer 통일도 괜찮은 선택임.

선택 옵션 중 기억할 것들.

| 옵션 | 기본값 | 역할 |
|---|---|---|
| acks | 1 | 전송 성공을 어디까지 확인할지 (신뢰도의 핵심) |
| linger.ms | 0 | 배치를 채우려 기다리는 시간 |
| retries | 2147483647 | 에러 후 재전송 횟수 |
| partitioner.class | DefaultPartitioner | 파티셔너 지정 |
| enable.idempotence | false | 멱등성 프로듀서 여부 (3.x부터 true) |
| transactional.id | null | 지정 시 트랜잭션 프로듀서 |

## ISR(In-Sync-Replicas)와 acks 옵션

ISR은 리더와 팔로워의 오프셋이 동일하게 싱크된 상태.

복제에는 시간이 걸리므로 리더에 10건, 팔로워에 8건인 순간이 생기는데, 이 시간차 때문에 ISR이라는 개념이 필요함.

참고로 ISR은 리더를 포함하는 개념이라 복제 개수 1이어도 리더 혼자서 ISR임.

acks는 이 복제 상태를 어디까지 확인할지 정하는 옵션이고, 철저한 트레이드오프임.

| acks | 확인 범위 | 속도 | 신뢰도 |
|---|---|---|---|
| 0 | 확인 안 함(응답도 안 받음) | 가장 빠름 | 유실 가능 |
| 1 (기본) | 리더 적재 확인 | 중간 | 복제 전 리더 장애 시 유실 가능 |
| all(-1) | 리더+팔로워 적재 확인 | 가장 느림 | 브로커 장애에도 안전 |

acks=0은 GPS 좌표처럼 일부 빠져도 전체 흐름에 문제없는 데이터에 씀.

대부분의 환경은 acks=1로 충분하고, 그래서 기본값임.

하나도 놓치면 안 되는 데이터라면 acks=all인데, 이때 토픽 옵션 min.insync.replicas가 함께 감.

all이 확인하는 대상은 "복제본 전체"가 아니라 min.insync.replicas 개수만큼임.

이 값이 1이면 가장 먼저 적재되는 파티션이 리더라서 acks=1과 동일해져 all로 설정한 의미가 없음.

그래서 최고 신뢰도 조합은 acks=all + min.insync.replicas=2 + 복제 개수 3.

min.insync.replicas=3에 복제 개수 2 같은 조합은 전제부터 모순이라 동작하지 않음.

## 프로듀서 애플리케이션의 안전한 종료

프로듀서 종료는 반드시 close()로.

close()는 Accumulator에 남은 데이터를 모두 전송한 뒤 리소스를 해제함.

강제 종료하면 버퍼에 남은 레코드가 전송조차 되지 못하고 유실되는데, 이것은 acks로도 막을 수 없음. acks는 "전송한 데이터의 적재 확인" 문제이고 이것은 "전송 자체가 안 된" 문제이기 때문.

## 마무리

프로듀서를 관통하는 주제는 결국 두 가지였음.

데이터를 어느 파티션에 둘 것인가(파티셔너·키·순서), 그리고 얼마나 확실하게 보낼 것인가(acks·ISR·min.insync.replicas).

둘 다 정답이 있는 문제가 아니라 데이터의 성격과 비즈니스 요구에 따라 고르는 트레이드오프임.
