# [Kafka] 섹션 7 - 카프카 컨슈머 애플리케이션 개발

프로듀서의 반대편, 컨슈머.

브로커에 적재된 데이터를 가져와 DB 적재·타 시스템 연동 같은 처리를 하는 애플리케이션임.

사실 프로듀서 쪽 설계도 컨슈머에서 출발함 — 컨슈머가 어떤 데이터를 필요로 하는지 확인하고, 그 정보가 담기도록 토픽에 데이터를 넣는 것이 순서임.

## 컨슈머 내부 구조 — poll()도 매번 브로커에 다녀오지 않는다

프로듀서의 send()가 즉시 전송이 아니었듯, 컨슈머의 poll()도 매번 브로커에 다녀오는 것이 아님.

**Fetcher**가 리더 파티션에서 레코드를 배치로 미리 가져와 쌓아두고, poll()은 거기서 꺼내 ConsumerRecords(오프셋 포함)로 리턴함.

쓰기의 Accumulator와 읽기의 Fetcher — 양쪽 모두 네트워크 왕복을 줄이는 배치+버퍼 구조로 대칭임.

카프카가 push가 아니라 pull인 것도 같은 맥락 — 컨슈머가 자기 처리 속도에 맞춰 가져갈 양과 시점을 조절하므로 자연스러운 백프레셔가 생기고, 밀린 만큼이 컨슈머 랙이라는 운영 지표가 됨.

## 컨슈머 그룹 — 커플링을 끊는 장치

컨슈머 그룹은 특정 토픽에 대해 목적에 따라 컨슈머들을 묶은 단위.

서로 다른 그룹은 격리되어 같은 토픽의 데이터를 각자 온전히 다 가져감 — 커밋(오프셋)이 그룹 단위로 저장되기 때문에, 데이터는 한 벌인데 그룹마다 "어디까지 읽었는지" 북마크만 따로 관리되는 구조임.

할당 규칙은 단순함.

**1개 파티션은 그룹 내 최대 1개 컨슈머에만 할당**되고, 1개 컨슈머는 여러 파티션을 받을 수 있음.

따라서 컨슈머 개수 ≤ 파티션 개수여야 하고, 초과분은 아무 일도 안 하는 유휴(idle) 컨슈머가 됨.

파티션 개수만큼 컨슈머를 띄우는 1:1 매칭이 최대 성능이자 가장 일반적인 운영 방식임 — 뒤집으면 파티션 개수가 곧 한 그룹의 최대 병렬성 상한이라는 뜻.

그룹의 존재 이유는 장애 격리임.

에이전트가 엘라스틱서치와 하둡에 동기로 직접 적재하는 구조라면 한쪽 장애가 파이프라인 전체를 막지만, 일단 토픽에 넣고 적재 목적별로 그룹을 나누면 엘라스틱서치가 죽어도 하둡 적재는 무관하고, 복구 후 마지막 커밋 지점부터 이어서 처리하면 됨.

신규 저장소가 필요해지면 기존 파이프라인을 건드리지 않고 그룹만 새로 만들면 됨.

## 리밸런싱 — 사실상 장애 상황

리밸런싱은 파티션-컨슈머 할당이 변경되는 과정.

장애 난 컨슈머의 파티션 소유권을 정상 컨슈머에게 넘겨 가용성을 높이는 컨슈머의 페일오버 방식이고, 컨슈머 추가·제외 두 상황에서 발생함.

문제는 비용 — 파티션이 수백 개면 재할당에 수십 초에서 몇 분이 걸리고, 그동안 처리가 멈추므로 리밸런싱 자체가 사실상 장애와 비슷함.

자주 발생하지 않게 운영하는 것이 기본 목표이되, 언제든 일어날 수 있으므로 대응 코드(리밸런스 리스너)는 반드시 준비할 것.

의외의 함정 하나 — 컨슈머 제외 판정은 하트비트(session.timeout.ms)만이 아님.

poll() 호출 간격이 max.poll.interval.ms를 넘으면 프로세스가 멀쩡해도 "처리가 멈춘 컨슈머"로 간주해 그룹에서 제외함.

레코드 처리 로직이 오래 걸리는 것만으로 리밸런싱이 터지는, 실무에서 가장 흔한 의도치 않은 리밸런싱 원인임.

## 커밋 — 여기까지 처리했다는 기록

컨슈머는 처리를 완료하면 커밋으로 "n번까지 처리했다"를 브로커 내부 토픽 `__consumer_offsets`에 기록함.

기록되는 값은 마지막 처리 오프셋이 아니라 **다음에 읽을 오프셋**(마지막 처리 + 1)임.

커밋이 누락되면 재시작 시 이전 커밋 지점부터 다시 읽어 중복 처리가 발생함 — 그래서 원칙은 "처리 완료 후 반드시 커밋".

처리와 커밋이 별개 동작인 한 그 간극은 0이 되지 않음 — 커밋으로 도달할 수 있는 최선은 at-least-once(유실 없음, 중복 가능)이고, 완전한 해법은 트랜잭션(72강)이나 처리 로직 자체의 멱등 설계(DB upsert 등)임.

## 주요 옵션

필수 옵션은 bootstrap.servers와 key/value.deserializer.

역직렬화는 프로듀서의 직렬화 포맷과의 약속임 — String으로 보낸 것을 int로 읽으면 원하는 값이 절대 나오지 않음.

선택 옵션 중 기억할 것들.

| 옵션 | 기본값 | 역할 |
|---|---|---|
| group.id | null | 컨슈머 그룹 — subscribe() 사용 시 사실상 필수 |
| auto.offset.reset | latest | 커밋 기록이 없을 때 어디서부터 읽을지 |
| enable.auto.commit | true | 자동/수동 커밋 선택 |
| auto.commit.interval.ms | 5초 | 자동 커밋 간격 |
| max.poll.records | 500 | poll() 한 번의 최대 레코드 수 |
| session.timeout.ms | 10초 | 하트비트 없이 버티는 시간 — 초과 시 리밸런싱 |
| heartbeat.interval.ms | 3초 | 하트비트 전송 간격 (timeout의 1/3 이하 권장) |
| max.poll.interval.ms | 5분 | poll() 호출 간격 상한 — 초과 시 리밸런싱 |

생사 판정이 두 축인 것이 포인트 — 하트비트는 별도 스레드가 보내므로 "프로세스가 살아 있는가"를, poll 간격은 "처리가 진행되고 있는가"를 각각 감시함.

처리가 느려 max.poll.interval에 걸린다면 interval을 늘리는 것 말고 max.poll.records를 줄여 배치당 처리 시간을 낮추는 방법도 있음 — 장애 감지 속도를 희생하지 않는 쪽이 보통 더 나음.

## auto.offset.reset — 커밋 기록이 없을 때만

오해가 많아 별도 강의로 분리된 옵션.

**컨슈머 그룹이 한 번도 커밋한 적 없을 때** 어느 오프셋부터 읽을지 정함 — latest(최신부터, 기본값), earliest(가장 오래된 것부터 전부), none(기록 없으면 예외).

이미 커밋 기록이 있으면 이 옵션은 싹 무시되고 커밋 지점부터 이어 읽음.

즉 새 그룹을 처음 운영할 때 한 번 의미가 있는 옵션임 — 유실이 허용되지 않는 적재 파이프라인이면 earliest, 실시간성만 중요하면 latest.

주의할 것 하나 — group.id를 바꿔 재배포하면 새 그룹으로 취급되어 이 옵션이 다시 발동함.

earliest 설정 + 그룹명 변경 조합이 의도치 않은 전체 재처리를 일으키는 단골 사고 패턴임.

## 코드로 — 컨슈머의 진화

기본 골격: 필수 옵션 + group.id → KafkaConsumer 생성 → subscribe() → **while(true) { poll() → 레코드 처리 }**.

무한 루프가 컨슈머 애플리케이션의 기본 원칙이고, 여기서부터 하나씩 얹어감.

**수동 커밋**은 enable.auto.commit=false가 전제.

commitSync()는 poll 배치의 마지막 오프셋 기준으로 커밋하되 응답을 기다리는 동안 처리가 멈추고, commitAsync()는 백그라운드로 커밋해 처리량이 좋지만 재시도하지 않음 — 실패한 옛 커밋을 재시도하면 이미 성공한 최신 커밋을 과거로 되돌릴 수 있기 때문.

그래서 정석은 혼합형 — 루프 안에서는 commitAsync(속도), 종료·리밸런싱 직전에는 commitSync(확실함).

레코드 단위 커밋은 Map<TopicPartition, OffsetAndMetadata>(오프셋+1)을 파라미터로 넘기면 되지만, 커밋은 브로커와의 통신이라 레코드마다 하면 처리 속도가 크게 떨어짐 — 특수한 경우의 기능임.

**리밸런스 리스너**는 ConsumerRebalanceListener 구현체를 subscribe()의 두 번째 파라미터로 등록.

onPartitionsRevoked(리밸런스 직전)에서 지금까지 처리분을 커밋하는 것이 핵심 패턴 — 파티션 소유권을 내려놓기 직전의 마지막 훅이라, 여기서 커밋해야 새 소유자의 중복 처리를 최소화함.

실습에서 컨슈머 B가 조인·이탈할 때 A의 리스너 로그에 revoke → assign이 그대로 찍혔고, B가 나가자 A가 파티션 10개 전부를 이어받아 처리가 중단 없이 지속되는 것까지 확인함.

**assign()**은 그룹 구독 대신 특정 파티션을 직접 할당하는 방식.

group.id가 필수가 아닌 대신 그룹 조인이 없으므로 리밸런싱·자동 분배·페일오버도 전부 없음 — 제어권과 책임을 모두 직접 가져가는 선택이라 특수한 경우에만 씀.

## 안전한 종료 — wakeup()

정상 종료를 알리지 않은 컨슈머는 세션 타임아웃까지 그룹에 좀비처럼 남아 리밸런싱을 지연시킴.

구조는 3단 — 셧다운 훅 스레드에서 wakeup() 호출 → poll()에서 WakeupException 발생 → catch로 받아 finally에서 close().

KafkaConsumer는 스레드 안전하지 않아 다른 스레드에서 close()를 직접 부를 수 없고, wakeup()만이 다른 스레드에서 호출 가능한 유일한 메서드라 이 구조가 나옴.

close()는 코디네이터에 LeaveGroup을 명시적으로 보내므로 타임아웃을 기다리지 않고 즉시 리밸런싱됨.

단 셧다운 훅은 SIGTERM(kill -15)에서만 실행됨 — kill -9는 JVM이 즉사해 이 안전장치 전체가 무력화됨.

수동 커밋 + subscribe + wakeup 종료를 합친 예제가 사실상 실무 컨슈머의 뼈대임.

## 멀티스레드 컨슈머

KafkaConsumer는 스레드 안전하지 않으므로 원칙은 1스레드 1컨슈머.

확장은 두 갈래 — N스레드 프로세스 1개(배포 간단, 장애가 스레드 간 전파 가능) vs 1스레드 프로세스 N개(장애 격리, 배포 부담).

물리 장비·수동 배포 환경이면 멀티스레드, 쿠버네티스처럼 배포 자동화된 환경이면 프로세스 분리가 유리함 — 컨테이너 시대에는 "1스레드 1컨슈머 1파드"가 사실상 표준.

## 컨슈머 랙 — 눈 감고 운전하지 않기

**컨슈머 랙 = 로그 엔드 오프셋(파티션 최신) − 컨슈머 오프셋(커밋 지점)**.

컨슈머 그룹 × 파티션 단위로 생성되는, 파이프라인 운영에서 가장 중요한 지표임.

랙이 늘어난다는 것은 프로듀서 유입량을 컨슈머 처리량이 못 따라간다는 뜻이고, 대응은 파티션·컨슈머 개수를 함께 늘려 병렬 처리량을 선형 확장하는 것.

컨슈머 장애, 파티션 개수 산정, 브로커·파티션 이상까지 이 지표 하나로 파악됨 — 랙 수집 시스템 없이 컨슈머를 운영하는 것은 눈 감고 운전하는 것과 같음.

읽을 때 주의 — 랙의 단위는 개수지 시간이 아니고, 순간적으로 튀는 랙은 정상임.

우상향으로 계속 자라는 추세가 진짜 문제임.

모니터링 방법은 셋.

| 방법 | 한계 |
|---|---|
| kafka-consumer-groups 명령 | 일회성 — 임시 확인용 |
| 컨슈머의 metrics() 메서드 | 컨슈머가 살아 있을 때만, 자기 그룹만, 코드 중복, 서드파티 불가 |
| 외부 모니터링 툴 | 사실상 없음 — 최선 |

외부 툴의 본질은 브로커 관점의 상시 측정임.

랙 모니터링이 가장 필요한 순간은 컨슈머가 죽었을 때인데, metrics()는 그 순간 함께 사라짐 — 브로커에서 재는 외부 툴만이 이 역설을 해결함.

## 버로우 — 임계치 대신 상태 판정

링크드인이 공개한 컨슈머 랙 전용 오픈소스 툴.

REST API로 그룹별 랙을 제공하고, 다수 클러스터를 동시에 모니터링할 수 있음.

최대 강점은 **Evaluation** — "랙 100 이상이면 알람" 식 임계치는 잠깐 튀었다 스스로 내려오는 정상 상황에도 알람을 울리는 무의미한 짓이 되기 쉬움.

버로우는 슬라이딩 윈도우로 랙과 오프셋의 추세를 계산해 파티션(OK/STALLED/STOP)·컨슈머(OK/WARNING/ERROR) 상태를 판정함.

| 상태 | 상황 | 대응 |
|---|---|---|
| OK | 랙이 낮게 유지, 가끔 튀어도 복귀 | 정상 |
| WARNING | 랙이 선형으로 계속 증가 (처리량 부족) | 파티션·컨슈머 증설 |
| ERROR | 커밋 자체가 정지, 랙 급증 (처리 멈춤) | 즉각 알람·조치 |

수집 스택은 버로우 → 텔레그래프 → 엘라스틱서치 → 그라파나, 전부 오픈소스임.

## 마무리

컨슈머를 관통하는 주제는 결국 세 가지였음.

일을 어떻게 나눌 것인가(그룹·파티션 할당·리밸런싱), 어디까지 처리했다고 기록할 것인가(커밋·오프셋), 그리고 밀리고 있지 않은가(랙·모니터링).

프로듀서가 "확실하게 보내기"의 트레이드오프였다면, 컨슈머는 "중복 없이·멈춤 없이 가져오기"의 트레이드오프임.
