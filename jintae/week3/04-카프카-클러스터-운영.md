# [Kafka] 섹션 4 - 카프카 클러스터 운영

이번 섹션은 코드가 아니라 선택의 이야기.

카프카 클러스터를 어디에, 어떤 형태로 띄울 것인가.

직접 설치와 SaaS 사이의 트레이드오프를 따져봄.

## 운영 방법에 따른 서비스 형태

소프트웨어 운영 형태는 직접 관리 영역이 줄어드는 순서로 네 가지.

| 형태 | 특징 |
|---|---|
| 온프레미스 | 자체 전산실 서버에 직접 설치. 하드웨어 커스터마이징 가능, 초기 도입·유지보수 비용 발생 |
| IaaS | AWS·GCP 등에서 인스턴스를 발급받아 사용. OS·애플리케이션은 직접 설정·배포·운영 |
| PaaS | 개발·실행 환경 제공(예: Lambda). 리소스 관리 불필요, 세세한 튜닝은 제한적 |
| SaaS | 소프트웨어 생명 주기 전체를 업체가 관리. 기능만 사용 |

카프카는 주로 온프레미스·IaaS(직접 설치) 또는 SaaS(컨플루언트 클라우드, AWS MSK)로 운영함.

직접 설치에는 또 하나의 갈림길이 있음.

아파치 2.0 라이선스의 **오픈소스 카프카**를 쓸 것인가, 커넥터와 모니터링 툴이 포함된 유료 **기업용 카프카**(컨플루언트 플랫폼)를 쓸 것인가.

## 직접 설치한다면: 하드웨어 공식

카프카는 데이터를 전부 파일 시스템에 저장하고 대규모 통신이 일어나므로 고성능 하드웨어가 필요함.

컨플루언트의 상용 환경 권장 사양이 흥미로움.

- 메모리: 32GB 머신에 **힙은 6GB만**. 나머지는 OS 페이지 캐시로
- CPU: 24core (SSL 사용 시 더 높게)
- 디스크: RAID 10, **NAS 금지**
- 파일시스템: XFS 또는 ext4

"메모리는 크게, 힙은 작게"가 핵심.

카프카는 레코드를 JVM 힙에 캐시하지 않고 OS 페이지 캐시에 위임하기 때문에, 힙을 크게 잡으면 GC 정지만 길어질 뿐임.

32GB에서 힙 6GB를 뺀 26GB가 통째로 읽기 캐시가 됨.

NAS가 금지인 이유도 같은 맥락.

카프카 성능의 전제는 로컬 디스크의 순차 I/O인데, 네트워크 너머의 스토리지는 그 전제를 깨고 모든 브로커의 공통 장애점이 됨.

규모는 개발용 브로커 5대(16GB·16core), 상용 10대(32GB·24core)가 기준선.

개발용조차 5대인 이유가 있음.

브로커 1대로는 복제·acks·min.insync.replicas 같은 분산 동작을 아무것도 테스트할 수 없고, 정작 상용에서 처음 겪는 사고가 됨.

개발 환경은 규모만 줄이고 구조는 상용과 같게 가져가는 것이 원칙.

디스크는 유입량 × 보존일 × 복제 수로 계산함(하루 1TB, 7일, 복제 3이면 21TB).

## SaaS형 카프카: 컨플루언트와 MSK

**컨플루언트**는 카프카를 처음 고안한 제이 크렙스가 세운 회사.

스키마 레지스트리, ksqlDB, REST Proxy 같은 도구를 공개하며 생태계를 주도함.

제공 형태는 둘.

| 컨플루언트 클라우드 | 컨플루언트 플랫폼 |
|---|---|
| 클라우드 기반, 완전 위임형 SaaS | 온프레미스 설치형 |
| 자동 리소스 확장, 리전 지정 | 서버를 내부에서 직접 발급·설치 |
| 120+ 커넥터, ksqlDB, 스키마 레지스트리 | 티어드 스토리지, GUI 모니터링 |
| 99.95% SLA, 엔터프라이즈 보안 | 컨플루언트 팀 지원 |

플랫폼(설치형)이 존재하는 이유는 법적 제약.

개인정보·결제정보가 외부 클라우드로 나가면 안 되는 산업군은 컨플루언트 기능을 온프레미스에서 쓰는 쪽을 택함.

**AWS MSK**는 오픈소스 카프카를 AWS가 관리형으로 제공하는 서비스.

직접이라면 `server.properties`를 고치고 브로커를 롤링 리스타트해야 하는 설정 변경이 웹 콘솔 클릭 몇 번으로 끝남.

카프카 버전을 직접 선택할 수 있어 기존 클라이언트와의 버전 차이 없이 마이그레이션 가능하고, 클러스터가 내 VPC 안에 생겨 기존 AWS 서비스와의 연동이 자연스러움.

둘은 같은 SaaS가 아님.

MSK는 진짜 오픈소스 카프카를 EC2 위에 띄워 주는 것이라 브로커가 사용자에게 보이고, 스케일링 판단·파티션 재분배 같은 카프카 운영 지식이 그대로 필요함.

컨플루언트 클라우드는 카프카 프로토콜 호환 자체 엔진(Kora)이 돌아 브로커 개념 자체가 추상화됨.

AWS 중심 + 운영 지식 보유 + 비용 민감이면 MSK, 운영 지식 최소화 + 생태계 통째 위임 + 멀티클라우드면 컨플루언트가 어울림.

## SaaS의 장점

**인프라 관리의 효율화.**

직접 운영하면 브로커 3대 + (구버전이라면) 주키퍼 3대, 총 6대 이상을 상시 모니터링해야 함.

SaaS는 브로커 서버 장애를 감지해 신규 장비로 알아서 복구하고, 스케일아웃은 대시보드에서 브로커 개수만 바꾸면 끝남.

**모니터링 대시보드.**

직접 설치한 카프카에는 아무것도 없음.

지표를 수집하려 하면 50개가 넘는 지표 중 뭘 봐야 할지부터 막막함.

SaaS는 중요한 지표를 자동 수집해 그래프로 보여줌.

**보안 기본 제공.**

보안 설정 없는 클러스터는 자물쇠 없는 외양간.

호스트와 포트만 알면 모든 토픽을 읽을 수 있고 어드민 API로 공격도 가능함.

카프카의 보안은 세 겹의 자물쇠인 SSL(암호화, 도청 방지), SASL(인증, 너 누구야), ACL(인가, 너는 여기까지)인데, 이 조합을 직접 구성하는 것은 쉽지 않은 일이고 SaaS는 완성본을 기본 제공함.

## SaaS의 단점

**비용.**

MSK로 브로커 3대(kafka.m5.xlarge)를 돌리면 서울 리전 기준 시간당 1.5달러, 월 약 120만 원.

동일 사양 인스턴스를 직접 발급하면 월 약 60만 원.

**2배 이상 차이**가 나고, 데이터를 하나도 안 보내도 나가는 최소 비용임.

다만 이 비교에는 함정이 있음.

직접 운영의 진짜 비용은 서버비가 아니라 모니터링 구축, 장애 대응, 그리고 그걸 할 줄 아는 인력의 급여임.

전담 엔지니어 인건비를 넣으면 소규모에서는 SaaS가 오히려 싸고, 클러스터가 수십 대로 커지면 역전됨.

**커스터마이징 제한.**

SaaS는 업체가 정한 아키텍처를 따라가므로 브로커 옵션을 충분히 조절할 수 없는 경우가 많음.

멀티 클라우드나 하이브리드 클라우드(사내 서버 + 퍼블릭 클라우드) 형태의 클러스터 구성도 불가능함.

**클라우드 종속성.**

서비스를 선택하는 순간 프로듀서·컨슈머를 포함한 모든 애플리케이션이 그 서비스에 종속됨.

더 싼 업체가 나타나거나 온프레미스로 돌아가야 할 때, 종속성 때문에 마이그레이션이 매우 복잡해짐.

## 그래서 어떻게

핵심 변수는 운영 노하우.

노하우가 부족한 상태에서 빠르게 인프라를 구축해야 한다면 SaaS가 최고의 선택지임.

직접 설치로 서비스 리스크를 높이는 것보다, 자동화된 인프라를 쓰면서 노하우를 키우고 필요해지면 마이그레이션을 고려하는 경로가 안전함.

다만 SaaS도 결국 카프카임.

토픽 설계, 클라이언트 튜닝, 컨슈머 랙 대응은 여전히 사용자 몫이라, 카프카에 대한 이해가 있어야 SaaS도 제대로 쓸 수 있음.

도입 판단의 체크리스트는 넷.

팀의 인력 구성, 카프카 운영 이해의 깊이, 클러스터 구축 비용, 추후 운영상 이슈.

이 네 가지를 다각도로 검토하는 것이 안정적인 서비스 운영의 밑바탕이 됨.
