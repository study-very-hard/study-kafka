# [Kafka] 섹션 5 - 아파치 카프카 CLI 활용

이번 섹션은 손으로 익히는 이야기.

카프카가 제공하는 커맨드 라인 툴로 토픽을 만들고, 데이터를 넣고, 읽고, 컨슈머 그룹을 관리해봄.

CLI는 브로커 운영자만의 도구가 아님.

애플리케이션을 개발하다 보면 "데이터가 정상적으로 갔는지, 토픽이 실제로 존재하는지, 파티션이 몇 개인지" 확인할 일이 계속 생기고, 그 확인은 결국 CLI로 하게 됨.

## 시작하기 전에 — 기본값의 함정

CLI 옵션은 필수 옵션과 선택 옵션으로 나뉨.

선택 옵션은 지정하지 않으면 브로커에 설정된 기본값으로 대체됨.

문제는 그 기본값이 내 의도와 다를 수 있다는 것.

브로커의 파티션 기본값이 10인데 5개면 충분한 토픽을 옵션 없이 만들면, 파티션 10개짜리 토픽이 생김.

그리고 파티션 개수는 줄일 수 없으므로 이 실수는 토픽 삭제·재생성 말고는 되돌릴 방법이 없음.

그래서 CLI 사용의 제1원칙은 "토픽은 기본값이 아니라 의도로 만든다".

사용 전에 브로커 설정을 확인하고, 파티션 수·복제 수는 항상 명시적으로 지정함.

## 로컬 브로커 실행

로컬 실행에 필요한 프로세스는 둘 — 주키퍼와 브로커, 반드시 주키퍼가 먼저.

바이너리(`kafka_2.12-2.5.0`)를 받으면 앞의 2.12는 스칼라 빌드 버전이고 뒤의 2.5.0이 카프카 버전임.

`server.properties`에서 눈여겨볼 것은 listeners와 advertised.listeners.

listeners는 브로커가 실제로 소켓을 여는 주소이고, advertised.listeners는 메타데이터에 실어 클라이언트에게 알려주는 접속 주소임.

로컬에서는 둘 다 localhost라 차이가 없지만, 도커·클라우드 환경에서 "부트스트랩 접속은 되는데 그 뒤 통신이 실패"하는 단골 문제가 대부분 이 설정 문제.

실행 확인은 `kafka-broker-api-versions.sh` 응답 또는 `kafka-topics.sh --list`의 빈 출력으로 함.

이후 실습과 소스코드가 모두 `my-kafka`로 접속하므로 hosts에 `127.0.0.1 my-kafka`를 등록해 둠.

## kafka-topics.sh — 토픽의 생성과 구조

필수값은 `--bootstrap-server`와 `--topic` 두 가지.

`--create`로 만들고, `--describe`로 파티션 개수·복제 개수·리더 위치를 확인하고, `--list`로 목록을 보고, `--alter --partitions N`으로 파티션을 늘림.

describe 출력의 Leader, Replicas, Isr은 전부 브로커 ID임.

Replicas의 첫 번째가 선호 리더이고, Replicas와 Isr이 다르면 뒤처진 팔로워가 있다는 뜻 — 운영 중 복제 상태 점검의 핵심 지표.

파티션 축소를 시도하면 InvalidPartitionsException이 남.

이미 분산된 데이터를 줄이려면 삭제 대상 파티션 선정과 레코드 재분산이 필요해 복잡하기 때문에 카프카는 이 기능 자체를 제공하지 않음.

늘리기 전에 "줄일 일은 없는지"를 논의하고, 정 줄여야 하면 새 토픽을 만드는 편이 나음.

## kafka-configs.sh — 설정의 조회와 변경

kafka-topics가 토픽의 구조를 다룬다면 kafka-configs는 설정값을 다룸.

`--alter --add-config min.insync.replicas=2`처럼 토픽 옵션을 브로커 재시작 없이 즉시 반영함.

반대 방향의 쓰임새가 더 중요할 수 있음.

`--broker 0 --all --describe`는 server.properties를 열지 않고도 브로커의 전체 설정을 보여줌.

토픽을 만들기 전에 파티션이 몇 개로 자동 생성될지 확인하는, 제1원칙의 실행 수단임.

## kafka-console-producer.sh — 데이터 넣기

토픽에 테스트 용도로 데이터를 넣는 CLI로, 한 줄이 하나의 레코드가 됨.

기본으로는 입력한 내용이 메시지 값이 되고 메시지 키는 null.

키를 넣으려면 `--property "parse.key=true" --property "key.separator=:"`를 주고 `k1:value` 형태로 입력함.

키가 있으면 동일한 키는 항상 동일한 파티션으로 들어감.

파티션 안에서는 오프셋 순서가 보장되므로, 특정 데이터의 순서를 지켜 처리하고 싶을 때 메시지 키를 지정하는 것.

이 매핑은 해시(`murmur2(키) % 파티션 수`)라서 파티션 수가 바뀌면 전부 바뀜 — 키를 쓰는 토픽의 파티션 수를 처음부터 여유 있게 잡아야 하는 이유.

## kafka-console-consumer.sh — 데이터 읽기

토픽 데이터를 임시로 조회하는 CLI.

`--from-beginning`은 가장 오래된 데이터부터, 없으면 실행 이후 데이터만 출력함.

`print.key=true`로 키를 함께 보고, `--max-messages`로 개수를 제한하고(상용 토픽에서 필수), `--partition`으로 특정 파티션만 조회함.

`--group`을 주는 순간 성격이 달라짐.

컨슈머 그룹은 어느 오프셋까지 읽었는지를 커밋하기 위한 단위이고, 커밋 기록은 `__consumer_offsets`라는 내부 토픽에 저장됨.

그룹으로 읽으면 컨슈머가 죽었다 살아나도 마지막 커밋 다음부터 이어 읽음.

주의할 점 하나 — 커밋이 있으면 `--from-beginning`은 무시됨.

이 옵션의 실체는 auto.offset.reset=earliest인데, 이 설정은 커밋된 오프셋이 없을 때만 적용되기 때문.

## kafka-consumer-groups.sh — 그룹 관리와 컨슈머 랙

컨슈머를 운영하면 그룹은 반드시 생기므로, 그룹을 다루는 이 툴이 정말 중요함.

`--describe`의 세 숫자가 핵심.

| 항목 | 의미 |
|---|---|
| CURRENT-OFFSET | 그룹이 커밋한(확실히 읽은) 오프셋 |
| LOG-END-OFFSET | 파티션의 마지막 오프셋 |
| LAG | 둘의 차이 = 처리하지 못하고 밀린 양 |

랙이 계속 늘어난다는 것은 컨슈머 처리량이 프로듀서 유입량을 못 따라간다는 신호.

이 지표를 보고 파티션이나 컨슈머 개수를 늘리는 결정을 내림.

`--reset-offsets`는 그룹이 어느 오프셋부터 다시 읽을지 되돌리는 기능.

밀린 데이터를 건너뛰고 신규 데이터부터 받으려면 `--to-latest`, 전체 재처리는 `--to-earliest`.

리텐션 기간 안에서는 데이터가 삭제되지 않으므로 "한 번 처리한 데이터의 전체 재처리"가 가능하다는 것이 카프카다운 운영 방식임.

안전장치도 눈여겨볼 만함 — `--execute`를 붙이기 전까지는 예상 결과만 보여주는 dry-run이 기본이고, 활성 컨슈머가 있는 그룹은 리셋이 거부됨.

## 그 외 툴들

`kafka-producer-perf-test.sh` / `kafka-consumer-perf-test.sh`는 호스트-브로커 구간의 처리량·지연을 측정하는 성능 진단 도구.

출력의 백분위 지연(95th, 99th)이 평균만 보면 놓치는 꼬리 지연을 드러냄.

`kafka-reassign-partitions.sh`는 리더 파티션이 특정 브로커에 쏠렸을 때 재분배하는 도구.

클라이언트는 리더와만 통신하므로 쏠린 브로커만 계속 일하게 되는데, 이를 브로커 사이에 고르게 재배치함.

`kafka-delete-records.sh`는 이름과 달리 특정 레코드 하나를 지우는 게 아니라 지정 오프셋 이전을 통째로 지움.

정확히는 로그 시작 오프셋을 앞으로 옮기는 것 — "카프카는 임의 삭제가 없다"의 유일한 공식 예외이지만 이것조차 앞부분 통째로만 가능함.

`kafka-dump-log.sh`는 세그먼트 파일에 실제로 어떤 레코드가 저장됐는지 확인하는 브로커 운영자용 도구.

## 토픽을 만드는 두 가지 방법

명시적 생성(kafka-topics --create) 말고도, 존재하지 않는 토픽에 프로듀서가 데이터를 보내거나 컨슈머가 요청하면 토픽이 자동 생성됨(auto.create.topics.enable=true가 기본).

자동 생성된 토픽은 전부 브로커 기본값으로 만들어짐.

더 위험한 것은 유령 토픽 — 토픽 이름에 오타를 내면 에러 대신 빈 토픽이 조용히 생기고, "왜 데이터가 안 오지?"류 사고의 단골 원인이 됨.

그래서 상용에서는 자동 생성을 끄는 것이 사실상의 표준이고, 결론은 다시 제1원칙으로 돌아감.

토픽은 기본값이 아니라 의도로 만든다.

## 버전 이야기 — 브로커와 CLI는 한 몸

마지막 강의의 결론은 하나.

브로커 버전과 커맨드 라인 툴 버전은 반드시 맞출 것.

버전에 따라 옵션이 달라 명령이 실패할 수 있는데, 오류가 나면 차라리 다행이고 원하지 않는 옵션으로 조용히 설정되는 쪽이 더 위험함.

브로커가 2.7.0이면 2.7.0 배포판을 받아 그 안의 셸 스크립트로 명령을 내림 — 배포판 tgz가 곧 CLI 모음이므로, 버전별로 배포판을 받아두는 것이 곧 버전 맞추기임.

## 마무리

CLI 툴의 실체는 카프카 배포판에 포함된 자바 클래스를 실행하는 래퍼임.

즉 콘솔 프로듀서·컨슈머도 결국 자바 클라이언트이고, 지금까지 옵션으로 만졌던 것들을 다음 섹션부터는 코드로 직접 다루게 됨.

섹션 6은 카프카 프로듀서 애플리케이션 개발.
