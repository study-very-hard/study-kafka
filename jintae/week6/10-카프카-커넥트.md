# [Kafka] 섹션 10 - 카프카 커넥트

앞 섹션들이 프로듀서로 넣고 컨슈머로 꺼내고 스트림즈로 가공하는 이야기였다면, 이번 섹션은 그 넣고 빼는 파이프라인 자체를 코드 없이 반복 생성하는 카프카 커넥트를 다룸.

정형화된 적재와 추출을 매번 애플리케이션으로 개발하는 대신, 설정만으로 파이프라인을 찍어내는 도구임.

## 카프카 커넥트 소개

카프카 커넥트는 토픽에 데이터를 넣거나 빼는 파이프라인을 템플릿 형태로 반복 생성하는 공식 툴임.

일반적으로 토픽에 데이터를 넣고 빼려면 프로듀서나 컨슈머를 직접 개발해야 하는데, 파이프라인이 여러 개로 늘어나면 비슷한 코드를 반복 작성하는 비용이 커짐.

커넥트는 한 번 만든 양식을 두고 설정만 바꿔 파이프라인을 반복 생성하므로 이 비용을 줄여줌.

방향에 따라 두 종류로 나뉨. 외부의 데이터를 토픽에 넣는 소스 커넥터는 프로듀서 역할이고, 토픽의 데이터를 외부로 내보내는 싱크 커넥터는 컨슈머 역할임.

용어를 구분하면, 툴 전체 구조는 커넥트이고 그 안에서 실제 파이프라인으로 동작하는 것이 커넥터임.

REST API로 파이프라인을 실행하거나 중단하거나 수정할 수 있고, JMX 익스포터 같은 도구로 커넥트 내부의 모든 파이프라인을 한 번에 관측할 수 있음.

내부 구조는 커넥터와 태스크로 나뉨. 실제 데이터 처리는 태스크가 담당하고, 커넥터는 태스크를 몇 개 둘지와 각 설정을 정하며 상태를 관장함.

정확히는 커넥터를 실행하는 프로세스 단위를 워커라 부르고, 그 안에서 커넥터가 하나, 태스크가 여러 개 스레드로 동작함.

## 커넥터

소스 커넥터를 직접 개발하는 대신 커넥터로 만드는 이유는 파이프라인의 반복성에 있음.

지금은 테이블 하나를 토픽에 넣지만 나중에 열 개, 백 개의 테이블을 각각 토픽으로 나눠 넣어야 할 때, 매번 프로듀서를 개발하면 파이프라인이 파편화됨.

커넥터 하나를 템플릿으로 두면 같은 양식으로 여러 파이프라인을 운영할 수 있고 통합 모니터링도 됨.

커넥터는 자바로 컴파일한 jar 플러그인으로 동작하며 필요한 만큼 추가할 수 있음.

종류는 두 가지로, 이미 공개된 jar를 내려받아 쓰는 오픈소스 커넥터와 직접 개발하는 커스텀 커넥터임.

HDFS, AWS S3, JDBC, 엘라스틱서치 커넥터 등 백 개가 넘는 오픈소스 커넥터가 컨플루언트 허브에 공개되어 있고, 각 기술을 만든 회사가 직접 제공하는 경우가 많아 성능과 기능 면에서 이점이 큼.

다만 오픈소스라고 모두 무료인 것은 아니므로, 라이선스와 사용 범위를 확인한 뒤 도입해야 함.

컨버터와 트랜스폼은 커넥터와 별개인 선택적 변환 플러그인으로, 스키마를 바꾸거나 메시지 단위로 데이터를 간단히 변환할 때 사용함.

## 커넥트 배포 및 운영

커넥트를 실행하는 방법은 단일 모드와 분산 모드 두 가지임.

단일 모드는 프로세스 하나로 실행되어 구성이 단순하지만 고가용성이 없음.

프로세스 하나에 문제가 생기면 파이프라인을 안전하게 이어받을 수단이 없어, 개발 환경이나 중요도가 낮은 파이프라인에 적합함.

이렇게 하나의 지점에 장애가 발생하면 전체가 멈추는 구조를 단일 장애점이라 부름.

분산 모드는 여러 프로세스를 하나의 그룹으로 묶어 운영함.

처리량이 많아지면 같은 그룹으로 프로세스를 추가해 무중단으로 확장하고, 특정 프로세스에 장애가 발생하면 그 작업이 남은 프로세스로 다시 분산됨.

그래서 상용 환경에서는 분산 모드를 기본으로 삼고 최소 두 대 이상으로 구성함.

분산 모드에서 커넥터를 실행하거나 수정하거나 삭제하는 작업은 REST API로 함.

8083 포트로 요청을 보내면 그때마다 파이프라인이 새로 생성되므로, 복잡한 배포 체계 없이도 파이프라인을 유연하게 운영할 수 있음.

커스텀 커넥터를 개발할 때 이 REST 인터페이스를 직접 만들 필요는 없음. 커넥트 툴이 제공하므로 개발자는 태스크와 커넥터 두 클래스만 구현하면 됨.

## 단일모드 커넥트

단일 모드는 커넥트 설정 파일과 커넥터 설정 파일을 함께 지정해 실행함.

커넥트 설정 파일에는 연동할 카프카 주소와 컨버터, 오프셋 저장 위치, 플러그인 경로가 들어가고, 커넥터 설정 파일에는 커넥터 이름과 클래스, 태스크 개수, 소스 대상이 들어감.

어떤 카프카와 연동할지는 커넥터 설정이 아니라 커넥트 설정 파일에 적힌다는 점이 핵심임.

단일 모드는 진행 위치를 로컬 파일에 저장하므로 그 파일 경로를 안전하게 관리해야 함. 이 로컬 저장 방식이 단일 장애점의 근본 원인이기도 함.

## 분산모드 커넥트

분산 모드는 여러 워커를 같은 group.id로 지정해 하나의 클러스터로 묶음.

태스크 개수가 100개인 커넥터를 실행하면 워커들에 나뉘어 스레드로 동작하고, 처리량이 늘면 같은 group.id로 워커를 추가해 확장함.

분산 모드의 결정적 특징은 상태를 로컬 파일이 아니라 카프카 토픽에 저장한다는 점임.

오프셋과 설정과 상태를 담는 세 가지 내부 토픽을 두어, 워커 여러 대가 모두 종료되었다가 다시 실행돼도 데이터가 그대로 유지됨.

이 세 토픽은 사용자가 직접 데이터를 넣거나 빼지 않고, 파이프라인 관리는 전적으로 REST API로 함. 토픽에 임의로 손대면 커넥트 클러스터의 데이터가 손상될 수 있으므로 주의해야 함.

group.id와 세 토픽은 클러스터마다 고유해야 함. 다른 클러스터와 겹치면 서로의 설정이 섞이기 때문임.

실행 흐름은 두 단계임. 설정 파일로 커넥트 프로세스를 먼저 실행하고, 그다음 REST API로 파이프라인을 생성함.

## 커스텀 소스 커넥터

오픈소스로 해결되지 않는 요구사항이 있으면 소스 커넥터를 직접 개발함.

connect-api 라이브러리를 추가해 SourceConnector와 SourceTask 두 클래스를 상속 구현하고, 참조 라이브러리까지 묶은 하나의 jar로 빌드해 플러그인으로 추가함.

참조 라이브러리를 함께 담지 않으면 실행 시 클래스를 찾지 못하는 오류가 발생하므로, 의존성을 모두 포함한 uber jar로 만들어야 함.

커넥터는 설정을 검증하고 어떤 태스크를 쓸지 지정하는 관리 역할만 하고, 실제 데이터 처리는 태스크가 담당함.

소스 태스크는 프로듀서와 다르게 자체 오프셋을 가짐. 소스를 어디까지 읽었는지 저장하는 값으로, 파일을 줄 단위로 읽으면 라인 번호가 그 역할을 함.

프로듀서와 결정적으로 다른 점은 데이터를 직접 보내지 않는다는 것임. poll 메서드가 레코드 목록을 반환하면 커넥트가 그 레코드를 토픽으로 보냄.

poll도 개발자가 호출하지 않고 커넥트가 주기적으로 호출함. 이 자체 오프셋 덕분에 태스크가 재시작돼도 처음부터 다시 읽지 않고 이어서 읽음.

## 커넥터 옵션값 설정 시 중요도(Importance) 지정 기준

커넥터 옵션을 정의할 때 중요도를 HIGH, MEDIUM, LOW로 지정할 수 있음.

다만 이 값에 명확한 기준은 없고, 옵션이 중요하다는 것을 표시하는 문서 용도일 뿐임.

HIGH로 지정해도 입력이 필수가 되는 것은 아니고, LOW라고 해서 기본값이 강제되는 것도 아님.

권장 구분은 반드시 입력해야 하는 값을 HIGH, 기본값이 있는 선택 옵션을 MEDIUM, 없어도 되는 옵션을 LOW로 두는 정도임.

정말 필수인 값은 중요도 표시가 아니라 코드로 강제해야 함. 시작 단계의 검증에서 값이 없으면 예외를 발생시키는 방식이 더 확실함.

## 커스텀 싱크 커넥터

싱크 커넥터는 토픽의 데이터를 외부로 저장하는 파이프라인으로, 내부적으로 컨슈머와 같은 방식으로 동작함.

SinkConnector와 SinkTask 두 클래스를 구현한다는 점은 소스 커넥터와 같지만, 태스크의 핵심 메서드가 다름.

소스 태스크의 poll에 해당하는 것이 싱크 태스크의 put임. 컨슈머가 반복 호출하던 폴링이 put 메서드로 추상화되어, 커넥트가 폴링한 레코드 묶음을 put으로 넘겨줌.

개발자는 put 안에 각 레코드를 처리하는 로직을 넣으면 됨. 데이터베이스에 저장한다면 여기에 저장 구문이 들어감.

flush는 커밋 시점마다 호출되어 어디까지 처리했는지를 반영함. put에서 적재하고 flush에서 확정하는 두 단계 분리가 싱크 태스크 설계의 핵심임.

싱크 커넥터의 설정에서는 어떤 토픽에서 데이터를 받을지를 담는 topics가 기본으로 제공되므로, 저장 대상 같은 추가 옵션만 정의하면 됨.

## 분산모드 카프카 커넥트 실습

분산 모드 커넥트의 전체 생명 주기를 REST API로 다뤄봄.

설정 파일을 준비하고 워커를 실행한 뒤, 사용할 수 있는 커넥터 플러그인을 조회함.

토픽 데이터를 파일에 저장하는 커넥터를 JSON으로 생성하고, 상태 조회로 커넥터와 태스크가 실행 중인지 확인함.

여기서 태스크 개수는 싱크 커넥터 기준으로 파티션 개수와 동일하게 두는 것이 좋음. 싱크 태스크가 컨슈머 역할이라 파티션과 일대일로 맞을 때 가장 빠르기 때문임.

파티션보다 태스크를 많이 띄우면 할당받지 못한 태스크가 유휴 상태로 남음.

토픽에 데이터를 넣으면 지정한 파일에 저장되는 것을 확인하고, 마지막으로 삭제 요청으로 파이프라인을 정리함.

이 과정을 JMX 같은 도구 없이 REST 요청만으로 확인할 수 있어, 파이프라인 관리 도구를 만들 때 유용함.

## 카프카 커넥트를 운영하기 위한 웹페이지

지금까지의 실습처럼 커넥트를 curl로만 운영하면 부담이 큼.

매번 명령을 작성하고 응답을 해석해야 하며, 운영자가 개발자가 아니면 REST API 전체를 파악하기 어렵기 때문임.

그래서 파이프라인을 지속적으로 관리하려면 웹 화면을 두는 것이 일반적임. 조회와 생성, 수정, 삭제를 화면에서 클릭으로 처리함.

강의에서는 오픈소스로 공개한 kafka-connect-web을 소개했고, 이런 웹 UI를 도입해 운영하는 것을 권장함.

웹 UI도 내부적으로는 같은 REST API를 호출하므로, REST 구조를 이해하면 어떤 도구를 쓰든 동작을 예측할 수 있음.

## 마무리

이 섹션을 관통하는 물음은 반복되는 적재와 추출을 어떻게 표준화하는가였음.

프로듀서와 컨슈머를 매번 개발하는 대신, 커넥트는 설정과 REST API로 파이프라인을 찍어냄. 소스 커넥터가 데이터를 토픽에 넣고, 싱크 커넥터가 토픽 데이터를 외부로 보냄.

분산 모드가 상용의 기본이 되는 이유는 상태를 카프카 토픽에 저장해 확장과 장애 대응을 얻기 때문이고, 이 설계는 컨슈머 그룹의 리밸런싱과 토픽의 영속성 위에 서 있음.

프로듀서가 확실히 보내기, 컨슈머가 빠짐없이 가져오기, 스트림즈가 실시간으로 가공하기였다면, 커넥트는 그 파이프라인을 반복 가능하게 만들기의 트레이드오프임.

다음 섹션은 이 모든 기술을 언제 무엇으로 선택할지 실제 사례로 정리하는 카프카 활용 아키텍처.
