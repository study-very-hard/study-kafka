# [Kafka] 섹션 12 - 커리큘럼 복습

마지막 섹션은 지금까지 배운 개념을 단어별로 되짚는 복습임.

각 개념이 무엇이고 어떤 역할을 하는지 한 번에 정리함.

## 카프카 기본 개념

- **카프카**: 카프카 클러스터를 포함한 이벤트 스트림 프로세싱 아키텍처 전반을 뜻하는 통합 개념
  - 브로커, 토픽, 파티션, 레코드, ISR, 프로듀서, 컨슈머, 스트림즈, 커넥트가 모두 이 안에 속함
  - "카프카를 쓴다"는 말은 브로커와 통신하거나 스트림즈를 쓰는 것까지 폭넓게 가리킴
- **브로커**: 카프카 클러스터를 이루는 서버 하나, 그리고 그 서버에서 실행되는 애플리케이션
  - 데이터를 저장하고 전달하는 역할이 가장 큼
  - 프로듀서가 데이터를 보내면 리더 파티션에 저장하고, 컨슈머가 요청하면 리더 파티션의 데이터를 전달함
  - 브로커가 없으면 카프카를 쓸 수 없으므로 반드시 실행해 두어야 함
- **토픽**: 데이터를 구분하는 단위
  - 파티션을 한 개 이상 가짐. 하나에서 많으면 백 개 이상까지 둘 수 있음
  - 한 토픽에 모든 데이터를 넣기보다, 필요에 따라 새 토픽을 만들어 데이터를 구분해 처리함
- **파티션**: 토픽 내부에서 데이터를 논리적으로 구분하는 단위
  - 메시지 키로 파티션을 지정하면 같은 키를 가진 레코드의 순서를 보장함
  - 파티션을 적절히 나눠 순서 보장이나 컨슈머 연계 처리량 확대에 활용함
- **레코드**: 파티션에 들어가는 실제 데이터이자 메시지를 담는 가장 작은 단위
  - **offset**: 프로듀서가 보낸 레코드가 브로커에 저장될 때 받는 고유 번호
    - 컨슈머는 이 번호로 몇 번째 레코드까지 처리했는지 파악하고, 커밋으로 처리 지점을 저장함
    - 프로듀서는 offset을 지정할 수 없음. 브로커에 저장되는 순간 부여됨
  - **timestamp**: 레코드가 생산되거나 브로커에 적재된 시간
    - 스트림즈의 이벤트 타임 기준 집계나 윈도우 처리에서 활용함
  - **header**: 레코드의 특징을 담는 키값 저장소. 스키마 버전 같은 구분 정보를 넣음
  - **메시지 키와 값**: 키는 데이터를 구분하는 값, 값은 실제 처리 대상 데이터
    - 키를 지정하면 특정 파티션으로 데이터가 감. 지정하지 않으면 라운드 로빈으로 분산됨
    - 스트림즈의 코파티셔닝과 조인에서 기준이 되는 값도 이 메시지 키임
- **ISR(In-Sync-Replicas)**: 동기화가 완료된 리더와 팔로워 파티션의 묶음
  - 프로듀서의 전달 신뢰성 설정과 직접 연결됨

## 카프카 프로듀서

- **프로듀서**: 카프카 브로커로 데이터를 전달하는 애플리케이션
  - 공식 자바 라이브러리로 개발함. 자바스크립트, Go 등 서드파티 라이브러리로도 개발할 수 있음
- **파티셔너**: 메시지 키를 토대로 파티션을 정하는 클래스
  - 키가 없으면 라운드 로빈으로 분산하고, 키가 있으면 해시값으로 같은 키를 항상 같은 파티션에 보냄
  - 커스텀 클래스로 파티셔닝 로직을 바꿀 수 있음
- **어큐뮬레이터**: 레코드를 배치로 묶어 전송하는 내부 버퍼
  - 하나씩 보내는 대신 여러 개를 묶어 보내면 TCP 연결 비용을 아껴 처리 속도가 빨라짐
- **acks**: 레코드 전송 시 전달 신뢰성을 정하는 옵션
  - **0**: 전송 완료 여부를 확인하지 않음. 가장 빠르지만 신뢰성이 가장 낮음
  - **1**: 리더 파티션 저장까지만 확인. 복제 지연 중 장애가 나면 유실 가능성이 있음
  - **-1(all)**: 리더와 팔로워 파티션까지 저장을 확인. 가장 안전함
    - 이때 최소 저장 보장 파티션 개수는 min.insync.replicas로 정함
    - 안전하게 가려면 acks=all, replication.factor=3, min.insync.replicas=2 조합이 무난함
    - 브로커 여러 대가 동시에 장애 날 가능성은 낮으므로, 이 조합만으로도 높은 수준의 안전성을 얻음
- **멱등성 프로듀서**: 네트워크 장애로 같은 레코드가 중복 적재되는 상황을 막는 프로듀서
  - enable.idempotence를 켜면 동작함. 2.x까지는 기본값이 false, 3.x부터는 true
- **트랜잭션 프로듀서**: 여러 레코드를 하나의 트랜잭션으로 묶어 원자 단위로 처리하는 프로듀서
  - transactional.id를 지정해 사용함. 컨슈머도 이 레코드들을 한 번에 처리하거나 처리하지 않음

## 카프카 컨슈머

- **컨슈머**: 카프카 클러스터에 저장된 레코드를 받아 처리하는 애플리케이션
  - 데이터베이스에 저장하거나 다른 애플리케이션과 연동하는 역할로 씀
- **컨슈머 그룹**: 같은 group.id로 컨슈머를 묶어 파티션을 나눠 할당하는 단위
  - 같은 로직의 컨슈머는 같은 그룹으로 묶는 것이 일반적임
- **컨슈머 랙**: 가장 최근 레코드의 offset과 컨슈머가 처리한 offset의 차이
  - 지연 정도를 나타내므로 운영 중 반드시 모니터링해야 함
  - 모니터링 방법은 세 가지
    - kafka-consumer-groups.sh 스크립트
    - 자바 라이브러리의 metrics 메서드
    - 클러스터 외부의 모니터링 도구. 오픈소스로는 버로우를 많이 씀
- **커밋**: 마지막으로 처리한 레코드 지점을 저장하는 동작
  - 자동 커밋은 몇 초 간격으로 저장하고, 수동 커밋은 레코드별 또는 동기·비동기로 저장함
- **리밸런싱**: 컨슈머나 파티션 개수 변화로 할당을 다시 나누는 작업
  - 자주 일어나면 좋지 않지만, 일어날 때 할당을 조정해 데이터를 안전하게 이어 처리함
  - 리밸런스 리스너로 할당과 해제 시점을 관측할 수 있음
- **auto.offset.reset**: 이전 기록이 없는 컨슈머 그룹이 처음 읽을 위치를 정하는 옵션
  - **latest**: 가장 최신 데이터부터 읽음
  - **earliest**: 가장 오래된 데이터부터 읽음
- **isolation.level**: 커밋된 레코드만 읽는 트랜잭션 컨슈머로 동작하게 하는 옵션
  - 기본값은 미커밋 레코드까지 읽음. read_committed로 바꾸면 트랜잭션 단위로 처리함
  - 앞단에서 트랜잭션 프로듀서가 커밋을 어떻게 수행하는지 함께 확인해야 함

## 카프카 스트림즈

- **스트림즈**: 상태 기반과 무상태 스트림 처리를 수행하는 공식 자바 라이브러리
  - JVM 위의 코틀린, 스칼라로도 개발할 수 있지만 다른 언어에는 같은 개념이 없음
- **태스크**: 내부에서 자동 생성되어 로직을 처리하는 최소 단위
  - 스트림즈DSL이나 프로세서 API로 토폴로지를 만들면 데이터가 태스크에서 처리됨
- **프로세서**: 데이터를 가져오고 처리하고 내보내는 노드. 세 가지로 나뉨
  - 소스 프로세서, 스트림 프로세서, 싱크 프로세서
  - 노드와 노드를 잇는 흐름이 스트림임
- **세 가지 추상화**
  - **KStream**: 레코드의 흐름. 컨슈머의 poll처럼 레코드를 하나씩 처리함
  - **KTable**: 파티션의 메시지 키 기준 최신 레코드. 파티션과 일대일 태스크에서 구체화된 뷰로 활용함
  - **GlobalKTable**: 모든 파티션의 키 기준 최신 레코드
    - 코파티셔닝이 안 된 경우 KTable을 대신함
    - 데이터가 많으면 부담이 크므로 적은 용량에만 사용함
- **스트림즈DSL과 프로세서 API**
  - 대부분의 처리는 DSL에 정의되어 있어 DSL로 개발함
  - DSL에 없는 로직이 필요할 때 프로세서 API로 내려감
- **코파티셔닝**: 두 토픽의 파티션 개수와 파티셔닝 전략이 같은 상태
  - KStream, KTable 조인 같은 조합 처리의 전제 조건임

## 카프카 커넥트

- **커넥트**: 데이터 파이프라인을 반복적으로 생성할 때 쓰는 공식 도구
  - 다른 언어나 플랫폼에는 없는 카프카만의 기능임
- **소스 커넥터와 싱크 커넥터**: 실제 데이터 파이프라인을 담당함
  - 소스 커넥터: 파일이나 소스 애플리케이션의 데이터를 토픽으로 보냄. 프로듀서 역할
  - 싱크 커넥터: 토픽 데이터를 처리하거나 파일, 데이터베이스에 저장함. 컨슈머 역할
- **오픈소스 커넥터와 커스텀 커넥터**
  - 오픈소스 커넥터는 jar로 배포됨. 라이선스에 따라 무료일 수도, 유료일 수도 있음
  - 필요한 오픈소스 커넥터가 없으면 소스나 싱크 커넥터를 직접 개발해 배포함
- **태스크**: 커넥터가 아니라 태스크가 실제 데이터를 처리함
  - 처리량을 늘리려면 태스크 개수를 늘림
- **실행 모드**
  - 단일 모드: 디버깅이나 테스트에 적합한 단일 프로세스 실행
  - 분산 모드: 여러 프로세스로 태스크를 분산해 스케일 아웃함. 상용 환경의 기본

## 마무리

- 이 복습을 관통하는 흐름은 데이터가 카프카로 들어와 저장되고 처리되어 나가는 한 줄기임
  - 프로듀서가 넣고, 브로커가 저장하고, 컨슈머가 가져가고, 스트림즈가 가공하고, 커넥트가 반복 연동함
- 옵션은 대부분 기본값으로 충분하지만, 각 요소가 어떤 역할을 하는지는 정확히 알고 써야 함
- 이렇게 105강에 걸친 아파치 카프카 A to Z 커리큘럼을 마무리함
