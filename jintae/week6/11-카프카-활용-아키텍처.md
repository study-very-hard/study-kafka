# [Kafka] 섹션 11 - 카프카 활용 아키텍처

지금까지 프로듀서, 컨슈머, 스트림즈, 커넥트를 하나씩 배웠음.

이번 섹션은 실제 회사들이 이 기술을 어떤 니즈로 어떻게 도입했는지 사례로 살펴보고, 언제 무엇을 선택할지 정리함.

아키텍처를 고민할 때는 기술 자체보다 다른 회사가 어떤 문제를 어떤 구조로 풀었는지를 먼저 읽는 것이 중요함.

## 카카오 스마트 메시지 서비스

소재 최적화와 유저 타게팅으로 적합한 유저에게 광고 메시지를 개인화 전송하는 서비스임.

톡의 메시지 반응 로그가 오면 로그 프로세서인 카프카 스트림즈가 분석용 DB에 저장하고, 저장된 데이터로 타게팅을 수행함.

핵심은 대용량 스트림을 MongoDB에 저장하는 방식의 선택임. 건건이 저장하면 로직은 단순하지만 부하가 큼. 클릭 로그가 1억 건이면 짧은 시간에 인서트가 몰려 DB가 감당하기 어려움.

반대로 윈도우 시간당 데이터를 취합해 저장하면 인서트량이 크게 줄어듦. 아무리 데이터가 많아도 5분이나 10분 단위로 묶으므로 대용량 스트림을 안정적으로 적재할 수 있음.

스트림즈의 groupByKey, windowedBy, aggregate로 로그를 취합하고, map으로 레디스의 유저 데이터와 결합함. 취합에 스트림즈를 쓴 이유는 이전 레코드를 기억하는 상태 기반 처리가 필요했기 때문임.

## 넷플릭스 키스톤 프로젝트

넷플릭스는 카프카 클러스터를 두 개 둠. 대규모 수집을 담당하는 프론팅 카프카와 실제 처리를 담당하는 컨슈머 카프카임.

무비와 드라마의 노출, 사용자 클릭 데이터를 적재해 관심 여부를 판별하고, 추천 서비스로 다시 제공함.

두 클러스터를 잇는 도구가 라우터인 키스톤임. 사용자 니즈에 따라 데이터를 나눠 보냄. 배치와 장기 저장은 S3로, 실시간 분석은 엘라스틱서치로, 커스텀 스트림 처리는 다음 카프카 클러스터로 전달함.

클러스터를 두 개로 나눈 이유는 용도마다 리텐션이나 파티션 같은 브로커 옵션을 다르게 가져가야 했기 때문임. 대량 유입과 세밀한 처리의 요구사항을 분리한 구성임.

## 라인 쇼핑 플랫폼

레거시의 유연성을 개선하고 처리량 한계를 없애기 위해 카프카를 중앙에 둔 아키텍처를 적용함. 무중단 이벤트 스트림 처리의 중추로 활용함.

독특한 점은 MongoDB의 변경 데이터 캡처(CDC)를 커넥터로 붙였다는 것임. 주문 데이터가 변경되면 그 변경 이벤트를 다시 카프카로 가져와 재가공하고, 다양한 분석에 활용함.

MongoDB CDC 소스 커넥터는 오픈소스로 제공됨. 결과적으로 이벤트 기반 처리로 상품 처리 속도가 크게 빨라졌다고 함.

## 11번가 주문 결제 시스템

주문 결제 시스템의 데이터베이스 병목을 해소하기 위해 카프카 브로커를 도입함.

평상시에는 DB가 주문 결제를 감당하지만, 11절이나 설날처럼 주문량이 몰리면 DB가 병목이 됨. 카프카를 큐처럼 앞에 두어 이 병목을 완화함.

카프카를 단일 진실 공급원으로 정의해 결제와 주문 데이터를 한 곳에만 남기고, 중복과 파편화를 막음. 각 메시지를 구체화된 뷰로 구축해 배치 데이터처럼도 활용한 점이 독창적임.

## 기술별 선택 기준

사례를 바탕으로 언제 무엇을 쓸지 정리함.

카프카 커넥트는 반복적인 파이프라인이 필요할 때 분산 모드로 설치해 운영함. 되도록 오픈소스 커넥터를 쓰되, 암호화나 비즈니스 특화 처리가 필요하면 커스텀 커넥터를 개발함. REST API로 동작하므로 웹 화면과 함께 운영하는 것이 좋음.

카프카 스트림즈는 상태 기반 처리가 강점임. 집계나 윈도우 처리처럼 이전 레코드를 기억해야 하는 대용량 처리에 적합함. 커넥트는 태생이 컨슈머 기반의 건건이 처리라 상태 기반 처리에 약하고, 스트림즈는 상태 기반과 무상태 처리를 모두 다룸.

반복 파이프라인도 아니고 상태 기반 처리도 아니라면 컨슈머와 프로듀서를 고려함. 특히 단 하나만 만들면 되는 단일성 파이프라인은 굳이 커넥트로 만들 필요가 없음.

전체 흐름으로 보면 프로듀서나 소스 커넥터가 데이터를 넣고, 스트림즈가 토픽 데이터를 가공해 다시 넣고, 커넥트가 반복 파이프라인으로 외부와 연동하고, 컨슈머가 단일성 처리를 맡음.

참고로 커넥트와 스트림즈는 아파치 카프카의 고유 기능이라 자바 라이브러리로만 개발함. 컨슈머와 프로듀서는 다른 언어 구현도 많지만, 카프카의 모든 기능을 안전하게 쓰려면 공식 자바 라이브러리가 가장 낫다고 강조함.

## 마무리

사례를 관통하는 공통점은 데이터베이스의 처리 능력을 넘는 유입을 카프카로 완충했다는 것임.

카카오는 1억 건 인서트를, 11번가는 주문 폭증을, 라인은 처리량 한계를 카프카 앞단에서 흡수했음.

카프카가 대량 유입을 받아내고, 뒤에서 스트림즈로 취합하거나 커넥트로 나눠 내보내 DB 부하를 고르게 만듦. 카프카를 왜 도입하는가의 실전 답이 바로 이 완충 구조임.

그래서 아키텍처를 볼 때는 이 회사의 병목이 어디였고 카프카가 그 사이에서 무엇을 흡수했는지를 읽으면 도입 이유가 보임.
