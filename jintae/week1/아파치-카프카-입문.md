# [Kafka] 아파치 카프카 입문 — for beginners 정리

데브원영의 무료 강의 [아파치 카프카 for beginners] 15강 정리.

유료 강의(A to Z)에 들어가기 전, 카프카의 전체 지도를 그리는 과정임.

## 카프카는 왜 쓰는가

| 이유 | 근거 |
|---|---|
| 높은 처리량 | 파티션 병렬 처리, 배치 전송, 브로커가 컨슈머 상태를 추적하지 않는 경량 설계 |
| 확장성과 장애 허용 | 브로커 수평 확장, 복제/ISR 기반 리더 승격, 컨슈머 리밸런싱에 의한 무중단 운영 |
| 삭제되지 않는 로그 | 소비 후에도 데이터 유지. 다중 소비·재처리 가능 |

소스와 타깃을 직접 연결하면 파이프라인이 N×M개로 불어나고 장애가 전파됨.

카프카를 가운데 두면 모든 데이터가 카프카를 거쳐 흐르고, 소스와 타깃의 결합이 끊어짐.

## 데이터 모델 — 토픽, 파티션, 오프셋

```
Topic (테이블에 해당하는 논리 단위)
 └─ Partition (병렬 처리 단위, append-only 로그)
     └─ Offset (파티션에 누적되는 순번)
```

레코드는 토픽 + 키 + 값으로 구성됨.

파티션 배정 공식은 `partition = hash(key) % 파티션 수`.

같은 키는 항상 같은 파티션으로 가므로 키 단위 순서가 보장됨.

뒤집으면, 파티션 수를 바꾸는 순간 키-파티션 매핑이 무너짐.

키 기반 토픽은 초기 설계에서 파티션 수에 여유를 둬야 함.

파티션은 늘릴 수만 있고 줄일 수 없음.

그리고 카프카에서 소비와 삭제는 무관함.

삭제는 리텐션(기간·용량)만 담당하고, "모두가 소비하면 삭제" 같은 로직 자체가 없음.

메시지별 상태를 추적하지 않는 이 설계가 고성능과 재사용성의 원천임.

## 안정성 — 브로커, 복제, ISR

```
              Broker 1       Broker 2       Broker 3
Partition-0   [Leader]       Follower       Follower
Partition-1   Follower       [Leader]       Follower
Partition-2   Follower       Follower       [Leader]
```

파티션은 분할(성능), 복제는 사본(안전).

별개의 개념임.

읽기·쓰기는 리더가 전담하고, 팔로워는 복제 후 대기함.

리더 장애 시 ISR(동기화된 복제본 집합) 안의 팔로워가 승격됨.

acks 옵션은 쓰기 확인 수준을 정함.

`0`은 무확인, `1`은 리더 저장 확인, `all`은 ISR 저장 확인.

유실 방지의 실전 조합은 `acks=all` + `min.insync.replicas=2`.

브로커 3대가 최소 권장인 이유는 1대 장애를 견디며 acks=all 쓰기를 유지하고 과반수 투표가 성립하는 최소 구성이기 때문임.

## 클라이언트 — 프로듀서와 컨슈머

프로듀서는 레코드를 배치로 모아 전송함.

처리량 확보의 핵심임.

컨슈머는 poll 루프 기반의 pull 방식으로 가져감.

```
동일 그룹 = 분담 소비 (파티션당 1명 전담, 큐처럼 동작)      → 처리량 확장
상이 그룹 = 독립 소비 (그룹마다 전체 수신, pub/sub처럼 동작) → 용도 확장
```

유효 컨슈머 수의 상한은 파티션 수.

초과분은 유휴 상태가 됨.

커밋은 소비 위치를 내부 토픽 `__consumer_offsets`에 기록하는 것.

키가 (그룹, 토픽, 파티션)이므로 그룹별로 완전히 독립적임.

`auto.offset.reset=earliest`는 커밋이 없을 때만 적용되고, 커밋이 있으면 무조건 이어서 읽음.

## 모니터링 — 컨슈머 랙

```
LAG = LOG-END-OFFSET(생산 위치) − CURRENT-OFFSET(소비 위치)
```

| 관찰 | 진단 |
|---|---|
| LEO 정체 | 프로듀서/상류 장애 |
| CURRENT 정체 (LEO 증가 중) | 컨슈머 정지 |
| LAG 지속 증가 | 처리량 부족 → 증설 검토 |
| LAG이 리텐션의 절반 도달 | 미소비 데이터 유실 임박 |

판단 기준은 절대값이 아니라 추세임.

감소 중인 랙 5000이 증가 중인 랙 700보다 건강함.

버로우(Burrow)가 이 슬라이딩 윈도우 방식의 자동 판정을 제공함.

## 생태계 — 스트림즈와 커넥트

스트림즈는 카프카 → 처리 → 카프카를 담당하는 자바 라이브러리.

별도 클러스터가 필요 없음.

KStream은 전체 이벤트, KTable은 키별 최신값, GlobalKTable은 전체 복제본.

상태는 로컬 RocksDB에 두고 체인지로그 토픽으로 백업함.

로컬의 속도와 카프카의 내구성을 결합한 구조임.

커넥트는 설정만으로 구성하는 반복 파이프라인.

Source(외부→카프카)와 Sink(카프카→외부)로 나뉨.

REST API(8083)는 제어 채널일 뿐이고 데이터는 별도 경로로 이동함.

CDC(Debezium)는 폴링 대신 DB 변경 로그를 구독해 삭제 감지·순서 보존·DB 부하 최소화를 얻음.

## 아키텍처와 미래

람다 아키텍처는 배치 + 스피드 이중 레이어.

이중 구현·이중 배포·결과 불일치가 문제였음.

카파 아키텍처는 스트림으로 단일화함.

로그 재생(replay)이 배치의 재계산을 대체하므로 배치 레이어의 존재 이유가 사라짐.

스트리밍 데이터 레이크는 티어드 스토리지 기반 무한 보관으로 경유지와 저장소를 통합하려는 방향임.

KRaft는 주키퍼를 제거하고 메타데이터를 카프카 자체 Raft 합의로 관리함(4.0에서 주키퍼 완전 삭제).

| 모델 | 로그(소비 후 유지) | 큐(소비 시 삭제) | 인메모리 큐 | 관리형 큐 |

| 용도 | 데이터 파이프라인 | 복잡한 작업 분배 | 경량 큐 | 단순 비동기 작업 |

## 핵심 명제 10

1. 파티션 = 성능(분할), 복제 = 안전(사본)
2. 오프셋 = 누적 순번. 소비 = 삭제가 아닌 책갈피 이동
3. 동일 키 → 동일 파티션 → 파티션 수 변경은 신중히
4. 리더 승격 자격은 ISR 내 팔로워로 한정
5. 동일 그룹은 분담, 상이 그룹은 독립 소비
6. 랙 판단 기준은 절대값이 아닌 추세
7. 랙이 리텐션 초과 시 미소비 데이터 유실
8. 스트림즈 상태 = 로컬(속도) + 체인지로그(내구성)
9. 커넥트의 REST = 제어 채널. 데이터는 별도 경로
10. 배치의 존재 이유는 재계산 — 로그 재생이 이를 대체(카파)
