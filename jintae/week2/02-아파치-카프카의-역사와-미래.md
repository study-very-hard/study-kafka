# [Kafka] 섹션 2 - 아파치 카프카의 역사와 미래

카프카는 2011년 링크드인에서 태어남.

어떤 문제를 풀려고 만들어졌는지를 알면, 카프카를 언제 어떻게 써야 하는지가 따라옴.

## 카프카의 탄생

데이터를 생성하는 소스 애플리케이션과 최종 적재되는 타깃 애플리케이션은 연결되어야 함.

초기에는 소스→타깃 1:1 단방향 연동 코드로 충분했음.

문제는 규모.

소스 N개, 타깃 M개가 되는 순간 파이프라인은 **N×M개**로 불어남.

N=10, M=10이면 연결선이 100개.

더 심각한 것은 장애 전파.

소스나 타깃 하나가 죽으면 직접 연동된 애플리케이션들이 동시에 흔들림.

링크드인 데이터팀은 기존 상용 프레임워크와 오픈소스(메시징 플랫폼, ETL 툴)를 조합해 이 파편화를 풀려 했지만 번번이 실패했고, 결국 직접 만듦.

그것이 아파치 카프카임.

핵심 아이디어는 **Unified Log**.

애플리케이션끼리 직접 연결하지 않고 데이터를 한 곳에 모음.

소스는 어느 타깃으로 보낼지 고민하지 않고 카프카에 넣기만 하면 되고, 타깃은 카프카만 바라봄.

파이프라인은 N+M개로 줄고, 커플링이 끊어지면서 장애 전파 범위도 줄어듦.

새 타깃을 추가하는 비용이 N이 아니라 1이 되는 구조적 이점이 큼.

### 내부 구조는 큐, 그러나 삭제하지 않는 큐

- **토픽**: RDBMS의 테이블 같은 데이터 구분 단위
- **파티션**: 토픽당 1개 이상. 프로듀서가 보낸 레코드 하나는 여러 파티션 중 **하나에만** 적재됨
- 파티션의 동작은 FIFO 큐와 같음. 먼저 들어간 레코드를 컨슈머가 먼저 가져감

일반 큐와의 결정적 차이.

**컨슈머가 가져가도 데이터가 삭제되지 않음.**

컨슈머는 어디까지 읽었는지를 커밋으로 기록할 뿐임.

이 성질이 카프카 활용의 대부분을 결정함.

## 데이터 파이프라인으로 적합한 4가지 이유

| 특징 | 핵심 메커니즘 |
|---|---|
| 높은 처리량 | 배치 묶음 전송 + 파티션 단위 병렬 처리 |
| 확장성 | 브로커 스케일아웃/스케일인, 무중단 |
| 영속성 | 디스크 저장 + OS 페이지 캐시 |
| 고가용성 | 복제로 여러 브로커에 분산 저장 |

**높은 처리량.**

카프카는 보낼 때도 받을 때도 데이터를 묶어서 전송함.

초당 1건이면 의미 없지만 초당 1,000건이면 네트워크 연결 비용이 급증함.

같은 양을 보낼 때 통신 횟수를 줄이면 같은 시간에 더 많이 보낼 수 있음.

여기에 파티션 하나당 컨슈머 하나를 붙여 병렬 처리함.

처리 속도를 올리는 스케일업 대신, 파티션과 컨슈머 개수를 함께 늘리는 스케일아웃으로 처리량이 선형으로 늘어남.

**확장성.**

파이프라인에 데이터가 얼마나 들어올지는 예측할 수 없음.

하루 1,000건 들어오던 로그가 이벤트 하나로 100만 건이 됨.

데이터가 적을 때는 브로커를 최소로 운영하다가 많아지면 늘리고(스케일아웃), 줄면 뺌(스케일인).

이 과정이 무중단이라 24시간 365일 데이터를 처리하는 커머스·은행에서도 쓸 수 있음.

**영속성.**

카프카는 데이터를 메모리가 아닌 파일 시스템에 저장함.

느릴 것 같지만 OS의 **페이지 캐시**를 활용함.

한 번 읽은 파일 내용은 메모리에 남아 재사용되므로 디스크 기반인데도 처리량이 높음.

속도(메모리)와 안정성(디스크)을 동시에 잡았고, 브로커가 급작스럽게 죽어도 재시작하면 디스크의 데이터로 다시 처리할 수 있음.

**고가용성.**

프로듀서가 보낸 데이터를 한 브로커에만 저장하지 않고 다른 브로커에도 복제함.

한 대가 죽어도 남은 복제본으로 계속 처리함.

서버 랙 단위, 클라우드 리전 단위 장애까지 대비하는 옵션도 준비되어 있음.

## 빅데이터 아키텍처의 변천

### 초기 빅데이터 플랫폼

원천 데이터 → 파생 데이터 → 서빙 데이터를 엔드 투 엔드 배치로 모으는 구조였음.

유연하지 못했고, 실시간 인사이트를 서비스에 전달하지 못함.

가공이 반복되며 데이터 히스토리 파악이 어려워지고 데이터 거버넌스가 무너짐.

### 람다 아키텍처

| 레이어 | 역할 |
|---|---|
| 배치 레이어 | 배치 데이터를 모아 시간 단위로 일괄 처리 |
| 스피드 레이어 | 원천 데이터를 실시간 분석. **카프카가 여기 있음** |
| 서빙 레이어 | 가공된 데이터를 사용자·애플리케이션에 제공 |

명확한 분리가 장점이자 단점임.

같은 데이터를 처리하는 로직이 배치용(하둡 맵리듀스)과 실시간용(카프카)으로 **두 벌** 존재해야 함.

언어와 프레임워크가 갈라지며 로직이 파편화됨.

트위터가 서밍버드로 한 로직을 양쪽에 추상화하려 했지만, 배포도 두 번 디버깅도 두 번이라는 문제는 남음.

### 카파 아키텍처

카프카를 처음 고안한 제이 크렙스(전 링크드인, 현 컨플루언트 CEO)가 제안함.

**배치 레이어를 제거**하고 모든 데이터를 스피드 레이어에서 처리함.

전제가 있음.

스트림 데이터를 배치처럼 쓸 수 있어야 함.

열쇠는 로그의 표현 방식임.

배치 데이터를 매 시점 전체 백업(스냅샷)으로 표현하는 대신, **변환 기록 로그(change log)** 를 시간순으로 남기면 모든 시점의 스냅샷을 저장하지 않고도 배치 데이터를 표현할 수 있음.

로그를 되감아 재생하면 임의 시점의 상태를 복원할 수 있기 때문임.

카프카는 레코드마다 타임스탬프를 남김.

그래서 특정 기간의 스트림 데이터를 **구체화된 뷰(Materialized View)** 로 가져와 배치처럼 일괄 처리할 수 있음.

2021년 신입생 목록이 필요하면 1월 1일부터 12월 31일까지의 스트림을 뷰로 만들어 처리하면 됨.

| 배치 데이터 | 스트림 데이터 |
|---|---|
| 한정된(bounded) 데이터 | 무한(unbounded) 데이터 |
| 분·시간·일 단위 지연 | 분 단위 이하 지연 |
| 복잡한 키 조인 | 단순한 키 조인 |

다만 카파가 만능은 아님.

로직이 바뀌면 스트림 로그를 처음부터 재소비해야 하고, 대용량 데이터셋을 넘나드는 복잡한 조인은 여전히 배치가 유리함.

실무에서는 실시간 경로만 카파식으로 가져가고 무거운 정산·분석은 배치로 남기는 혼합 구성이 흔함.

### 스트리밍 데이터 레이크

2020년 카프카 서밋에서 제이 크렙스가 한 발 더 나아감.

**서빙 레이어까지 제거**함.

스피드 레이어(카프카)가 분석을 마친 대용량 데이터를 오래 저장할 수 있다면, 서빙 레이어와 스피드 레이어를 이중으로 관리할 이유가 없다는 것임.

걸림돌은 저장 비용이었음.

자주 접근하지 않는 데이터까지 비싼 브로커의 메모리·디스크에 둘 수는 없음.

해법이 **티어드 스토리지**.

자주 쓰는 데이터만 브로커에 두고, 나머지는 저렴한 오브젝트 스토리지로 내림.

강의 시점(2022년)에는 오픈소스 카프카에 없던 기능인데, 이후 실제로 들어옴.

KIP-405가 카프카 3.6에서 얼리 액세스로 도입됐고 3.9에서 프로덕션 준비가 완료됨.

강의가 예견한 미래가 현실이 된 셈임.
