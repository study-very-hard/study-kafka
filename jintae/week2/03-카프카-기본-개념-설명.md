# [Kafka] 섹션 3 - 카프카 기본 개념

카프카의 뼈대를 세우는 섹션.

브로커가 무엇을 하는지, 데이터가 어디에 어떻게 저장되고 언제 사라지는지, 복제가 어떻게 장애를 버티는지.

이후 프로듀서·컨슈머·스트림즈가 전부 이 위에 서 있음.

## 카프카 생태계

가운데에 카프카 클러스터가 있고, 목적별로 토픽을 만듦.

**프로듀서**가 토픽에 데이터를 넣고 **컨슈머**가 가져감.

토픽의 데이터를 처리해 다시 토픽에 넣고 싶으면 **스트림즈**를 씀.

반복적인 데이터 파이프라인은 **커넥트**가 담당함.

커넥트의 소스 커넥터는 프로듀서 역할(DB → 토픽), 싱크 커넥터는 컨슈머 역할(토픽 → 타깃)을 함.

그냥 프로듀서·컨슈머로 개발하면 되지 않나 싶지만, 커넥트는 클러스터로 운영되며 REST API에 JSON 설정만 던지면 파이프라인이 카처럼 반복 생성됨.

파이프라인마다 코드 작성·빌드·배포를 반복하는 것과는 운영 효율이 다름.

하나 짚을 것.

프로듀서, 컨슈머, 스트림즈, 커넥트는 모두 **오픈소스 아파치 카프카에 포함된 공식 자바 라이브러리**임.

다른 언어 라이브러리는 서드파티라 릴리즈가 별개로 돌고, 모든 기능이 제공된다는 보장이 없음.

## 브로커, 클러스터, 주키퍼

**브로커**는 클라이언트가 데이터를 주고받을 때 반드시 통신하는 프로세스.

서버 1대당 브로커 1개가 원칙임.

1대로도 동작하지만 데이터를 안전하게 보관하려면 **3대 이상을 클러스터로** 묶음.

한 대에만 저장된 데이터는 그 브로커가 죽는 순간 쓸 수 없기 때문임.

주키퍼는 클러스터의 메타데이터(브로커 멤버십, 토픽 정보, 컨트롤러 선출)를 관리함.

하나의 주키퍼 앙상블에 z노드를 나눠 여러 카프카 클러스터를 연결할 수도 있음.

다만 앙상블을 공유하면 리소스는 아끼지만 앙상블 장애가 모든 클러스터로 번짐.

강의 시점에는 "3.0부터 주키퍼 없이 운영 가능하지만 아직 미완성"이었음.

지금은 상황이 다름.

KRaft 모드가 3.3에서 프로덕션 레디가 됐고, **4.0에서 주키퍼 지원이 완전히 제거됨.**

신규 클러스터에 주키퍼라는 선택지는 이제 없음.

## 브로커의 네 가지 역할

**컨트롤러.**

브로커 중 한 대가 맡음.

다른 브로커들의 상태를 체크하고, 브로커가 클러스터에서 빠지면 그 브로커에 있던 리더 파티션을 재분배함.

컨트롤러 자신이 죽으면 다른 브로커가 이어받음.

**데이터 삭제.**

오직 브로커만 삭제할 수 있음.

컨슈머도 프로듀서도 삭제를 요청할 수 없음.

삭제 단위는 파일 단위인 로그 세그먼트라서, 특정 레코드만 핀셋으로 집어 지우는 것은 불가능함.

**컨슈머 오프셋 저장.**

컨슈머가 어디까지 처리했는지(커밋)를 내부 토픽 `__consumer_offsets`에 저장함.

컨슈머가 재시작해도 이어서 읽을 수 있는 이유임.

**그룹 코디네이터.**

컨슈머 그룹의 상태를 체크하고 파티션을 컨슈머에 분배함.

컨슈머가 빠지면 남은 컨슈머에게 파티션을 재할당함.

이 과정이 **리밸런스**임.

컨트롤러와 코디네이터는 헷갈리기 쉬움.

|           | 컨트롤러                 | 그룹 코디네이터         |
| --------- | ------------------------ | ----------------------- |
| 관리 대상 | 브로커                   | 컨슈머 그룹             |
| 장애 시   | 리더 파티션 재분배(승급) | 파티션 재할당(리밸런스) |

브로커 쪽 장애는 컨트롤러가, 컨슈머 쪽 장애는 코디네이터가 수습함.

## 데이터는 어떻게 저장되는가: 로그와 세그먼트

브로커는 `config/server.properties`의 log.dir 경로 아래 `토픽명-파티션번호` 디렉토리에 데이터를 저장함.

안에는 세 종류의 파일이 있음.

- **.log**: 메시지와 메타데이터
- **.index**: 오프셋 → 파일 내 위치 색인
- **.timeindex**: 타임스탬프 기준 색인

파티션의 로그는 하나의 파일이 아니라 **세그먼트** 단위로 쪼개짐.

기준은 둘.

log.segment.bytes(기본 1GB)에 도달하거나, log.roll.ms(기본 7일)가 지나면 다음 파일로 넘어감.

파일 이름은 그 세그먼트의 첫 오프셋임.
`10.log`라면 오프셋 10부터 들어 있음.

가장 마지막, 지금 쓰기가 일어나는 파일이 **액티브 세그먼트**.

액티브 세그먼트는 삭제 대상에서 제외됨.

세그먼트로 쪼개는 이유는 삭제 때문임.

오래된 데이터를 지울 때 파일째 지우면 끝남.

거대한 단일 파일이었다면 앞부분만 지우기 위해 전체를 다시 써야 함.

## 데이터는 언제 사라지는가: cleanup.policy

토픽 단위로 두 가지 정책 중 선택함.

**delete(기본).**

retention.ms(기본 7일) 또는 retention.bytes(기본 -1)를 넘긴 세그먼트를 통째로 지움.

브로커가 5분 간격(log.retention.check.interval.ms)으로 검사함.

리텐션은 디스크 용량과 함께 계산해야 함.

하루 1TB 유입에 7일 보존이면 7TB인데, 여기에 **복제 개수까지 곱해야** 실제 사용량임(복제 3이면 21TB).

실무에서 3일 설정이 흔한 이유가 재미있음.

금요일 밤 장애가 나도 주말을 넘겨 월요일에 데이터를 처음부터 재처리할 수 있는 기간이기 때문임.

**compact.**

zip 압축이 아님.

**메시지 키별로 가장 최신 레코드만 남기고 과거를 지우는** 정책임.

키-밸류 스토어처럼 최종 상태만 필요할 때 씀.
`__consumer_offsets` 자체가 compact 토픽임.
같은 컨슈머 그룹의 과거 커밋은 필요 없기 때문.

압축 시점은 min.cleanable.dirty.ratio가 정함.

압축이 끝난 영역(테일, 클린 로그)과 아직인 영역(헤드, 더티 로그)의 레코드 비율임.
0.9처럼 크게 잡으면 한 번에 많이 지워 압축 효율은 좋지만 그때까지 용량을 차지함.
0.1처럼 작게 잡으면 최신 상태는 잘 유지되지만 압축이 잦아 브로커에 부담이 됨.

레코드 단위 삭제도 수정도 불가능하므로, 잘못된 데이터는 들어가기 전에 막아야 함.

카프카는 적재 시 검증을 해주지 않음.

프로듀서의 send() 전에, 그리고 컨슈머의 처리 로직에서 각자 검증해야 함.

## 복제와 ISR

복제는 카프카를 장애 허용 시스템으로 만드는 원동력.

단위는 토픽이 아니라 **파티션**임.

복제 개수(replication factor)는 최소 1(복제 없음), 최대 브로커 수이며 상용에서는 2~3을 씀.

복제된 파티션은 **리더**와 **팔로워**로 나뉨.

프로듀서와 컨슈머는 **리더 파티션과만 통신**함.

팔로워는 리더의 오프셋과 자기 오프셋을 비교해 차이만큼 데이터를 가져감(pull 방식).

브로커가 다운되면 팔로워 중 하나가 리더로 **승급**해 처리가 이어짐.

비용도 있음.

1GB를 보내면 복제 3에서는 3GB가 저장됨.

디스크를 쓰는 대신 가용성을 사는 트레이드오프임.

그래서 데이터 특성별로 다르게 설정함.

GPS 메트릭처럼 1분에 60건 중 2~3건 빠져도 무방한 데이터는 1, 일반적으로는 2, 금융 정보처럼 유실 불가면 3.

**ISR(In-Sync-Replicas)** 은 리더와 팔로워의 오프셋이 일치하는, 즉 복제가 완료된 복제본 집합임.

복제는 리더 적재 후에 따라가는 구조라 팔로워가 순간적으로 뒤처지는 구간이 항상 존재함.

문제는 그 순간 리더가 죽었을 때임.

ISR이 아닌 팔로워를 리더로 올리면 미복제 데이터가 유실됨.

이 선택이 `unclean.leader.election.enable`임.

| 설정         | 의미                                                  |
| ------------ | ----------------------------------------------------- |
| true         | 유실 감수. 미복제 팔로워라도 승급시켜 무중단 처리     |
| false (기본) | 유실 불가. 리더 브로커가 복구될 때까지 해당 토픽 중단 |

가용성과 일관성 중 무엇을 버릴지 토픽 단위로 정하는 스위치임.

참고로 컨슈머는 애초에 ISR 전체에 복제 완료된 지점(하이 워터마크)까지만 읽을 수 있어서, "읽은 데이터가 사라지는" 일은 발생하지 않음.

## 토픽과 파티션 운영

토픽을 만들면 리더 파티션이 0번 브로커부터 **라운드 로빈**으로 분산 배치됨.

클라이언트는 리더와 통신하므로, 리더가 분산되어야 특정 브로커에 통신이 몰리는 핫스팟이 없음.

장애와 재시작을 거치며 리더가 한 브로커에 쏠리면 `kafka-reassign-partitions.sh`로 재분배함.

처리량 설계의 기본 공식.

파티션과 컨슈머는 1:1로 매칭되므로, 컨슈머만 늘려서는 소용없고 **파티션과 컨슈머를 함께** 늘려야 함.

프로듀서가 초당 10건을 보내고 컨슈머가 초당 1건을 처리하면 지연(컨슈머 랙)이 쌓임.

최소 파티션 10, 컨슈머 10이 답이지만, 실무에서는 20/20처럼 여유를 두고 잡음.

단, 여유에도 이유가 있어야 함.

**파티션 개수는 줄일 수 없음.**

세그먼트로 저장된 데이터를 취합·재정렬해야 해서 지원되지 않고(KIP-694도 중단됨), 토픽 삭제 후 재생성이 유일한 방법임.

게다가 파티션을 늘리면 키 해시 매핑이 바뀌어 그 시점부터 키 단위 순서 보장이 깨짐.

늘리는 것도 신중해야 함.

## 레코드

레코드는 다섯 요소로 구성됨.

| 필드      | 내용                                                                                               |
| --------- | -------------------------------------------------------------------------------------------------- |
| timestamp | 스트림 프로세싱용 시간. 기본 CreateTime, 옵션으로 LogAppendTime (토픽 단위 message.timestamp.type) |
| offset    | 브로커 적재 시 지정. 파티션별 고유, 0부터 1씩 증가                                                 |
| headers   | 스키마 버전·포맷 등 참고용 key/value 메타데이터                                                    |
| key       | 파티셔닝(분류)용. 필수 아님                                                                        |
| value     | 실질적으로 처리할 데이터                                                                           |

메시지 키가 파티셔닝을 결정함.

키가 null이면 라운드 로빈으로 균등하게 들어가고, 키가 있으면 해시값으로 특정 파티션에 고정 매핑됨.

같은 키 → 같은 파티션 → 파티션 내 FIFO이므로 **키 단위 순서가 보장됨**.

순서가 필요하면 키를 넣고, 전부 병렬로 처리하고 싶으면 키를 비움.

메시지 값의 직렬화 포맷은 사용자가 정함.

주의할 점은 브로커에 저장된 값이 어떤 포맷인지 컨슈머가 알 방법이 없다는 것.

컨슈머는 역직렬화 포맷을 미리 알아야 함.

문자열(JSON)이 편해서 흔히 쓰이지만 모든 타입을 문자열로 다루는 공간 낭비가 있음.

## 토픽 이름은 데이터의 얼굴

제약 조건부터.

영어 대소문자·숫자·`.`·`_`·`-` 조합, 249자 미만, 내부 토픽(`__consumer_offsets`, `__transaction_state`)과 동일한 이름은 불가함.

마침표와 언더바를 섞으면 WARNING이 뜸.

메트릭 이름에서 `.`이 `_`로 치환되어 `my.topic`과 `my_topic`의 지표가 충돌하기 때문임.

`test-20210204`, `abcd`, `bigdata` 같은 이름은 누가 왜 만들었는지 알 수 없는 기술 부채가 됨.
카프카는 **토픽 이름 변경을 지원하지 않음.**

삭제 후 재생성뿐임.

그래서 규칙을 사전에 정의하고 따르게 하는 것이 중요함.

| 템플릿                                     | 예시                                       |
| ------------------------------------------ | ------------------------------------------ |
| `<환경>.<팀>.<앱>.<메시지-타입>`           | prd.marketing-team.sms-platform.json       |
| `<프로젝트>.<서비스>.<환경>.<이벤트>`      | commerce.payment.prd.notification          |
| `<환경>.<서비스>.<JIRA번호>.<메시지-타입>` | dev.email-sender.jira-1234.email-vo-custom |
| `<클러스터>.<환경>.<서비스>.<메시지-타입>` | aws-kafka.live.marketing-platform.json     |

환경을 붙이는 이유가 실용적임.

데브와 프로드 클러스터에서 같은 토픽 이름을 쓰면, 애플리케이션이 실수로 프로드 부트스트랩 서버를 바라봐도 그대로 동작해 버림.

이름에 환경을 박으면 이런 사고를 줄일 수 있음.

메시지 타입은 컨슈머가 알아야 할 역직렬화 포맷을 이름에서 드러냄.

## 클라이언트는 리더를 어떻게 찾는가: 메타데이터

클라이언트는 반드시 리더 파티션과 통신해야 함.

그래서 데이터를 주고받기 전에 브로커로부터 **메타데이터**를 요청하고 응답으로 받음.

메타데이터에는 내가 통신할 리더 파티션이 어느 브로커에 있는지가 담겨 있고, 클라이언트는 이를 근거로 해당 브로커와 직접 통신함.

리더가 없는 브로커와는 통신할 이유가 없으므로, 메타데이터 수신이 통신의 기본 전제임.

- **metadata.max.age.ms**: 메타데이터를 강제로 리프래시하는 간격. 기본 5분
- **metadata.max.idle.ms**: 유휴 상태의 프로듀서가 메타데이터를 캐시에 유지하는 기간. 기본 5분

부트스트랩 서버의 정체도 여기서 풀림.

bootstrap.servers는 **최초 연결용 입구**일 뿐, 한 대에만 붙으면 메타데이터 응답으로 클러스터 전체를 알게 됨.

2~3개를 적는 관례는 첫 브로커가 죽어 있을 때를 대비한 가용성 장치임.

문제는 캐시가 낡았을 때임.

리더가 승급으로 옮겨졌는데 클라이언트가 옛 메타데이터로 리더가 없는 브로커에 요청하면 **LEADER_NOT_AVAILABLE** 익셉션이 발생함.

다만 이 에러는 발생 자체보다 **지속 여부**로 판단해야 함.

리더 교체 직후 잠깐 나오는 것은 자연스러운 현상이고, 클라이언트가 메타데이터를 갱신해 재시도하면서 스스로 회복함.

계속 나온다면 메타데이터 리프래시 간격과 클라이언트의 메타데이터 상태를 의심해야 함.

## 정리

- 생태계: 프로듀서·컨슈머·스트림즈·커넥트, 전부 공식 자바 라이브러리
- 브로커는 3대 이상 클러스터로. 주키퍼는 KRaft로 대체되어 4.0에서 제거됨
- 브로커의 역할: 컨트롤러, 세그먼트 단위 삭제, 오프셋 저장, 코디네이터
- 저장은 세그먼트 파일, 삭제는 delete(리텐션)와 compact(키별 최신) 정책
- 복제는 파티션 단위 리더/팔로워, ISR과 unclean 옵션이 유실·중단의 갈림길
- 파티션은 늘릴 수만 있음. 처리량 설계는 파티션·컨슈머를 함께
- 레코드의 키가 순서를, 값의 포맷은 컨슈머와의 약속이 결정함
- 클라이언트는 메타데이터로 리더를 찾음. LEADER_NOT_AVAILABLE은 지속 여부로 판단
- 토픽 이름은 변경 불가. 규칙을 정하고 시스템으로 강제할 것
