# 아파치 카프카란?

Apache Kafka는 **대용량 데이터를 빠르고 안정적으로 전달하기 위한 분산 이벤트 스트리밍 플랫폼**이다.

쉽게 말하면 서비스에서 발생하는 이벤트(주문 생성, 결제 완료, 회원 가입 등)를 저장하고, 필요한 여러 시스템이 동시에 가져가서 처리할 수 있도록 해주는 메시지 브로커이다. (정확히는 이후 강의에서 이야기하지만 이벤트 브로커이다)

- 빅데이터 처리의 핵심
- 실시간 데이터 프로세싱에서 카프카의 역할은 매우 중요

### 특징

- 높은 처리량(High Throughput)
- 낮은 지연 시간(Low Latency)
- 장애에 강한 분산 구조
- 데이터를 일정 기간 저장(Retention)
- 여러 Consumer가 같은 데이터를 각각 소비 가능

# 토픽이란?

**Topic은 메시지를 저장하는 논리적인 공간**이다.

Producer는 Topic에 데이터를 보내고(Publish), Consumer는 Topic에서 데이터를 읽는다(Consume).

예를 들어

- click-log
- order-created
- payment-completed
- user-signup

처럼 이벤트 종류별로 Topic을 분리한다.

> 데이터베이스의 테이블과 비슷한 개념이지만, 데이터를 저장하기 위한 목적이 아니라 이벤트를 저장하는 공간이다.
>

# 브로커, 복제, ISR

### 브로커(Broker)

Kafka 서버 한 대를 Broker라고 한다.

Broker 여러 대가 모여 Kafka Cluster를 구성한다.

### 복제(Replication)

Topic의 데이터를 여러 Broker에 복사해 두는 기능이다.

목적은 장애 발생 시 데이터 유실을 막기 위함이다.

```jsx
Broker1 (Leader)
Broker2 (Follower)
Broker3 (Follower)
```

Leader가 데이터를 받고, Follower들이 동일한 데이터를 복제한다.

### ISR(In-Sync Replicas)

Leader와 동일한 데이터를 정상적으로 가지고 있는 Replica들의 집합이다.

Leader가 장애가 발생하면 ISR에 속한 Broker 중 하나가 새로운 Leader가 된다.

즉, **ISR은 장애 발생 시 Leader가 될 수 있는 Broker 목록**이라고 이해하면 된다.

## 파티셔너란(Partitioner)?

Partitioner는 **Producer가 어떤 Partition에 메시지를 저장할지 결정하는 역할**을 한다.

기본적으로

- Key가 있으면 같은 Key는 같은 Partition으로 전송
- Key가 없으면 Round Robin 방식으로 분산

```jsx
user1 → Partition0
user1 → Partition0
user2 → Partition2
```

같은 Key는 항상 같은 Partition으로 가므로 **메시지 순서(Ordering)**를 보장할 수 있다.

## 컨슈머 랙(Consumer Lag)이란?

Consumer Lag은 **Producer가 저장한 메시지와 Consumer가 읽은 메시지의 차이**를 의미한다.

```jsx
Producer Offset : 1200
Consumer Offset : 1180

Lag = 20
```

Lag가 커질수록

- Consumer 처리 속도가 느리거나
- 장애가 발생했거나
- 처리량이 부족할 가능성이 있다.

Kafka 운영에서 가장 중요한 모니터링 지표 중 하나이다.

## 컨슈머 랙 모니터링 애플리케이션, 카프카 버로우(Burrow)

Burrow는 LinkedIn에서 만든 **Kafka Consumer Lag 모니터링 도구**이다.

단순히 Lag 수치만 보여주는 것이 아니라,

Consumer가 정상적으로 동작하는지 상태까지 판단해 준다.

주요 기능

- Consumer Lag 확인
- Consumer 상태 확인
- REST API 제공
- 여러 Consumer Group 모니터링

운영 환경에서 Consumer 장애를 빠르게 감지하는 데 활용된다.

## 카프카, 레빗엠큐, 레디스 큐의 차이점

| 항목 | Kafka | RabbitMQ | Redis Queue |
| --- | --- | --- | --- |
| 목적 | 이벤트 스트리밍 | 메시지 브로커 | 간단한 큐 |
| 처리량 | 매우 높음 | 높음 | 높음 |
| 데이터 저장 | 일정 기간 저장 | 소비 후 삭제 | 메모리 기반 |
| 메시지 재처리 | 가능 | 어려움 | 어려움 |
| 순서 보장 | Partition 단위 | Queue 단위 | Queue 단위 |
| 대표 사용처 | 로그, 이벤트, 데이터 파이프라인 | 업무 메시지 처리 | 실시간 작업 큐 |

### Kafka

- 대용량 이벤트 처리
- 로그 수집
- 데이터 파이프라인
- 이벤트 기반 아키텍처

### RabbitMQ

- 작업 큐
- 이메일 발송
- 주문 처리
- RPC 통신

### Redis Queue

- 빠른 작업 처리
- 실시간 알림
- 캐시 기반 작업 큐
- 간단한 비동기 작업

> 간단히 정리하면 **Kafka는 이벤트를 저장하고 여러 Consumer가 재사용할 수 있는 스트리밍 플랫폼**, **RabbitMQ는 메시지를 전달하고 처리하는 데 초점을 둔 메시지 브로커**, **Redis Queue는 빠르고 단순한 작업 큐**라고 이해하면 된다.
>
